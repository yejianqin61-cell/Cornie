# 011 待确认动作持久化与会话建模

## 1. 任务目标

为确认流补齐后端基础设施，让 `policyDecision = confirm` 不再只是一次性返回给前端，而是能够在本地持久化为“待确认动作”，供用户后续同意或拒绝。

本任务完成后，应至少具备：

- 后端存在待确认动作的数据模型
- 一次对话触发的确认请求可持久化到本地
- 待确认动作与原始消息、tool call、来源文本建立关联
- 后续任务可基于该数据恢复执行链路

## 5. 数据建模要求

建议新增待确认动作表，例如：

```sql
CREATE TABLE IF NOT EXISTS pending_confirmations (
  id TEXT PRIMARY KEY,
  date TEXT NOT NULL,
  conversation_message_id TEXT NOT NULL,
  status TEXT NOT NULL,
  source_text TEXT,
  assistant_reply TEXT,
  confirm_type TEXT NOT NULL,
  tool_calls_json TEXT NOT NULL,
  confirm_request_json TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  resolved_at INTEGER
);
```

### 字段要求

- `id`
  - 待确认动作唯一标识
- `date`
  - 所属对话日期
- `conversation_message_id`
  - 触发该确认流的 Cornie 消息 id
- `status`
  - `pending` / `approved` / `rejected` / `executed` / `failed`
- `source_text`
  - 引发该动作的用户原始表述
- `assistant_reply`
  - 模型在发起确认前给出的自然语言回复
- `confirm_type`
  - 类目新增、长期记忆写入、删除动作等类型标识
- `tool_calls_json`
  - 原始待执行 tool calls
- `confirm_request_json`
  - 发送给前端展示的确认卡片结构

## 6. 输出结构设计

建议补充统一结构：

```ts
type PendingConfirmation = {
  id: string
  date: string
  status: 'pending' | 'approved' | 'rejected' | 'executed' | 'failed'
  sourceText: string
  assistantReply: string
  confirmType: string
  toolCalls: ToolCall[]
  confirmRequest: ConfirmRequest
  createdAt: number
  updatedAt: number
  resolvedAt?: number | null
}
```

## 7. 实现步骤

### Step 1

在 `electron/db.js` 中新增表结构与基础 CRUD 方法：

- `createPendingConfirmation`
- `getPendingConfirmation`
- `updatePendingConfirmationStatus`
- `listPendingConfirmationsByDate`

### Step 2

新增 `electron/backend/confirm/service.js`

服务职责：

- 创建待确认动作
- 查询待确认动作
- 标记已同意 / 已拒绝 / 已执行 / 已失败

### Step 3

修改 `orchestrator.js`

当 `policyDecision.decision === 'confirm'` 时：

- 保存待确认动作
- 将 `pendingConfirmationId` 一并返回给前端
- 返回结构中保留 `policyDecision.confirmRequest`

### Step 4

统一后端返回结构

确保 `/api/conversations` 的返回中包含：

- `policyDecision`
- `pendingConfirmation`

或至少包含：

- `pendingConfirmationId`
- `confirmRequest`

## 8. 测试点

### 8.1 单元测试建议

- 创建待确认动作后能正确读回
- 状态更新后字段正确变化
- `tool_calls_json` 与 `confirm_request_json` 能正确序列化与反序列化

### 8.2 联调测试

- 模型触发新增类目确认时，数据库中出现一条 `pending` 状态记录
- 前端收到的确认卡片与数据库持久化内容一致
- 同一次确认请求不会重复创建多条相同记录

## 9. 完成标准

- 存在独立的待确认动作持久化模型
- `confirm` 类型动作可在后端被可靠保存
- 前端后续可通过 `pendingConfirmationId` 继续推进确认流程

## 10. 注意事项

- 不要只把确认请求保存在内存中
- `toolCalls` 必须保留原始参数，后续恢复执行时不得重新猜测
- 持久化结构应兼容后续新增确认类型
