# 256-8.3-治理结果历史页到提醒中心与待审核池的跨页回流说明增强

## 1. 任务目标

在 `251`、`252`、`253` 已补齐治理结果历史页长期浏览态、摘要和空态基础上，继续增强历史页与提醒中心、待审核池之间的跨页回流说明，让用户能理解“过去的治理结果”和“当前仍需关注的问题”之间的关系。

## 2. 背景与现状

治理结果历史页和当前提醒中心/待审核池本来就不是同一个页面语义，但用户会自然在它们之间来回跳转。若没有补充说明，会出现：

1. 用户从历史页跳回提醒中心后，不清楚为何要回去
2. 用户从提醒中心跳到历史页后，不清楚是在看过去结果还是当前问题
3. 三个页面之间的关系容易被误解成重复功能

## 3. 涉及范围

- Memory Wiki 治理结果历史页
- 提醒中心
- 待审核池
- 跨页来源说明与回流提示
- 对应前端测试

## 4. 前置依赖

1. `251-8.3-Memory-Wiki治理结果历史页长期浏览态与筛选持久化增强.md` 已完成或至少已有历史页
2. `232-8.3-巡检提醒中心与待审核入口统一收口增强.md` 已完成或至少已有提醒中心

## 5. 具体开发项

### 5.1 跨页来源说明

1. 从历史页跳到提醒中心或待审核池时，说明这是在查看当前仍相关的问题
2. 从提醒中心或待审核池跳到历史页时，说明这是在回顾过去处理结果
3. 来源说明文案应帮助用户分辨“现在”和“过去”

### 5.2 关系表达

1. 明确历史页记录的是已处理结果或已发生过的治理轮次
2. 明确提醒中心和待审核池承接的是当前待关注或待决策事项
3. 让用户明白两边是前后链路，而不是重复列表

### 5.3 回流状态保持

1. 从历史页去提醒中心再返回时，恢复原历史页筛选与滚动位置
2. 从提醒中心或待审核池回到历史页时，保留回流来源说明一小段时间
3. 不让跨页往返破坏各自页面的原浏览状态

### 5.4 弱打扰边界

1. 跨页说明要轻量，不做满屏导览
2. 若用户已多次在同一条链路来回，可自动降低提示强度
3. 优先帮助判断语义，不打断治理动作

### 5.5 测试补齐

1. 覆盖历史页到提醒中心的来源说明
2. 覆盖提醒中心回历史页的说明与位置恢复
3. 覆盖待审核池与历史页往返链路
4. 覆盖多次往返后的提示降级

## 6. 验收标准

1. 用户能清楚区分治理结果历史页与当前治理工作台的语义边界
2. 跨页往返后不容易迷路
3. 状态保持和来源说明都足够轻量
4. 对应前端测试通过
