# 299-8.2-观察日志用户进入实际整理流后的顶部合并提示退场增强

## 1. 任务目标

在 `295` 已补齐观察日志跨模块弱提示与本地恢复提示合并摘要基础上，继续细化用户一旦真正进入编辑、批量整理或逐条处理流程后，顶部合并提示如何快速退场、保留最少必要上下文，以及何时允许再次出现。

## 2. 背景与现状

观察日志页的合并提示是帮助用户理解“你是从哪里回来、当前要续哪段现场”。但一旦用户开始真实操作，如果提示还长时间停留，就会出现：

1. 顶部提示反复占位，干扰整理界面
2. 用户已经进入当前任务，提示却还在重复说明前情
3. 主工作区和顶部说明区同时争夺注意力

## 3. 涉及范围

- 观察日志工作台顶部合并提示
- 编辑态、批量整理态、逐条处理态
- 退场、最小保留和再次出现规则
- 对应前端测试

## 4. 前置依赖

1. `295-8.2-观察日志跨模块弱提示与本地恢复提示并存时的合并摘要增强.md` 已完成或至少已有合并提示
2. `235-8.2-观察日志批量补全小控制台与连续处理增强.md` 已完成或至少已有连续处理流
3. `193-8.2-观察日志详情编辑表单与删除确认收口.md` 已完成或至少已有编辑态主流程

## 5. 具体开发项

### 5.1 进入实际整理流的判定

1. 明确哪些行为代表用户已经进入真正整理阶段，例如开始编辑、保存草稿、批量处理下一条
2. 判定成立后，顶部合并提示应从解释模式转入让位模式
3. 浏览停留不等于实际整理，不应过早退场

### 5.2 提示退场与最小保留

1. 顶部合并提示在进入整理流后快速退场
2. 若仍需保留上下文，只保留极简状态条或返回来源入口
3. 不同时保留完整摘要和完整面包屑

### 5.3 再次出现条件

1. 用户中断整理并回到列表态后，可重新评估是否显示摘要
2. 用户切换到全新条目或新日期时，可按新上下文重建提示
3. 同一条处理流中不反复弹出相同说明

### 5.4 与恢复态兼容

1. 顶部提示退场不影响本地恢复态本身
2. 需要时仍可通过次级入口回看来源说明
3. 与跨天降级、互斥恢复态和跨模块回流兼容

### 5.5 测试补齐

1. 覆盖进入编辑态后的顶部提示退场
2. 覆盖进入批量整理态后的极简保留
3. 覆盖中断整理回到列表态后的重新评估
4. 覆盖切换新日期或新条目后的新上下文重建

## 6. 验收标准

1. 观察日志用户进入真实工作流后，界面会快速把注意力让给主工作区
2. 解释性提示不会在整理过程中长期占位
3. 需要时仍可找回来源和恢复上下文，不会彻底丢失
4. 对应前端测试通过
