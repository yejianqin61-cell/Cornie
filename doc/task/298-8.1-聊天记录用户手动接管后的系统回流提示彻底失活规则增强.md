# 298-8.1-聊天记录用户手动接管后的系统回流提示彻底失活规则增强

## 1. 任务目标

在 `286`、`290`、`294` 已补齐聊天记录多入口回流、刷新防重放与空态冲突收口基础上，继续细化当用户已经主动接管聊天记录浏览后，系统回流提示、自动落点和恢复建议何时应彻底失活，避免“人已经自己在看了，系统还在旁边继续提醒”。

## 2. 背景与现状

聊天记录页的系统辅助能力越来越多，包括：

1. 外部回流提示
2. 自动滚动落点
3. 最近访问恢复提示
4. 空态下的来源说明

这些能力本来是帮助用户快速进入上下文，但当用户已经明确开始手动操作时，如果不及时收口，会出现：

1. 用户已经手动切换日期，旧提示还挂着
2. 用户已经自己滚到别处，系统还在保留“回到这里”的说明
3. 页面看起来像是系统仍在主导，而不是用户已经接管

## 3. 涉及范围

- 聊天记录工作台
- 外部回流提示、最近访问恢复提示、空态来源说明
- 用户手动操作识别与系统提示失活逻辑
- 对应前端测试

## 4. 前置依赖

1. `286-8.1-聊天记录多入口回流并发时的主落点判定与提示降级增强.md` 已完成或至少已有回流主次规则
2. `290-8.1-聊天记录刷新后回流语义残留与错误复现防护增强.md` 已完成或至少已有回流失活防护
3. `294-8.1-聊天记录空态与旧回流恢复态并存时的优先级与文案收口增强.md` 已完成或至少已有空态合并说明

## 5. 具体开发项

### 5.1 用户手动接管判定

1. 明确哪些行为算作用户已接管，例如手动切换日期、主动搜索、手动滚动较大距离
2. 接管判定一旦成立，旧系统提示应进入失活倒计时或立即退场
3. 不把轻微滚动抖动误判为明确接管

### 5.2 提示彻底失活

1. 外部回流提示在用户接管后不再以主提示身份存在
2. 最近访问恢复提示在用户主动重新定位后彻底失活
3. 空态来源说明仅在仍有解释价值时保留，否则收口

### 5.3 自动落点关闭

1. 用户接管后，同一轮上下文里不再继续触发自动跳读
2. 即使数据刷新，也不应因旧回流状态再次尝试拉回
3. 只有新的明确外部入口到来时，才允许重新启动系统引导

### 5.4 轻量保留与再进入

1. 若仍需保留历史来源信息，应降级为非打断式小入口
2. 用户重新点击来源入口时，视为新一轮明确请求
3. 与空态、搜索态、跨模块回流态兼容

### 5.5 测试补齐

1. 覆盖用户切换日期后的旧提示退场
2. 覆盖用户主动搜索后的恢复提示失活
3. 覆盖用户大幅滚动后的自动落点关闭
4. 覆盖新的外部入口到来后重新启用引导

## 6. 验收标准

1. 聊天记录页在用户主动接管后会明显“把方向盘交还给人”
2. 旧系统提示不会在用户已明确操作后继续刷存在感
3. 新旧引导轮次边界清楚，不互相污染
4. 对应前端测试通过
