# 231-8.3-Memory-Wiki待审核池排序模式与批量浏览增强

## 1. 任务目标

在 `181`、`182`、`195`、`200` 已补齐待审核提醒、候选分区和快捷治理入口的基础上，继续增强待审核池的排序模式和批量浏览能力，让用户可以按轻重缓急处理治理请求，而不是单条线性翻页。

## 2. 背景与现状

随着记忆治理候选增多，用户会更关心“先看什么、怎么成批处理”。当前虽然已有待审核区，但仍会存在：

1. 候选项较多时，只能顺序浏览，处理效率低
2. 高风险、高频、最新到达的候选混在一起，不利于排优先级
3. 批量扫读时难以快速比较候选之间的差异

## 3. 涉及范围

- Memory Wiki 待审核池
- 候选列表排序与分组工具区
- 批量浏览交互
- 对应前端测试

## 4. 前置依赖

1. `181-8.2-Memory-Wiki待审核角标与异步提醒增强.md` 已完成或至少已有待审核提醒
2. `182-8.3-治理候选分区与批量处置工作台增强.md` 已完成或至少已有候选分区基础

4. `200-8.3-Memory-Wiki高频治理快捷入口与状态概览增强.md` 已完成或至少已有状态概览

## 5. 具体开发项

### 5.1 排序模式

1. 支持按最新到达、风险等级、主题热度、影响范围等维度排序
2. 默认排序策略要清楚表达“优先建议你先看什么”
3. 排序切换后保持候选状态和已展开项尽量稳定

### 5.2 批量浏览视图

1. 在列表中提供更适合扫读的紧凑卡片模式
2. 支持连续预览上一条 / 下一条候选，不必每次退回列表
3. 对同类候选提供成组查看入口，方便批量判断

### 5.3 候选比较辅助

1. 在列表层展示来源数量、涉及页面数、最近触发时间等摘要
2. 让用户在打开详情前，先做轻量排优先级
3. 避免让全部判断都只能依赖深度展开详情

### 5.4 状态记忆

1. 记住最近使用的排序模式和浏览密度
2. 从候选详情返回列表时恢复原浏览位置
3. 保持与 `213` 这类筛选持久化任务的行为一致

### 5.5 测试补齐

1. 覆盖不同排序模式
2. 覆盖紧凑浏览与连续预览
3. 覆盖返回列表后的原位置恢复
4. 覆盖无候选与大量候选两类极端场景

## 6. 验收标准

1. 待审核池可以支撑高频治理，而不是只适合少量候选
2. 用户能更自然地按优先级处理治理请求
3. 排序与批量浏览增强不破坏现有候选详情能力
4. 对应前端测试通过
