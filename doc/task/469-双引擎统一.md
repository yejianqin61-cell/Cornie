# 469 双引擎统一

## 背景

聊天记录存在双引擎读写并存（Cornie-018 D-15）：写走 sql.js、读走 better-sqlite3（`server.js` 显式 `CHATLOG_REPOSITORY_DRIVERS.betterSqlite3`），且 `repository.js` L270 明确"better-sqlite3 chatlog repository is not implemented yet"——已注册为运行驱动但实现是死骨架，行为一致性风险高（Cornie-019 后端审查 P0-3）。

## 目标

1. 明确唯一写引擎（推荐 better-sqlite3 全面接管，sql.js 仅作兼容读取/迁移）。
2. 消除"两份真相"（sql.js 内存态 vs better-sqlite3 磁盘态）。
3. 原生依赖打包校验（electron-rebuild）。

## 范围

- `electron/backend/chatlog/repository.js`（实现 better-sqlite3 驱动或明确回退 sql.js 单引擎）
- `electron/backend/server.js`（驱动选择）
- `electron/db.js`（持久化策略配合）
- 打包/依赖脚本（electron-rebuild 校验）

## 设计要求

### 1. 方案决策（二选一，需记录决策）

- 方案 A（推荐）：聊天记录读写全部迁移 better-sqlite3（repository 已抽象，删除 sql.js 写路径）。
- 方案 B：明确 sql.js 保留范围并文档化边界，删除 better-sqlite3 死骨架。

### 2. 一致性

- 读写一致性测试通过（同一文件同一引擎）。
- 删除 `createBetterSqlite3ChatlogRepositorySkeleton` 死骨架（配合 467）。

### 3. 打包校验

- 原生依赖（better-sqlite3）在 Electron 运行时 ABI 匹配校验（electron-rebuild 纳入构建流程）。

## 验收标准

1. 单一引擎路径生效（读与写同一实现）。
2. 读写一致性测试通过。
3. 决策记录写入本任务文档修订。
4. 打包后聊天记录读写正常（原生模块 ABI 校验通过）。

## 决策记录（469 交付物）

**方案 B（已实施）：聊天记录统一 sql.js 单引擎，删除 better-sqlite3 全部路径。**

- **理由**：
  1. 当前写路径为 sql.js（内存态 + 每次写全量导出持久化），better-sqlite3 只读打开同一磁盘文件，构成"双份真相"；任何未来把写路径切到 better-sqlite3 或加异步持久化，都会整库覆盖丢数据（Cornie-019 后端审查 P0-3）。
  2. better-sqlite3 为原生模块（NODE_MODULE_VERSION 敏感），Electron/Node 版本不一致即无法加载（本环境已实证），且每次查询新建/关闭连接性能差。
  3. 方案 A（全面迁移 better-sqlite3 作为唯一写引擎）改动面大、风险高，需 WAL/事务/原子写配套，建议作为独立的数据库重构项目（对齐 db.js 持久化重构）另行排期。
- **实施**：
  - `chatlog/repository.js`：删除 `BetterSqlite3` 导入、只读连接/probe、`createBetterSqlite3ChatlogRepository`（约 210 行）；`createChatlogRepository` 恒返回 sql.js 兼容驱动；`CHATLOG_REPOSITORY_DRIVERS` 仅剩 `sqljs`。
  - `electron/server.js`：chatlog 驱动显式 `sqljs`。
  - `package.json`：移除 `better-sqlite3` 依赖（应用运行时不再加载原生模块，消除 ABI 风险）。
  - `scripts/verify-task396` 断言更新为 sql.js 默认；`verify-task367`（测被删驱动的孤儿脚本）删除。
- **验证**：`verify-task396/404/086` 全绿；fast 套件 chatlog 相关通过。
- **遗留（后续项目）**：db.js 的 sql.js 全量导出持久化（P0-1）与内存态/磁盘态一致性，需独立排期重构（迁移方案 A 时一并处理）。
