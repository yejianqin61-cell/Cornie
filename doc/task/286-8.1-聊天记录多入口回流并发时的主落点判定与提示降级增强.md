# 286-8.1-聊天记录多入口回流并发时的主落点判定与提示降级增强

## 1. 任务目标

在 `250`、`255`、`282` 已补齐聊天记录与 Cornie 日记回看链路、同日多来源提示优先级、回看失效替代落点基础上，继续细化“多个外部入口几乎同时回流到聊天记录”时的主落点判定、提示降级和状态冲突消解，避免页面一次性叠出多层提示。

## 2. 背景与现状

随着同日总览、Cornie 日记、观察日志、Memory Wiki 之间的互跳越来越多，聊天记录页可能会同时接收到多类回流语义：

1. 来自 Cornie 日记的回看请求
2. 来自同日总览的关系查看请求
3. 来自观察日志的来源回跳请求
4. 来自搜索或最近访问恢复的内部定位请求

如果缺少统一判定，会出现：

1. 多个提示条同时出现，用户分不清当前主语义
2. 锚点落点和提示来源不一致
3. 页面先后多次滚动，造成阅读位移漂移

## 3. 涉及范围

- 聊天记录工作台
- 聊天记录外部回流状态管理
- 提示条优先级、落点判定与自动降级逻辑
- 对应前端测试

## 4. 前置依赖

1. `250-8.1-聊天记录与Cornie日记之间的回看面包屑增强.md` 已完成或至少已有日记回看提示
2. `255-8.1-同日总览多来源回流提示优先级规则增强.md` 已完成或至少已有多来源优先级基础
3. `282-8.1-聊天记录回看链路失效后的同日替代落点与说明增强.md` 已完成或至少已有失效回落落点

## 5. 具体开发项

### 5.1 主落点判定

1. 在单次进入聊天记录时，只确定一个主落点来源
2. 主落点优先服务“明确回看任务”，其次才是一般浏览恢复
3. 若多个来源指向同一日期但不同消息区，优先采用更精确的锚点来源

### 5.2 提示降级

1. 主来源提示保留完整表达
2. 次级来源提示降级为轻量说明或合并摘要
3. 避免多个提示条并列占据聊天记录顶部

### 5.3 滚动与状态冲突消解

1. 页面进入后只执行一次主滚动定位
2. 次级来源不再重复触发自动跳读
3. 用户手动滚动后，剩余次级提示进一步降级或收起

### 5.4 弱冲突与例外

1. 若两个来源都失效，优先回落到同日可读区域并统一提示
2. 若主来源已完成定位，内部“最近访问恢复”只保留非打断式状态
3. 若用户主动切换日期，所有旧回流语义应立即失活

### 5.5 测试补齐

1. 覆盖日记回看与同日关系提示并存时的主落点判定
2. 覆盖主落点已执行后次级提示的降级
3. 覆盖多来源都失效时的统一回落
4. 覆盖用户手动切换日期后的回流状态清理

## 6. 验收标准

1. 多入口回流并发时，聊天记录只表现出一个清楚的主落点语义
2. 页面不会因多来源竞争而多次自动滚动
3. 次级提示存在但不打架、不抢主阅读流
4. 对应前端测试通过
