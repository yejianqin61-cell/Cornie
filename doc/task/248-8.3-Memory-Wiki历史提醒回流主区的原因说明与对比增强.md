# 248-8.3-Memory-Wiki历史提醒回流主区的原因说明与对比增强

## 1. 任务目标

在 `241` 和 `247` 已补齐历史提醒区、筛选清理边界基础上，继续增强历史提醒重新回流主提醒区时的原因说明和前后对比表达，让用户知道“为什么这条老提醒又回来了”。

## 2. 背景与现状

历史提醒支持重新激活是必要的，但如果没有解释，就会产生困惑：

1. 用户以为自己已经处理过，为什么又出现在主提醒区
2. 旧提醒重新激活后，和上次相比到底变了什么不清楚
3. 若没有对比表达，回流体验会显得随机

## 3. 涉及范围

- Memory Wiki 主提醒区
- 从历史区回流主区的提醒卡
- 回流原因说明与前后差异提示
- 对应前端测试

## 4. 前置依赖

1. `241-8.3-Memory-Wiki提醒中心历史区与静默归档视图增强.md` 已完成或至少已有历史区
2. `247-8.3-Memory-Wiki历史提醒筛选搜索与批量清理边界增强.md` 已完成或至少已有历史区管理能力
3. `237-8.3-Memory-Wiki提醒中心已读暂缓与再次提醒规则增强.md` 已完成或至少已有再提醒规则

## 5. 具体开发项

### 5.1 回流原因说明

1. 对重新回到主区的提醒明确说明原因，例如风险升高、来源更新、问题再次出现
2. 说明应平实、可理解，不暴露过多内部术语
3. 原因说明默认简短，可展开查看更多细节

### 5.2 前后对比提示

1. 轻量展示这次回流与上次状态相比的关键变化
2. 让用户知道是“旧问题未解决”还是“出现了新证据”
3. 不要求完整 diff，但至少要有可理解的变化摘要

### 5.3 回流后动作指引

1. 在回流提醒卡上提供合适的下一步入口
2. 区分“重新查看”与“重新审核”两类动作
3. 让用户不必自己猜这次回流该怎么处理

### 5.4 与历史区协同

1. 历史区中该项的旧状态应与主区当前状态保持可追溯关系
2. 回流后仍可返回查看它的历史上下文
3. 保持主区与历史区之间的关系清晰、非重复堆叠

### 5.5 测试补齐

1. 覆盖历史提醒回流主区时的原因说明
2. 覆盖关键变化摘要渲染
3. 覆盖回流后的动作入口差异
4. 覆盖主区与历史区的状态联动

## 6. 验收标准

1. 历史提醒重新激活时，用户知道为什么会再次出现
2. 回流后的提醒卡具备足够的变化上下文
3. 主区与历史区关系清楚，不让用户产生随机感
4. 对应前端测试通过
