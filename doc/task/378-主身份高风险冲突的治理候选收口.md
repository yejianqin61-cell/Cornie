# 378-主身份高风险冲突的治理候选收口

## 1. 任务目标

根据 `Cornie-0630-Identity记忆实体模型与页面结构设计.md`、`Cornie-0630-记忆层改进治理总纲-第一版.md` 与既有 `352-主身份冲突更新确认流与治理候选补齐.md` 的约束，先把 `identity_profile` 高风险冲突的后端治理候选链路补齐，让主身份页在遇到名字、称呼、与 Cornie 关系等冲突时，不只返回 `conflict`，还会正式沉淀到待治理池。

## 2. 任务来源

- `doc/design/Cornie-0630-Identity记忆实体模型与页面结构设计.md`
- `doc/design/Cornie-0630-记忆层改进治理总纲-第一版.md`
- `doc/task/352-主身份冲突更新确认流与治理候选补齐.md`

## 3. 涉及范围

- `electron/backend/identity/profileUpsert.js`
- `scripts/`

## 4. 当前问题

当前 `identity_profile` 已经具备冲突检测能力，但冲突发生后：

- 正式页不会被直接覆盖，这是对的
- 但也没有把冲突沉淀进治理候选池
- 结果是系统知道“名字/称呼/关系冲突了”，人类却看不到待处理项

这和 0630 设计稿里“高价值身份记忆必须支持确认与修订”“治理审核不耦合在聊天现场”的要求还不一致。

## 5. 目标设计

- 针对以下高风险字段冲突，自动创建治理候选：
  - `userName`
  - `preferredName`
  - `cornieRelationship`
- 冲突时继续保留旧正式值，不直接覆盖
- 治理候选中保留：
  - 冲突字段名
  - 旧值
  - 新值
  - 来源日期
  - 来源消息 ID
  - 来源标题
- 候选进入独立分区，供后续前端治理工作台或确认流消费

## 6. 实现步骤

### Step 1

在 `profileUpsert` 中新增“主身份冲突治理候选”辅助方法。

### Step 2

仅针对高风险字段冲突创建治理候选，避免把低价值摘要差异都塞进待审核池。

### Step 3

在 `conflict` 分支中创建治理候选，并保证正式页仍保留旧值。

### Step 4

新增验证脚本，证明主身份冲突会进入治理候选池且保留证据。

## 7. 测试点

- 用户名冲突会创建治理候选
- 与 Cornie 关系冲突会创建治理候选
- 治理候选中能看到旧值、新值与来源
- 正式页不会被冲突输入直接覆盖
- `npm run build` 通过
