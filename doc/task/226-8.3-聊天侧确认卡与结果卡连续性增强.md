# 226-8.3-聊天侧确认卡与结果卡连续性增强

## 1. 任务目标

在 `183`、`188`、`216` 已建立轻量治理提示、类目映射失败确认流和确认后恢复执行回显的基础上，继续把“确认卡 -> 用户同意或拒绝 -> 结果卡 -> 最终回复”的链路做得更连贯，减少用户对流程断点的困惑。

## 2. 背景与现状

当前确认流虽然已经能工作，但在视觉和叙事连续性上仍可能出现：

1. 用户确认后，不容易一眼看出这是在承接刚才哪张确认卡
2. 拒绝或取消后，缺少清晰的收口说明
3. 确认前后的结果表现风格不一致，导致体验割裂

## 3. 涉及范围

- 聊天区确认卡
- 确认完成后的结果卡与恢复执行卡
- 对应前端测试

## 4. 前置依赖

1. `183-8.3-聊天侧轻量治理提示与跳转入口.md` 已完成或至少已有聊天侧治理提示
2. `188-8.2-类目映射失败确认卡与新建类目决策流.md` 已完成或至少已有高价值确认卡模板
3. `216-8.3-聊天侧确认后恢复执行结果回显增强.md` 已完成或至少已有确认完成后的结果回显

## 5. 具体开发项

### 5.1 确认链路标识

1. 让结果卡明确指向它承接的是哪一次确认请求
2. 在确认完成后保留轻量“已同意 / 已拒绝 / 已跳过”的状态痕迹
3. 对跨时间稍长的确认恢复，也能让用户迅速回忆上下文

### 5.2 同意后的连续性

1. 确认成功后，结果卡应紧跟确认卡或形成明确连续关系
2. 恢复执行的步骤卡和最终结果卡之间要有轻量过渡
3. 避免让用户误以为确认后又开启了一个完全新的流程

### 5.3 拒绝与取消的收口

1. 用户拒绝后，明确说明本次流程止步于哪里
2. 若仍有可选替代动作，给出简洁提示
3. 对取消后的聊天收尾保持克制，不制造额外噪音

### 5.4 视觉与文案一致性

1. 确认前后的卡片层级、状态色和摘要风格尽量统一
2. 铃湾口吻应保持平实、可爱，但不影响信息判断
3. 不把确认流做成“弹窗式打断感”，而是自然嵌入聊天时间线

### 5.5 测试补齐

1. 覆盖同意后的结果链路
2. 覆盖拒绝后的收口状态
3. 覆盖跨时间恢复确认的上下文标识
4. 覆盖确认卡与结果卡样式一致性相关分支

## 6. 验收标准

1. 用户能清楚理解确认前后是同一条业务链
2. 同意、拒绝、取消三类路径都有清晰收口
3. 聊天确认体验更顺，不割裂
4. 对应前端测试通过
