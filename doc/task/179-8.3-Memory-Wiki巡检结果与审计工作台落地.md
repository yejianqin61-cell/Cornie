# 179-8.3-Memory-Wiki巡检结果与审计工作台落地

## 1. 任务目标

在当前治理待审核区、确认中心、版本历史面板基础上，继续补齐 Memory Wiki 的巡检结果与审计工作台，让用户能直接在前端查看断链、孤儿页、治理建议和关键操作审计，而不是让这些能力停留在后端或脚本层。

## 2. 背景与现状

当前系统已经具备：

1. 关键操作审计日志
2. 断链索引与失效来源引用巡检
3. 孤儿页面检查与修复建议输出
4. 治理待审核池
5. Memory Wiki 前端治理待审核区与确认中心

但前端当前还缺少：

1. 巡检结果的独立可视工作区
2. 审计日志的正式查看入口
3. 巡检结果与待审核区之间的前端联动
4. 人类对“哪些问题只是查看、哪些问题需要治理”的清晰分层

## 3. 涉及范围

- `src/renderer/components/MemoryWikiWorkspace.vue`
- `src/renderer/api.js`
- 如有必要，补充巡检 / 审计只读接口
- 对应前端测试

## 4. 前置依赖

1. `168-8.3-治理待审核区与确认中心产品化收口.md` 已完成
2. `171-8.3-治理筛选与详情证据面板增强.md` 已完成

## 5. 具体开发项

### 5.1 巡检结果面板

1. 增加巡检结果区域，至少支持断链、孤儿页、来源失效三类问题
2. 对每条问题显示问题类型、目标页面、发现时间、修复建议摘要
3. 区分“信息类结果”和“可进一步治理类结果”

### 5.2 与待审核区联动

1. 若某条巡检结果已生成治理候选，应明确展示其待审核状态
2. 支持从巡检结果跳转到对应待审核项或对应页面详情
3. 避免把信息型巡检结果错误地渲染成必须立即确认的高风险动作

### 5.3 审计日志查看入口

1. 增加关键操作审计列表
2. 至少显示操作类型、时间、目标页面、执行来源或执行人
3. 支持基础筛选，例如按页面、按操作类型查看

### 5.4 前端信息分层

1. 明确区分“查看巡检结果”“进入治理候选”“查看历史审计”三类区域
2. 保持文案克制，突出可理解性，不把运维术语直接堆给用户

### 5.5 测试补齐

1. 覆盖巡检结果列表渲染
2. 覆盖有治理候选与无治理候选两类分支
3. 覆盖审计日志列表渲染
4. 覆盖跳转或筛选入口逻辑

## 6. 验收标准

1. 用户在前端可正式查看 Memory Wiki 巡检结果
2. 用户可区分信息型巡检结果与待治理候选
3. 用户在前端可查看关键操作审计日志
4. 对应前端测试通过
