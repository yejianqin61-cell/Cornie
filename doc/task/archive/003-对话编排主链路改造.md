# 003 对话编排主链路改造

## 1. 任务目标

把当前“用户消息 -> 模型回复”的简单链路升级为完整的 Agent 编排链路。

本任务完成后：

- 可装载摘要上下文
- 可进行首轮模型调用
- 可解析 `reply / tool_call`
- 可在工具执行后再次调用模型生成最终回复
- 可控制单轮通信上限

## 5. 目标结构

### 5.1 `contextBuilder.js`

负责读取并整理：

- 最近几轮对话摘要
- 当前类目摘要
- 未完成待办摘要
- 近期日程摘要
- 今日观察日志摘要
- 长期记忆摘要

### 5.2 `promptBuilder.js`

负责构建：

- 人格 prompt
- JSON 协议说明
- 工具说明
- 上下文摘要块

### 5.3 `orchestrator.js`

负责：

- 首轮模型调用
- 协议解析
- 分支判断
- 工具结果二次调用
- 轮次上限控制

## 6. 对话流程

```text
1. 收到用户消息
2. 保存用户消息
3. 装载上下文摘要
4. 构造 prompt
5. 首轮调用模型
6. 解析 JSON
7. 若 reply：直接结束
8. 若 tool_call：进入策略层/工具层
9. 收到 tool_result
10. 二次调用模型生成最终回复
11. 保存最终回复
12. 返回前端
```

## 7. 接口改动

### 7.1 现有接口

`POST /api/conversations`

建议响应结构升级为：

```json
{
  "userMessage": {},
  "cornieMessage": {},
  "toolExecution": {
    "used": true,
    "results": []
  }
}
```

### 7.2 兼容要求

- 前端若暂时不消费 `toolExecution`，也不能报错

## 8. 实现步骤

### Step 1

提炼 `contextBuilder.js`

- 暂时先用空数据或 stub 替代未实现模块
- 确保返回结构稳定

### Step 2

提炼 `promptBuilder.js`

- 固定 prompt 分段
- 统一“铃湾 / 小铃湾”人格设定

### Step 3

重构 `conversation/service.js`

- 不再把业务逻辑全写在一个函数里
- 改为 orchestration 风格

### Step 4

接入 JSON 协议解析

- `reply` 走直接返回
- `tool_call` 先预留调用点

### Step 5

增加轮次控制

- 最多 1 次工具调用主回合
- 最多 1 次修复重试
- 最多 1 次只读补查

## 9. 测试点

### 9.1 单元测试建议

- 上下文构建器在无待办、无观察日志时也能返回稳定结构
- `reply` 流程可直接结束
- `tool_call` 流程可正确进入下一步

### 9.2 联调测试

- 普通聊天能正常返回
- 需要工具的回复能返回 `toolExecution`
- 二次调用后的最终自然语言回复正常
