# 004 工具策略层与确认流落地

## 1. 任务目标

建立 Tool Policy Layer，使模型提出的工具调用先经过风险判断和业务审查，再决定是否执行。

本任务完成后：

- 工具有风险分级
- 高风险动作不会被盲执行
- 新增类目、长期记忆写入等可走确认流
- 模型提议过强时可自动降级

## 5. 策略层输出结构

```ts
type PolicyDecision =
  | { decision: 'allow' }
  | { decision: 'confirm', confirmRequest: ConfirmRequest }
  | { decision: 'ask_back', question: string }
  | { decision: 'deny', reason: string }
```

## 6. 风险分级

| 风险级别 | 工具示例 | 默认行为 |
| --- | --- | --- |
| 低风险 | `list/get` 查询工具 | 直接执行 |
| 中风险 | 新增收支、待办、日程、观察日志 | 参数齐全且置信度高时可执行 |
| 高风险 | 删除、改类目、新增类目、写长期记忆 | 需要确认或拒绝 |

## 7. 核心规则

### 7.1 财务规则

- 无金额不得执行 `ledger.add_expense`
- 无可映射类目不得直接执行写入
- 低置信度不得直接执行

### 7.2 类目规则

- 类目新增默认进入确认流
- 类目删除默认进入确认流

### 7.3 长期记忆规则

- 只有稳定偏好、长期目标、重大事件才允许写入
- 含糊表达不允许直接写入

### 7.4 观察日志规则

- 与今日已存在日志高度重复时不新增

## 8. 确认流设计

确认流至少覆盖：

- 新增类目
- 长期记忆写入
- 删除数据
- 修改历史账目

前端接收到确认流后，需展示：

- 动作说明
- 原始来源文本
- 用户可同意/拒绝

## 9. 自动降级规则

示例：

- 模型要直接写账，但信息不足
  - 降级为追问
- 模型要直接新增类目
  - 降级为确认请求
- 模型连续提多个高风险写操作
  - 降级为保留主动作，其余延后或追问

## 11. 测试点

### 11.1 单元测试建议

- 高风险工具返回 `confirm`
- 条件不足的记账请求返回 `ask_back`
- 无效 tool call 返回 `deny`

### 11.2 联调测试

- 新增类目时前端能收到确认请求
- 长期记忆写入不会直接静默落库
- 低信息量财务表达不会误执行写账

## 12. 完成标准

- 存在独立 Tool Policy Layer
- 策略层能输出允许、确认、追问、拒绝四种结果
- 编排链路已接入策略层

## 13. 注意事项

- 不要把所有规则写死在 conversation service 里
- 策略层和工具层必须解耦
- 前端确认流协议要尽量稳定，避免后续反复改
