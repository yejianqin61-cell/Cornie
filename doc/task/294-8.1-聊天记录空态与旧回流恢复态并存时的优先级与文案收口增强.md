# 294-8.1-聊天记录空态与旧回流恢复态并存时的优先级与文案收口增强

## 1. 任务目标

在 `282`、`286`、`290` 已补齐聊天记录回流回落、多入口冲突消解和刷新后防重放基础上，继续细化“当前日期空态”与“旧回流恢复态”并存时的优先级、提示合并与文案收口，避免用户看到既像空态又像还在回流的矛盾界面。

## 2. 背景与现状

聊天记录工作台在跨模块联动后，可能同时存在：

1. 某个外部入口带来的回流语义
2. 当前日期没有聊天记录的空态
3. 最近访问或搜索恢复留下的内部状态

如果没有统一规则，就会出现：

1. 空态文案和回流提示互相打架
2. 用户分不清“这里真的没内容”还是“系统还在尝试回到旧位置”
3. 页面顶部提示太多，但没有一个真正解释当前状态

## 3. 涉及范围

- 聊天记录工作台空态区
- 外部回流提示、最近访问恢复提示与空态说明
- 优先级、合并摘要与退场逻辑
- 对应前端测试

## 4. 前置依赖

1. `233-8.1-聊天记录搜索空态与恢复建议卡增强.md` 已完成或至少已有空态体系
2. `282-8.1-聊天记录回看链路失效后的同日替代落点与说明增强.md` 已完成或至少已有回流回落说明
3. `290-8.1-聊天记录刷新后回流语义残留与错误复现防护增强.md` 已完成或至少已有回流失活防护

## 5. 具体开发项

### 5.1 空态与回流态优先级

1. 当当前日期确实无聊天记录时，空态应成为主语义
2. 旧回流语义在空态场景下应降级为“来源说明”而非主提示
3. 最近访问恢复不得压过真实空态

### 5.2 文案收口

1. 明确区分“本日没有聊天记录”和“原回流位置已不可用”
2. 若两者同时成立，应合并成一条更自然的解释
3. 文案保持用户语言，不出现工程化状态描述

### 5.3 行动入口排序

1. 空态下优先给出最合理的下一步动作，例如切换日期或回到来源页
2. 回流来源相关入口保留，但降级为次级动作
3. 避免空态区域和提示条同时给出重复按钮

### 5.4 失活与退场

1. 用户切换到其他日期后，旧空态合并说明应立即失活
2. 用户从空态转入有内容日期后，不保留无意义空态提示
3. 与搜索筛选空态、最近访问恢复逻辑兼容

### 5.5 测试补齐

1. 覆盖当前日期空态与旧回流语义并存时的主次判定
2. 覆盖合并文案与按钮排序
3. 覆盖用户切换日期后的状态退场
4. 覆盖搜索空态与回流空态并存时的冲突消解

## 6. 验收标准

1. 聊天记录空态场景下只有一个清晰主语义
2. 用户能看懂“没内容”和“回不去旧位置”之间的区别
3. 回流说明存在但不破坏空态页面的清晰度
4. 对应前端测试通过
