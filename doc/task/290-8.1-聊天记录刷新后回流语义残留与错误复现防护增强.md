# 290-8.1-聊天记录刷新后回流语义残留与错误复现防护增强

## 1. 任务目标

在 `282`、`286` 已补齐聊天记录回看失效回落与多入口回流冲突消解基础上，继续细化页面刷新、组件重挂载或数据重拉后，旧回流语义残留、二次误触发和提示错误复现的防护规则，避免用户刷新一次页面后又被旧回流逻辑重新“拽回去”。

## 2. 背景与现状

聊天记录工作台后续会频繁承接：

1. 来自同日总览的跳入
2. 来自 Cornie 日记的回看
3. 来自观察日志的来源回跳
4. 内部最近访问和搜索恢复

这些状态如果只在内存中粗略保存，刷新或重新挂载后容易出现：

1. 旧回流提示再次出现，但上下文其实已经过期
2. 页面又重新自动滚动到上一次的外部落点
3. 用户已经手动切换到新日期，刷新后却回到旧回流语义

## 3. 涉及范围

- 聊天记录工作台
- 回流状态持久化、失活与重挂载恢复逻辑
- 提示条、自动滚动与外部入口状态同步
- 对应前端测试

## 4. 前置依赖

1. `282-8.1-聊天记录回看链路失效后的同日替代落点与说明增强.md` 已完成或至少已有回流回落逻辑
2. `286-8.1-聊天记录多入口回流并发时的主落点判定与提示降级增强.md` 已完成或至少已有主落点和冲突消解逻辑
3. `228-8.1-聊天记录消息区滚动恢复与锚点跳读增强.md` 已完成或至少已有滚动恢复基础

## 5. 具体开发项

### 5.1 回流语义的有效期

1. 为外部回流语义定义“仅首次消费”或“短时有效”的明确边界
2. 页面刷新后，仅在回流仍被判定为有效时才允许恢复
3. 已消费完成的回流语义不得在刷新后重复触发主落点

### 5.2 刷新后的提示与滚动防重放

1. 刷新后若恢复的是普通浏览状态，不再重放外部回流提示
2. 刷新后若确有必要恢复回流提示，也只允许一次主滚动
3. 旧提示条在刷新后应依据有效性重建，而不是盲目照搬上次 UI 状态

### 5.3 用户主动操作优先

1. 用户手动切换日期后，应立即覆盖旧回流语义
2. 用户关闭提示后，刷新不应让同一提示重新冒出来
3. 用户手动滚动离开原落点后，刷新也不应强行再拉回

### 5.4 重挂载与数据重拉边界

1. 组件重挂载但数据未变时，不重复执行自动落点
2. 数据重拉导致消息结构变化时，只做安全回落，不做强制复跳
3. 与最近访问、搜索筛选和同日关系提示保持兼容

### 5.5 测试补齐

1. 覆盖回流语义已消费后刷新不再复现
2. 覆盖用户关闭提示后刷新不再复现
3. 覆盖手动切换日期后刷新优先保留用户选择
4. 覆盖数据重拉后的安全回落而非重复跳读

## 6. 验收标准

1. 聊天记录页刷新后不会错误复活过期回流语义
2. 用户手动操作优先级高于旧回流状态恢复
3. 自动滚动与提示条在刷新场景下依然克制、可预测
4. 对应前端测试通过
