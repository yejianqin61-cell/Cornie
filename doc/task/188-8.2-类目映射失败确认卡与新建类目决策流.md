# 188-8.2-类目映射失败确认卡与新建类目决策流

## 1. 任务目标

在现有确认流与收支 / 待办 / 日程工作台基础上，补齐“模型无法把当前内容匹配到现有类目”时的人类确认工作流，让用户能够清楚完成：

1. 查看模型为什么没有匹配成功
2. 查看可选的现有类目候选
3. 决定采用已有类目，还是新建类目
4. 在确认后继续完成原始业务动作

## 2. 背景与现状

当前系统已经有以下设计前提：

1. 每次记账、待办、日程处理前，模型会先参考现有类目
2. 若无法可靠映射，模型需要主动意识到可能要新建类目
3. 新建类目应先提请人类确认，而不是静默创建

但前端目前仍缺：

1. 类目映射失败时的统一提示卡
2. 已有类目候选的清晰比较展示
3. “采用已有类目 / 新建类目 / 取消本次操作”三路决策流
4. 确认后恢复原业务动作的产品化承接

## 3. 涉及范围

## 5. 具体开发项

### 5.1 映射失败提示卡

1. 当模型无法可靠匹配类目时，展示统一的映射失败确认卡
2. 卡片中说明当前要处理的原始内容，例如支出描述、待办标题、日程主题
3. 清楚标明“没有直接匹配到合适类目”的原因与后续可选动作

### 5.2 已有类目候选展示

1. 展示模型建议的已有类目候选列表
2. 每个候选至少展示名称、所属域、简短匹配理由
3. 支持用户直接选择其中一个已有类目

### 5.3 新建类目决策流

1. 支持用户选择“新建类目”
2. 展示模型建议的新类目名称与归属域
3. 支持用户修改类目名称后再确认创建
4. 明确说明新建后原业务动作会继续执行

### 5.4 取消与回退路径

1. 支持用户取消本次操作
2. 支持用户拒绝新建并返回已有类目选择
3. 对取消后的聊天结果给出明确状态反馈，而不是无声结束

### 5.5 确认后续执行业务动作

1. 用户确认已有类目或新建类目后，应自动恢复原始业务动作
2. 成功后在聊天侧或工具结果面板中展示最终执行结果
3. 若恢复执行失败，要有清晰兜底提示

### 5.6 测试补齐

1. 覆盖映射失败卡渲染
2. 覆盖已有类目候选选择分支
3. 覆盖新建类目确认与名称调整分支
4. 覆盖取消路径与恢复执行路径
5. 覆盖执行失败兜底状态

## 6. 验收标准

1. 用户能够看懂为什么当前内容没有匹配到现有类目
2. 用户能够在已有类目与新建类目之间做清晰决策
3. 确认后原始业务动作能够顺畅恢复执行
4. 收支、待办、日程三域均可复用这一确认模式
5. 对应前端测试通过
