# 189-8.3-聊天侧工具过程态与结果态反馈分层增强

## 1. 任务目标

在现有工具结果面板与记忆透明提示基础上，继续补齐聊天侧“工具调用过程态”与“最终结果态”的分层反馈，让用户能够理解：

1. 铃湾当前是在读取、查询，还是在写入、修改
2. 工具执行是成功、失败、取消，还是等待确认
3. 本轮回复和哪些工具动作有关

## 2. 背景与现状

当前前端已经具备或已拆解：

1. 基础确认卡
2. 工具结果面板
3. 记忆引用轻提示
4. 聊天侧轻量治理提示

但仍存在明显缺口：

1. 用户通常只能看到最终文本回复，很难理解中间做了什么
2. 只读补查与写入执行的风险感知没有被清楚区分
3. 失败、取消、等待确认的状态表达仍不够统一
4. 工具执行链路与最终回复之间缺少足够的可解释承接

## 3. 涉及范围

- 聊天消息渲染链路
- `ToolResultPanel.vue`
- `ConfirmCard.vue`
- 如有必要，前端工具状态归一化适配层
- 对应前端测试

## 4. 前置依赖

1. `174-8.3-记忆引用透明提示与工具结果面板增强.md` 已完成或至少提供基础结果面板
2. `183-8.3-聊天侧轻量治理提示与跳转入口.md` 已完成或至少提供聊天侧轻提示框架

## 5. 具体开发项

### 5.1 过程态反馈

1. 对只读补查类工具展示“正在查看 / 正在查询 / 正在读取”的过程态
2. 对写入类工具展示“正在写入 / 正在创建 / 正在更新”的过程态
3. 对等待确认类动作展示“等待你决定是否继续”
4. 过程态文案保持平实、轻量，不把聊天气泡刷得过密

### 5.2 结果态分层

1. 区分成功、失败、取消、待确认四类结果态
2. 成功结果展示简短结果摘要
3. 失败结果展示可理解的失败原因与下一步建议
4. 取消结果展示“已按你的意思停在这里”一类明确反馈

### 5.3 只读与写入的风险区分

1. 只读补查应使用更轻的视觉权重
2. 写入或修改动作应明确标记影响对象
3. 高风险动作仍由确认流承接，不在过程态中偷跑执行

### 5.4 最终回复联动

1. 若本轮回复依赖了工具结果，应允许用户展开查看对应工具摘要
2. 若本轮使用了多次工具，允许按顺序查看主要步骤
3. 避免把原始协议直接暴露给用户，保持人类可读表达

### 5.5 测试补齐

1. 覆盖只读补查过程态
2. 覆盖写入执行过程态
3. 覆盖成功 / 失败 / 取消 / 待确认四类结果态
4. 覆盖多工具串联时的展示顺序
5. 覆盖无工具调用时的静默边界

## 6. 验收标准

1. 用户能区分当前是补查、写入还是等待确认
2. 用户能看懂工具调用最终处于什么结果态
3. 工具调用反馈与最终回复之间关系清晰
4. 工具反馈不泄露协议噪音，也不制造过度打扰
5. 对应前端测试通过
