# 236-8.2-观察日志联动入口已处理态与消退规则增强

## 1. 任务目标

在 `204`、`215`、`230` 已补齐观察日志到 Cornie 日记、长期记忆和跨模块返回链路基础上，继续细化这些联动入口的“已处理态”“已查看态”和消退规则，让页面不会长期堆满过期提示。

## 2. 背景与现状

当观察日志与多个模块联动后，前端很容易出现提示越来越多的问题。若没有状态治理，会出现：

1. 用户已经处理过的联动提示还长期挂着
2. 页面上无法区分“未处理”“已查看”“已完成”
3. 久而久之联动提示会失去可信度

## 3. 涉及范围

- 观察日志联动提示区
- 到 Cornie 日记 / 长期记忆 / 聊天记录的状态标签
- 已读与已处理状态持久化
- 对应前端测试

## 4. 前置依赖

1. `204-8.2-观察日志到Cornie日记生成联动入口收口.md` 已完成或至少已有到日记入口
2. `215-8.2-观察日志中的长期记忆引用提示与跳转增强.md` 已完成或至少已有长期记忆联动提示
3. `230-8.2-观察日志跨模块整理队列与返回原位增强.md` 已完成或至少已有跨模块回流基础

## 5. 具体开发项

### 5.1 状态分层

1. 区分联动入口的未查看、已查看、已处理三类状态
2. 对已处理项以更克制的方式展示，不与未处理项抢注意力
3. 状态切换规则要清楚，不让用户猜系统在怎么算

### 5.2 消退规则

1. 已处理完成的联动提示可自动降级到次级区域
2. 仅查看但未真正完成的提示不应过早消失
3. 当外部模块状态回退或发生变更时，提示可重新激活

### 5.3 批量整理兼容

1. 与 `235` 的连续整理控制台协同，避免重复提示同一事项
2. 在同日多条日志场景下，保持联动状态更新一致
3. 让用户一眼能看出今天还有哪些联动没处理完

### 5.4 文案边界

1. 已处理态文案应有完成感，但不要夸大“系统已经完全理解”
2. 已查看态应表达“你看过了”，而不是“已经完成”
3. 铃湾口吻可以温柔，但不要影响状态辨识

### 5.5 测试补齐

1. 覆盖三类状态渲染
2. 覆盖已处理后的消退逻辑
3. 覆盖外部状态变更后的重新激活
4. 覆盖与连续整理控制台并存时的状态一致性

## 6. 验收标准

1. 观察日志联动提示不会长期失真或堆积
2. 用户能清楚区分哪些只是看过，哪些已经处理完
3. 联动状态治理不破坏跨模块跳转能力
4. 对应前端测试通过
