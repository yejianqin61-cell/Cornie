# 012 确认结果提交接口与状态流转

## 1. 任务目标

在待确认动作持久化的基础上，建立用户提交“同意 / 拒绝”结果的后端接口与状态流转规则。

本任务完成后，应至少具备：

- 前端可提交确认结果
- 后端可校验 `pendingConfirmationId`
- 用户同意或拒绝后，待确认动作状态可正确更新
- 非法状态流转会被拦截

## 5. 接口设计

建议新增接口：

### 5.1 提交确认结果

`POST /api/confirmations/:id/decision`

请求体：

```json
{
  "decision": "approve"
}
```

或：

```json
{
  "decision": "reject"
}
```

返回体建议：

```json
{
  "confirmation": {
    "id": "xxx",
    "status": "approved"
  },
  "execution": {
    "next": "resume_execution"
  }
}
```

### 5.2 查询单条待确认动作

`GET /api/confirmations/:id`

用途：

- 前端刷新后恢复确认卡状态
- 后续调试与联调

### 5.3 按日期列出待确认动作

`GET /api/confirmations?date=YYYY-MM-DD`

用途：

- 按天恢复会话状态
- 聊天记录与确认动作对齐

## 6. 状态流转规则

允许的状态流转建议如下：

| 当前状态 | 目标状态 | 是否允许 |
| --- | --- | --- |
| `pending` | `approved` | 允许 |
| `pending` | `rejected` | 允许 |
| `approved` | `executed` | 允许 |
| `approved` | `failed` | 允许 |
| `pending` | `executed` | 不允许 |
| `rejected` | `approved` | 不允许 |
| `executed` | 任意其他状态 | 不允许 |

## 8. 异常处理要求

需要明确处理：

- `id` 不存在
- 已经被处理过的确认动作再次提交
- 非法 `decision`
- 非法状态流转

返回应区分：

- 参数错误
- 记录不存在
- 状态冲突
- 服务端异常

## 9. 测试点

### 9.1 单元测试建议

- `pending -> approved` 成功
- `pending -> rejected` 成功
- 重复提交同一确认结果被拒绝
- 非法 `decision` 返回错误

### 9.2 联调测试

- 前端点击同意后，数据库状态从 `pending` 变为 `approved`
- 前端点击拒绝后，数据库状态从 `pending` 变为 `rejected`
- 刷新页面后仍可查询到已处理状态

## 10. 完成标准

- 存在独立确认结果提交接口
- 待确认动作状态流转明确且受约束
- 前端可调用接口提交同意 / 拒绝结果

## 11. 注意事项

- 这一步只负责“提交确认结果并更新状态”，不要把恢复执行逻辑硬塞进路由层
- 状态校验应放在 service 层，而不是只靠前端约束
