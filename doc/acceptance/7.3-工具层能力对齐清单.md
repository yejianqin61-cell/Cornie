# 7.3 工具层能力对齐清单

## 1. 文档目的

本清单用于在 `7.3` 阶段统一回答四个问题：

1. 设计要求模型应该拥有哪些工具能力。
2. 当前代码里哪些能力已经落地到服务层。
3. 哪些能力已经注册为 tool、哪些还没有。
4. 后续 `047-051` 应该按什么顺序补齐。

本清单是 `doc/task/046-工具层能力对齐清单与缺口矩阵.md` 的正式交付物。

## 2. 评估口径

### 2.1 状态定义

| 状态 | 说明 |
| --- | --- |
| 已对齐 | 服务层、工具层、风险口径基本一致，可供模型调用 |
| 部分对齐 | 某一层已存在，但还未完全打通到模型调用 |
| 语义有误 | 名字看似存在，但真实行为与设计目标不一致 |
| 未对齐 | 设计明确要求，但当前代码未具备 |

### 2.2 本次核对范围

- 工具注册层
- 服务层
- JSON 协议层
- 风险 / 策略层

不包含：

- 人类前端入口是否已全部补齐
- 发布态配置与引导

## 3. 总体结论

截至当前代码状态，Cornie 的工具层整体判断如下：

- 待办、日程、观察日志、长期记忆的基础工具雏形已经存在。
- 收支工具层缺口最大，仍停留在“新增 + 类目”阶段。
- 一部分能力已经在服务层或数据库层具备，但还没有暴露到模型可调用的工具层。
- 协议层和策略层目前主要围绕类目映射主链路构建，尚未完全覆盖 `7.3` 扩展后的完整工具集合。

一句话判断：

`当前 7.3 的核心工作，不是重做架构，而是把已有能力正式对齐到“模型可合法调用”的层面。`

## 5. 协议层与策略层专项判断

### 5.1 JSON 协议层现状

当前 `electron/backend/agent/jsonProtocol.js` 已对以下类目相关 action tool 做了参数校验口径：

- `ledger.add_expense`
- `ledger.add_income`
- `todo.create`
- `todo.update`
- `schedule.create`
- `schedule.update`

结论：

- 当前协议层更像“围绕类目映射主链路的专项校验层”
- 还不是“覆盖 7.3 全部工具”的统一协议准入层

建议归属：

- 在 `050` 中统一扩展和收口

### 5.2 风险层与策略层现状

当前 `riskLevels.js` 与 `rules.js` 的特点是：

- 高风险规则主要已覆盖 `memory.*`、`*.update`、`*.delete`、`category*`
- 类目映射规则已较成熟
- 对新增系统只读工具、收支生命周期扩展工具，仍缺统一核对

结论：

- 当前策略层足够支撑 `7.2`
- 进入 `7.3` 后必须继续坚持“新增工具同步进策略层”的纪律

建议归属：

- 在 `050` 中统一收口

## 6. 推荐开发顺序

### 6.1 推荐顺序

1. `047-收支工具生命周期补齐`
2. `048-待办与日程类目删除及语义修正`
3. `049-系统只读工具接入`
4. `050-协议白名单与策略层对齐`
5. `051-工具层联调与7.3验收`

### 6.2 排序原因

- 收支工具缺口最大，且是最明确的设计落差，优先补齐收益最高。
- 待办 / 日程当前主要是缺少少量工具与语义修正，适合第二步收口。
- 系统只读工具在业务闭环后补齐，可以减少对主链路理解的干扰。
- 协议与策略必须放在工具补齐后统一收口，避免重复改。
- 联调与验收必须最后做，保证 `7.3` 真正有结束证据。

## 7. 当前阻塞与非阻塞项

### 7.1 当前阻塞项

- 无外部阻塞。
- 当前缺的是工程实现，不缺设计和方向。

### 7.2 非阻塞但需注意项

- `schedule.delete` 语义错误是明显风险，不能拖到 `7.4`
- 收支删除语义需要尽早明确，否则测试口径会反复变动
- 已有大量未提交 task 文档存在于工作区，后续提交时要严格控制暂存范围

## 8. 本阶段完成标准

满足以下条件时，可认为 `046` 完成：

- 已有正式的 `7.3` 工具能力对齐清单
- 已明确每个缺口对应的后续任务
- 后续开发者不依赖历史聊天也能直接开始 `047-051`

## 9. 结论

`7.3` 的主问题已经很清楚：最核心的不是设计不清，而是“已有能力没有完全对齐到模型可调用层”。因此后续工作应按本清单顺序推进，优先补收支生命周期，其次修正待办 / 日程缺口，再统一收口协议和策略。
