# Cornie-017-记忆层后端大治理完成度与前端对齐分析报告

日期：2026-06-30

## 1. 文档目的

本文档用于对 Cornie 当前“记忆层后端大治理”后的实际落地情况进行一次偏验收视角的复评，重点回答四个问题：

1. 记忆层后端目前完成到了什么程度。
2. 各类核心业务情景的覆盖度如何。
3. 前端和后端的能力对齐程度如何。
4. 普通用户当前到底能看到什么、能操作什么。

本文评估基于以下实际代码与界面入口：

- 后端记忆治理：`electron/backend/memory-wiki/*`
- 普通用户记忆入口：`src/renderer/components/ObserveMemoryHome.vue`
- 普通用户记忆列表：`src/renderer/components/MemoryPageList.vue`
- 普通用户记忆详情：`src/renderer/components/MemoryPageDetail.vue`
- 观察日志列表与详情：`src/renderer/components/ObservationList.vue`、`ObservationDetail.vue`
- 高级入口：`src/renderer/components/AdvancedSettings.vue`
- 高级治理工作台：`src/renderer/components/MemoryWikiWorkspace.vue`

---

## 2. 总体结论

当前记忆层的**后端主链已经基本成型**，可以认为 Memory Wiki 体系已经从“设计稿阶段”进入“可运行、可治理、可追溯”的阶段。

综合评估如下：

- 记忆层后端总体完成度：**85% - 90%**
- 业务情景总体覆盖度：**80% - 88%**
- 前后端能力对齐度：
  - 高级治理视角：**暂不作为本阶段前端目标继续推进**
  - 普通用户视角：**50% - 65%**
- 普通用户可见能力完成度：**当前边界已经明确，但“长期记忆 Wiki 的完整增删改查”仍未补齐，是普通前端最大缺漏**

一句话判断：

**后端治理已经明显跑在前面，而普通前端当前只应承接两类能力：查看观察日志，以及长期记忆 Wiki 的增删改查；其中后者仍未真正补齐。**

## 3. 记忆层后端完成度评估

## 3.1 已经基本完成的能力

当前后端已经具备以下正式能力：

- Memory Wiki 页面增删改查
- 页面状态、重要性、别名管理
- 页面版本记录、版本 diff、回滚
- 页面归档与恢复
- 页面合并
- 页面关联关系维护
- Topic Index 建立、别名维护、页面绑定、主题合并、解绑
- Governance 审核请求池
- 审计日志读取
- 巡检能力
  - 断链巡检
  - 孤儿页巡检
- 页面来源追溯
- 主题来源追溯

从接口层看，`routes.js` 已经不是一个“只会读写单页”的薄路由，而是一个比较完整的治理型 API 集合。  
从工具层看，`tools.js` 也已经把 wiki、topic、governance 主要动作注册为模型可调用工具。

这说明后端不只是“能存”，而是已经进入“能治理”的状态。

## 3.2 后端主链成熟度判断

当前后端主链的几个关键判断如下：

1. 长期记忆主源已经从旧 `memory_entries` 迁移到 Memory Wiki。
2. Identity 结构化页面已经成为正式的一等实体，而不是临时字段拼接。
3. 观察日志、聊天记录、长期记忆之间已经开始形成“事实层 - 历史层 - 沉淀层”的分层。
4. 页面治理、版本、审计、巡检已经补齐，后端具备长期运行基础。

因此，当前后端已经不是原型期记忆系统，而是**第一版正式记忆底座**。

## 4. 各业务情景覆盖度评估

## 4.1 用户身份与关系记忆

覆盖度评估：**90%**

当前已经覆盖：

- 用户名字
- 偏好称呼
- 用户与 Cornie 的关系
- 用户阶段画像
- 当前关注点
- 压力来源
- 沟通偏好
- 重要人物
- 偏好
- trait

这部分是目前最成熟的一块，尤其适合承接“你是谁、我是谁、我们是什么关系、我在意什么人和事”这类稳定长期记忆。

## 4.2 重要人物长期记忆

覆盖度评估：**85%**

当前已经覆盖：

- 人物页建模
- 人物页来源回链
- 与用户关系描述
- 共同经历沉淀
- 情感权重与时间线摘要
- 通过 Topic Index 形成主题层联动

还未完全产品化的部分：

- 人物关系网的可视化
- 更精细的人物合并/拆分辅助
- 普通用户的人物治理界面

## 4.3 偏好与 trait 记忆

覆盖度评估：**80% - 85%**

当前已经覆盖：

- 偏好页、trait 页的结构化承载
- 条件召回
- 谨慎写入
- 证据积累

不足点：

- 长期噪音治理策略还需继续优化
- 普通用户对这两类页面的理解与修改入口仍不足

## 4.4 观察日志

覆盖度评估：**88% - 92%**

当前已经覆盖：

- 按天归档
- 今日视图
- 历史按日期/类型/关键词搜索
- 新增、编辑、删除
- Prompt 侧“今日轻注入 + 历史按需召回”的边界

这块后端和前端都已经能工作，但产品表达仍需继续收紧，否则用户容易把观察日志误解成“全部聊天流水账”。

## 4.5 聊天记录与历史回查

覆盖度评估：**80% - 85%**

当前已经基本成立：

- 聊天记录已转入 SQLite 主链
- 支持按日归档
- 支持长会话边界控制
- 支持按需回查，不再把大量历史整包塞进 prompt

当前主要缺口不在后端，而在前端历史查看体验、索引入口与联动呈现。

## 4.6 Topic Index 与主题回查

覆盖度评估：**82% - 88%**

当前已经覆盖：

- 关键词主题索引
- 别名维护
- 页面关联
- 主题合并
- 主题来源追踪

这块已经具备你后面说的“龙虾 -> 日期索引 -> 快速定位历史聊天和长期记忆”的基础雏形。  
严格说，现在已经不是没有能力，而是还缺更完整的前端呈现与运营规则。

## 4.7 页面治理、审计、回滚

覆盖度评估：**85% - 90%**

当前已经覆盖：

- 审核请求池
- 巡检
- 页面版本
- diff
- 回滚
- 合并
- 删除
- 审计事件读取

这一块已经很像“内部运营后台能力”，后端成熟度较高，但前端只落了核心工作台，没有把所有治理入口都做成完整产品。

## 5. 前后端对齐度评估

## 5.1 普通用户视角

对齐度评估：**50% - 65%**

你当前重新明确后的普通用户权限边界只有两类：

1. 查看观察日志
2. 长期记忆 Wiki 的增删改查

按这个边界重新评估，当前对齐情况如下。

已经基本对齐的部分：

- 普通用户已经有观察与记忆首页入口
- 已经有观察日志列表页
- 已经有观察日志详情页
- 已支持观察日志查看、检索、编辑、删除

尚未真正对齐的部分：

- 长期记忆 Wiki 虽然已有列表和详情页雏形，但还不是“完整增删改查”
- 当前普通用户前端没有正式的“新建长期记忆页”入口
- 当前普通用户前端没有正式的“删除长期记忆页”入口
- 当前记忆详情页仍偏简单文本编辑页，还没有形成稳定的 Wiki 页面操作体验
- 当前普通用户前端对 Identity / Person / Preference / Trait 的页面类型差异没有清晰表达

结论：

**按你现在重新收紧后的边界来看，普通用户前端并不是做得太多，而是还没把“长期记忆 Wiki 增删改查”这一件该做的事完整做完。**

## 5.2 高级治理视角

高级入口、治理工作台、版本、回滚、索引、审计、巡检等能力，当前继续保留在后端与已有高级前端雏形中即可。  
但根据你这次的要求，这一块**暂不继续作为前端治理重点推进**，因此本报告不再把它列为近期前端对齐目标。

这意味着：

- 高级入口可以先停止继续治理
- 不再要求普通用户前端承接高级治理能力
- Topic Index、治理请求池、审计、巡检、版本等能力，暂时继续留在普通用户边界之外

## 6. 普通用户当前可见内容与可操作范围

这是当前最需要说清楚的一部分。

## 6.1 普通用户可见入口

当前普通用户可见的记忆相关页面主要有：

1. `观察与记忆首页`
2. `我的记忆` 列表页
3. `记忆详情` 页
4. `观察日志` 列表页
5. `观察日志详情` 页

## 6.2 普通用户当前可见的数据

普通用户当前能看到的数据包括：

- 最近沉淀出的少量 identity 类长期记忆页
- 记忆页标题
- 记忆页摘要/正文
- 观察日志的日期、类型、标题、正文
- 历史观察日志按日期、类型、关键词检索结果

## 6.3 普通用户当前能执行的操作

普通用户当前应该具备、且正在实现中的操作边界应当是：

- 查看观察日志
- 查看长期记忆 Wiki 页面
- 新建长期记忆 Wiki 页面
- 编辑长期记忆 Wiki 页面
- 删除长期记忆 Wiki 页面

而当前实际已经具备的普通用户操作是：

- 浏览记忆首页
- 查看最近记忆
- 查看全部记忆列表
- 打开单个记忆页
- 对单个记忆页做基础编辑
- 查看观察日志今日记录
- 搜索历史观察日志
- 新增观察日志
- 编辑观察日志
- 删除观察日志

因此，当前普通前端的核心缺口非常明确：

- 长期记忆 Wiki 的“新建”没有真正补齐
- 长期记忆 Wiki 的“删除”没有真正补齐
- 长期记忆 Wiki 的“改”还停留在很基础的文本编辑状态
- 长期记忆 Wiki 的“查”虽然已有入口，但呈现仍过于简化

## 6.4 普通用户当前看不到的部分

普通用户当前默认不应看到：

- 完整 Memory Wiki 工作台
- Topic Index
- 页面来源追溯
- 页面版本历史
- diff
- 页面回滚
- 页面合并
- 孤儿页 / 断链巡检
- 治理请求池
- 审计事件

这符合你当前重新明确的边界：**普通用户只保留观察日志查看能力，以及长期记忆 Wiki 的增删改查能力；所有高级治理能力、复杂抽象术语与索引体系都不向普通用户暴露。**

## 7. 当前主要问题与风险

## 7.1 普通用户前端的核心缺口已经重新明确

这是当前最明显的结构性现状。

问题不在于后端没做，而在于普通用户前端当前最关键的一件事还没做完：

- 长期记忆 Wiki 的完整增删改查还未产品化收口
- 观察日志这条线相对已经更完整
- 因此前端真正的最大缺漏不是“还要不要继续开放更多高级能力”，而是“该开放给普通用户的长期记忆 Wiki 能力还没补齐”

例如：

- `MemoryPageDetail.vue` 还是很基础的标题/内容编辑页
- 普通用户视角下，看不到这页记忆为什么存在、来自哪里、和谁有关、何时更新、是否经过确认

## 7.2 普通记忆页与正式 Wiki 模型之间仍有“表达落差”

普通用户页虽然已经读取 Memory Wiki 数据，但其展示模型仍然偏“简单笔记页”，没有把 Identity / Person / Preference / Trait 的结构差异讲清楚。

这会导致两个结果：

- 后端很强，但用户感知不出来
- 用户容易误把长期记忆当成普通文本笔记，而不是结构化关系记忆

## 7.3 高级入口当前应冻结，而不是继续前端补齐

高级设置页当前虽然还有未完成面板，但按你刚刚重新确认的边界，这一块不再属于当前普通前端目标。  
因此这里不再定义为“必须立即补齐的问题”，而是应当：

- 保留现状
- 停止继续扩展高级入口
- 把前端资源先集中到普通用户的长期记忆 Wiki 增删改查

## 7.4 数据容错性仍需继续补强

这次“高级入口新建页失败”已经说明了一个现实问题：

- 一旦某页 frontmatter 被污染，列表读取就会受影响
- 虽然现在前端错误提示已经更友好，但后端对坏页容错仍可继续增强

建议后续继续补：

- `listSummaries()` 的坏页降级容错
- 坏页隔离与修复提示
- 数据修复工具

## 8. 下一步建议

## 8.1 第一优先级：补齐普通用户前端的长期记忆 Wiki 增删改查

建议优先做：

- 普通用户可创建长期记忆 Wiki 页面
- 普通用户可删除长期记忆 Wiki 页面
- 普通用户可稳定编辑长期记忆 Wiki 页面
- 普通用户可清楚查看长期记忆 Wiki 页面列表与详情
- 页面展示中隐藏高级术语，改为平实可理解的表达

这是当前最核心、最直接影响产品体验的前端缺口。

## 8.2 第二优先级：补齐普通用户记忆页的表达能力

建议继续做：

- 让普通记忆页显示“这条记忆属于哪一类”
- 用自然语言说明这条记忆在记什么
- 对 identity_profile / identity_person / identity_preference / identity_trait 使用不同展示模板

这一步的目标不是治理，而是让普通用户真正看得懂长期记忆 Wiki。

## 8.3 第三优先级：加强记忆层数据容错与修复

建议补齐：

- 坏页容错读取
- 损坏页隔离
- 前端修复提示
- 一键修复/导出修复建议

## 8.4 第四优先级：高级入口暂缓，不进入本轮普通前端目标

高级入口、Topic Index、版本、回滚、巡检、审计等能力，当前不继续向普通用户前端推进。  
这部分后端能力继续保留，但前端实现优先级下调。

---

## 9. 最终结论

当前 Cornie 的记忆层后端大治理，**已经完成了第一阶段最难的部分**：

- 主链收口
- 长期记忆主源统一
- Identity 正式建模
- Topic / Governance / Audit / Version / Rollback / Merge 等治理能力成立

但如果从产品完成度来讲，还不能说“记忆系统已经彻底完工”。

更准确地说，当前状态是：

**后端记忆底座已经基本成型；普通用户前端的权限边界也已经明确；当前最大的缺漏，不是继续扩展高级治理，而是把普通用户的长期记忆 Wiki 增删改查真正补齐。**

因此，本阶段最合理的判断不是“继续大改后端”，而是：

**以后端为基础，优先补齐普通用户长期记忆 Wiki 前端；高级入口前端先冻结，暂不继续治理。**
