# R-01 聊天去重-后端落库时序修正（Persist After Distillation）

## 背景

Cornie-023 §3.1 问题一主因：`orchestrator.runTurn` 先把 cornie 消息 `saveMessage` 落库（`orchestrator.js:373-378`），随后才执行**慢速记忆提炼 LLM 调用**（`orchestrator.js:398-410` → `memoryDistillation.js:230`，maxTokens 700，耗时数秒），再 return；SSE `done` 在 return 后才发出（`conversation/routes.js`）。这数秒窗口内，前端 3s 轮询会从 DB 拉到"未来"的消息，与流式占位重复（前端双气泡根因之一）。

## 目标

1. 将 cornie 消息的 `saveMessage` 从"记忆提炼之前"挪到"记忆提炼完成之后、return 之前"，使 DB 可见与 SSE `done` 几乎同刻。
2. 行为等价：消息内容、id 生成、返回结构均不变，仅落库时机后移。

## 范围

- `electron/backend/agent/orchestrator.js`（`runTurn` 内 saveMessage 位置调整）
- `tests/orchestrator/conversation-orchestrator.test.mjs`（新增时序断言：落库在 return 前且不早于记忆提炼）

## 设计要求

### 1. 时序调整

- 当前顺序：工具轮/回复生成 → `saveMessage(cornieMessage)` → createPending（确认）→ `runMemoryDistillation` → return。
- 目标顺序：工具轮/回复生成 → createPending（确认）→ `runMemoryDistillation` → **`saveMessage(cornieMessage)`** → return。
- 注意：`createPending` 依赖 `cornieMessage.id`（确认流的 conversationMessageId）——**`saveMessage` 必须早于 createPending**，因此正确顺序是：生成 finalReply → saveMessage（拿到 id）→ createPending → runMemoryDistillation → return。即仅把 saveMessage 相对记忆提炼**前移不动**，把记忆提炼挪到 saveMessage 之后？——不，目标是把 saveMessage 挪到记忆提炼**之后**。但 createPending 需要 cornieMessage.id……
  - 解决：`saveMessage` 与 `createPending` 需要的 id 可以分离——先 `saveMessage` 拿 id 但把"对前端可见"理解为 DB 中已存在。轮询窗口的关键是**消息在 DB 中可被 loadConversation 拉到**。若 saveMessage 挪到提炼后，createPending 也要挪？createPending 只是内存/治理队列写入（confirm service 的 createPending 写 governance？）——看实现：createPending 写入 pending confirmations（DB？）。若 createPending 也写 DB 且依赖 cornieMessage.id，则 id 在 saveMessage 之后才有。
  - 折中方案：**保持 saveMessage 位置不变（先落库拿 id），但让"轮询窗口"消失**——实际上轮询窗口的根源是 saveMessage 与 SSE done 之间隔着记忆提炼。若 saveMessage 必须在 createPending 前，而 createPending 必须在 return 前，则 saveMessage 不能简单后移。
  - **更优方案**：把**记忆提炼**挪到 saveMessage **之前**（记忆提炼不依赖 cornieMessage 的 DB 落库，只依赖 finalReply 文本与 history——检查 runMemoryDistillation 入参：store/baseDir/date/userMessage/cornieMessage(messageId)/history。它用 cornieMessage 的 content 与 messageId？若依赖 messageId（DB id），则也需先落库）。
  - **最终方案（若 runMemoryDistillation 不依赖 DB 中的 cornie 行）**：`saveMessage` 保持在生成回复后立即执行（拿 id 供 createPending），但**把记忆提炼挪到 saveMessage 之前**——提炼用 `cornieMessage.content`（内存值）+ 不查 DB cornie 行 → 可先提炼后落库。验证 runMemoryDistillation 是否查 DB（`getMessagesByDate` 或 messageId 查询）。
- 实现时先读 `runMemoryDistillation` 与 `runTurn` 现状，确认依赖后选择：
  - 方案 A：记忆提炼挪到 saveMessage 前（若提炼不依赖落库行）；
  - 方案 B：saveMessage 后移 + createPending 改用内存 id 占位（若 createPending 不写 DB）。
- 无论哪种，验收锚点一致：**前端轮询在流式完成前永远拉不到本轮 cornie 消息**。

## 验收标准

1. 新增/更新 orchestrator 测试：mock 记忆提炼慢响应（受控 Promise），断言在 return 前、提炼完成后消息才可被 `getMessagesByDate` 查到（或 saveMessage 调用发生在提炼之后——按最终实现断言）。
2. 现有 conversation-orchestrator 测试（回复/追问/确认/记忆提炼路径）全部通过，返回结构不变。
3. `npm run test:full` 全绿。
4. 提交为 `fix(backend): ...` 单提交，符合 commit 规范。
