## 2. 文档背景

当前 Cornie 的前端存在一个根本问题：

`它过于像系统能力展示面，而不像一个面向普通人的陪伴型产品。`

具体表现为：

1. 布局密集，信息堆叠。
2. 主路径不突出，高频和低频操作混在一起。
3. 专业治理、来源追溯、内部结构等信息过多进入普通用户视野。
4. 前端承接了太多“系统内部世界”，而不是只承接“普通人真正关心的内容”。

Cornie 的目标用户不是程序员，不是知识库管理员，也不是工作流设计者，而是：

`希望被陪伴、被理解、被安慰，并顺手管理自己生活记录的普通人。`

因此，本设计文档的目标不是继续扩展前端暴露面，而是进一步压缩前端展示信息，重新定义：

1. 普通用户应该看到什么。
2. 普通用户不应该被迫看到什么。
3. 哪些页面应该成为主入口。
4. 哪些能力应该后置，甚至不进入普通用户前端。

## 3. 设计目标

| 编号 | 目标 | 说明 |
| --- | --- | --- |
| G1 | 重新定义前端能力边界 | 前端只保留普通人真正需要的内容 |
| G2 | 进一步压缩前端信息量 | 默认隐藏专业治理、来源链路、内部结构 |
| G3 | 重建前端主路径 | 让聊天、日记、生活管理成为绝对主线 |
| G4 | 保留必要确认，不扩大复杂治理暴露 | 普通人拥有决定权，但不承担系统复杂度 |
| G5 | 给前端重构提供统一原则 | 后续 UI / UX 重做必须遵循这份边界设计 |

## 4. 核心结论

本次设计的总原则只有一句话：

`Cornie 的前端应当是普通人与铃湾相处、记录、回看、被安慰、轻松管理生活的界面，而不是把后端和模型内部世界原样翻给人看的面板。`

进一步展开为五条：

1. 模型能做，不等于人类必须看到全过程。
2. 后端有能力，不等于前端必须给入口。
3. 普通人只需要结果、记录、少量确认和少量状态反馈。
4. 复杂治理、来源结构、内部关系图谱必须后置。
5. 前端首先服务于陪伴感和轻松感，而不是系统完备感。

## 5. 用户定位与前端定位

## 5.1 用户定位

Cornie 的目标用户是：

1. 普通人
2. 希望获得情感慰藉的人
3. 希望轻松记录生活、心情、收支、安排的人
4. 不希望被复杂系统细节打扰的人

## 5.2 前端定位

Cornie 前端应被定义为：

1. 普通人与铃湾相处的主界面
2. 日常记录、回看、安排、确认的界面
3. 带有陪伴感的轻量生活工作台

Cornie 前端不应被定义为：

1. 运维后台
2. 治理控制台
3. 内部结构浏览器
4. 工具调用过程监控页
5. 长期记忆基础设施操作台

## 6. 前端总原则

## 6.1 默认只展示三类内容

前端默认只展示：

1. 用户自己的内容
2. 铃湾的最终回应或最终结果
3. 少量确实需要用户确认的事项

## 6.2 默认隐藏的内容

前端默认隐藏：

1. 原始工具调用参数
2. 原始 JSON
3. 模型中间决策过程
4. 内部策略判断细节
5. 来源关系网
6. Topic / Index / Wiki 底层结构
7. 版本系统技术细节
8. 巡检、审计、压缩、回滚等治理细节

## 6.3 陪伴优先原则

对于普通用户而言，Cornie 首页最重要的感受应该是：

1. 好接近
2. 好理解
3. 不吓人
4. 不像后台
5. 有陪伴感

## 6.4 确认最小化原则

确认机制要存在，但必须克制。

只在以下场景才适合打扰用户：

1. 需要新增类目
2. 会删除重要内容
3. 会覆盖已有重要内容
4. 会执行用户可能后悔的高风险动作

不应为了“系统很严谨”而把大量普通操作都抬成确认项。

## 7. 普通用户前端能力边界

## 7.1 一级导航建议

一级导航建议只保留 7 个：

1. 聊天
2. 日记
3. 收支
4. 待办
5. 日程
6. 观察与记忆
7. 设置

说明：

1. `聊天` 必须是绝对主入口。
2. `观察与记忆` 应作为对普通人友好的合并概念，不直接暴露 `Memory Wiki`。
3. 不建议把“确认中心”“治理中心”“审计中心”做成一级导航。

## 7.2 二级入口建议

二级入口只保留普通用户能理解的内容：

1. 聊天记录回看
2. Cornie 日记回看
3. 类目管理
4. 观察记录回看
5. 记忆页列表
6. 待确认事项

## 7.3 不进入普通用户主路径的能力

以下能力不建议进入普通用户前端主路径：

1. Memory Wiki 批量治理
2. 页面版本差异对比
3. 页面回滚
4. 页面合并审核
5. Topic 热度治理
6. 巡检结果浏览
7. 审计查看
8. 大规模导入导出修复页

这些能力如果确实要保留，也应进入：

1. 高级设置
2. 开发模式
3. 高级用户模式

## 8. 人类可见数据边界

## 8.1 应默认可见的数据

前端应默认向普通用户展示：

1. 自己写的内容
2. 自己保存的内容
3. 铃湾生成的最终文字
4. 铃湾帮忙完成后的最终结果
5. 少量与当前动作强相关的状态说明
6. 少量待确认事项

## 8.2 不应默认可见的数据

以下内容不应默认展示：

1. 来源摘要
2. 关联信息网络
3. 回流逻辑说明
4. 长对话跳读技术信息
5. AI 建议过程
6. 记忆命中过程
7. 分类映射过程
8. 去重过程
9. 内部状态对象

## 8.3 仅在需要时可见的数据

仅在必要时可查看，但不应常驻：

1. 失败原因的用户化解释
2. 极少量来源说明
3. 高风险操作的简短依据

## 9. 各模块前端边界定义

## 9.1 聊天模块

### 普通用户应看到的内容

1. 对话本身
2. 铃湾的最终回复
3. 少量必要确认
4. 少量失败恢复建议

### 普通用户不应默认看到的内容

1. 每一步工具过程卡
2. 记忆引用过程
3. 工具调用流水
4. 中间失败重试过程
5. 工程化透明面板

### 产品原则

聊天页必须首先是“陪伴”和“交流”，不是“系统在背后怎么运作”。

## 9.2 聊天记录模块

### 普通用户应看到的内容

1. 按天回看
2. 日期标题
3. 对话内容
4. 简单的空状态和加载状态

### 普通用户不应默认看到的内容

1. 阅读辅助细枝末节
2. 回流提示
3. 同日关联线索
4. 内部跳转状态
5. 历史沉淀链路

### 产品原则

聊天记录页应该简单、安静、好回看。

## 9.3 收支模块

### 普通用户应看到的内容

1. 收支记录
2. 记一笔
3. 类目管理
4. 基础统计
5. 类目新增确认

### 普通用户不应默认看到的内容

1. AI 建议记账过程
2. 类目映射过程
3. 内部 ledger 结构

### 产品原则

收支页重点是“记得快、看得懂、改得了”。

## 9.4 待办与日程模块

### 普通用户应看到的内容

1. 列表
2. 新增
3. 编辑
4. 完成 / 取消 / 删除
5. 类目管理
6. 类目新增确认

### 普通用户不应默认看到的内容

1. AI 整理过程
2. 排序与重算过程
3. 工具执行过程

### 产品原则

待办和日程页重点是“安排生活”，不是“看系统怎么安排”。

## 9.5 观察模块

### 普通用户应看到的内容

1. 按日查看
2. 新增
3. 编辑
4. 删除
5. 简短边界说明

### 普通用户不应默认看到的内容

1. 与记忆、聊天、Topic 的复杂关系
2. 被用于素材的提示
3. 去重与调整过程
4. 来源归一化过程

### 产品原则

观察页应该像“生活片段记录本”，不是“事实素材治理台”。

## 9.6 Cornie 日记模块

### 普通用户应看到的内容

1. 当日日记
2. 重新生成入口
3. 往年今日回看

### 普通用户不应默认看到的内容

1. 来源透明摘要
2. 生成依据解释
3. 多来源综合关系

### 产品原则

Cornie 日记应该保留情感和文学感，不要被技术解释污染。

## 9.7 记忆模块

### 普通用户应看到的内容

1. 记忆页列表
2. 记忆正文
3. 基础编辑
4. 少量重要记忆的查看与补充

### 普通用户不应默认看到的内容

1. 关键来源
2. 关联页面网络
3. Topic 连接
4. 主动治理入口
5. 历史版本
6. 巡检候选
7. 审核队列

### 产品原则

记忆模块对普通人应当像“回忆和偏好笔记页”，而不是“知识治理系统”。

## 10. 待确认事项边界

## 10.1 普通用户前端中可以保留的确认

建议只保留：

1. 新建类目确认
2. 高风险删除确认
3. 少量重要内容覆盖确认
4. 高风险记忆写入确认

## 10.2 不建议保留在普通用户前端中的确认

以下确认不建议进入普通用户前端：

1. 页面合并确认
2. 页面回滚确认
3. 批量治理确认
4. 巡检候选处理

### 原因

1. 普通用户不理解这些概念。
2. 这类页面会显著破坏陪伴型产品气质。
3. 这些能力更适合高级模式。

## 10.3 待确认事项的产品角色

“待确认事项”应是：

1. 少量打扰用户但必须确认的收口点
2. 简短、易懂、低压力的决定页

而不是：

1. 治理中心
2. 系统消息堆放区
3. 低频复杂任务总入口

## 11. 高级模式边界

如果未来确实要保留复杂治理能力，建议统一放入 `设置 -> 高级设置 -> 高级模式`。

高级模式可包含：

1. 版本历史
2. 页面回滚
3. 治理审核池
4. 巡检结果
5. 审计查看

但默认不进入普通用户视野。

## 13. 与“模型工具集 = 人类接口集”的关系修正

这句话在能力层成立，但在普通用户前端呈现层绝不能机械理解为：

`模型能调用的所有东西，都应该让普通人看到和操作。`

正确理解应是：

1. 人类最终应拥有决定权
2. 人类在需要时应有等价能力
3. 但普通用户前端不必暴露全部中间操作
4. 一部分低频复杂能力可以后置到高级模式

## 14. 对当前前端重做的直接指导

## 14.1 这次重做不是纯视觉重做

必须同时重做：

1. 信息架构
2. 页面层级
3. 导航优先级
4. 数据暴露边界

## 14.2 这次重做要先删，再做

建议先做以下动作：

1. 删除普通用户看不懂的治理入口
2. 删除不必要的来源、关联、透明提示
3. 删除后台式的结构暴露
4. 删除“系统在背后做了什么”的过量解释

## 14.3 当前最应优先重做的模块

优先顺序建议为：

1. 聊天首页与陪伴感
2. 日记首页
3. 观察与记忆模块
4. 聊天记录回看页
5. 收支 / 待办 / 日程统一收口
6. App 壳层与全局导航

## 15. 最终结论

Cornie 当前前端最大的问题不是“缺几个页面”，而是“把太多不该给普通人看的东西给了普通人看”。

本次设计明确要求：

1. 前端从能力堆叠转为陪伴与生活记录导向。
2. 前端从后台控制台转为普通人可亲近的界面。
3. 前端默认展示记录、结果、少量确认和安慰性反馈。
4. 前端默认隐藏协议、流水、治理、结构关系。
5. 人类保留最终决定权，但不承担系统内部复杂度。

一句话总结：

`Cornie 的前端应当首先像一个温和陪伴普通人的生活界面，其次才是一个拥有复杂能力的系统。`
