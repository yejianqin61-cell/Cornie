# Cornie-0630-Identity记忆实体模型与页面结构设计

## 1. 文档定位

本文件是 [Cornie-0630-记忆层改进治理总纲-第一版.md](/abs/path/C:/Users/USER/Desktop/Cornie/Cornie/doc/design/Cornie-0630-记忆层改进治理总纲-第一版.md) 的下游设计文档。  
其目标是将“长期记忆 Wiki 先聚焦 Identity”的原则继续落地为可开发的实体模型与页面结构。

本文件重点解决：

1. Identity 到底由哪些实体组成。
2. 每种实体该存哪些字段。
3. 人物页应该如何组织。
4. 哪些内容属于高优先级稳定注入。
5. 后续页面层与 Topic Index 应如何联动。

---

## 2. 设计目标

Identity 记忆的目标不是“把所有关于用户的话都记下来”，而是建立 Cornie 对用户的**稳定身份认知结构**。

本设计要求长期记忆至少解决以下体验问题：

1. 用户名字能跨天稳定记住。
2. 用户与 Cornie 的关系能跨天稳定记住。
3. 用户的关键身份特征能逐步沉淀。
4. 用户反复提及的重要人物能形成独立人物页。
5. 人物相关的关系、性格、共同经历能够逐步补全，而不是散落在聊天流水里。

---

## 3. Identity 的实体划分

本期 Identity 记忆建议拆成 4 类核心实体：

1. `identity_profile`
2. `identity_preference`
3. `identity_trait`
4. `identity_person`

其中：

- `identity_profile`：用户主身份页
- `identity_preference`：用户稳定偏好页
- `identity_trait`：用户性格 / 状态侧写页
- `identity_person`：重要人物页

---

## 4. 用户主身份页：`identity_profile`

这是 Cornie 对“用户是谁”的主页面，也是最高优先级 Identity 页面。

### 4.1 页面职责

负责承载：

- 用户名字
- 用户偏好称呼
- 用户与 Cornie 的关系
- 用户核心身份描述
- 当前阶段的总侧写摘要

### 4.2 推荐字段

除通用 wiki 元数据外，正文结构建议至少包含：

- `user_name`
- `preferred_name`
- `cornie_relationship`
- `identity_summary`
- `life_stage_summary`
- `current_focus`
- `stressors`
- `communication_preference`

### 4.3 正文结构建议

建议页面正文采用固定分段：

1. 基本身份
2. 与 Cornie 的关系
3. 当前阶段画像
4. 长期关注点
5. 沟通与陪伴偏好

### 4.4 示例结构

```md
## 基本身份
- 用户名字：叶健钦
- 偏好称呼：爸爸

## 与 Cornie 的关系
- 用户是 Cornie 的创造者
- 用户是 Cornie 的爸爸

## 当前阶段画像
- 当前处于学业、项目、实习与就业压力交织阶段

## 长期关注点
- 项目推进
- 考试
- 实习与找工作

## 沟通与陪伴偏好
- 需要温柔、克制、能记住上下文的陪伴感
```

### 4.5 注入优先级

`identity_profile` 必须属于**最高优先级跨天稳定注入页**。

每次对话时，至少要保证该页摘要可被模型稳定拿到。

---

## 5. 用户偏好页：`identity_preference`

这类页面用于记录用户长期稳定偏好。

### 5.1 页面职责

负责承载：

- 喜欢什么
- 不喜欢什么
- 风格偏好
- 互动方式偏好
- 生活习惯型偏好

### 5.2 为什么单独拆页

偏好经常比身份更细碎，也更容易变动。  
如果全部堆在用户主身份页里，会让主身份页越来越臃肿。

因此更合适的做法是：

- 用户主身份页保留“高层摘要”
- 具体偏好拆成独立页或独立分组页

### 5.3 推荐字段

- `preference_type`
- `stance`
- `preference_summary`
- `stability_level`
- `evidence_count`
- `last_confirmed_at`

其中：

- `preference_type`：饮食 / 交流 / 风格 / 作息 / 情感表达等
- `stance`：喜欢 / 不喜欢 / 中性偏好
- `stability_level`：低 / 中 / 高

### 5.4 正文结构建议

```md
## 偏好结论
- 不喜欢太甜的咖啡

## 场景说明
- 在饮品选择中更偏好不过甜、清爽一些的口感

## 证据来源
- 多次在聊天中提到饮品口感偏好
```

### 5.5 注入优先级

这类页面不一定每次都全注入。  
应根据：

- 当前话题相关性
- 偏好稳定性
- 最近是否再次被提及

按需注入。

## 6. 用户性格 / 侧写页：`identity_trait`

这类页面用于沉淀用户长期体现出的性格特征、情绪习惯和表达方式。

### 6.1 页面职责

负责记录：

- 性格倾向
- 情绪反应模式
- 沟通风格
- 面对压力时的表现
- 人物身份，职业，工作

### 6.2 使用边界

这一类最容易引发误判，因此必须谨慎：

- 不能只凭一次聊天就生成强性格判断
- 不能把短期状态误写成长期特征
- 应尽量写成“倾向性描述”，而不是武断标签

### 6.3 推荐字段

- `trait_type`
- `confidence_level`
- `stability_level`
- `trait_summary`
- `evidence_count`
- `owner_confirmed`

### 6.4 正文结构建议

```md
## 特征倾向
- 在高压阶段容易疲惫，但仍会把回忆和责任转化为前进动力

## 语气与表达方式
- 表达情绪时常带自我消化和克制

## 使用注意
- 这是阶段性侧写，不应过度绝对化
```

### 6.5 注入优先级

`identity_trait` 不应高频大段注入。  
更适合：

- 压缩为 1-2 条高价值侧写摘要
- 在情绪、关系、长期压力相关话题下按需注入

## 7. 重要人物页：`identity_person`

这是 Identity 设计里最重要的实体之一。

### 7.1 页面职责

每个重要人物都应形成独立页面，而不是只在主身份页里记一句名字。

适用对象包括：

- 初恋
- 家人
- 朋友
- 同学
- 导师
- 同事
- 其他反复提及的重要人物

### 7.2 页面核心结构

每个重要人物页至少应包含以下 4 个一级结构：

1. 关系
2. 身份
3. 性格
4. 和用户的共同经历

### 7.3 推荐字段

除通用 wiki 元数据外，建议增加：

- `person_name`
- `relationship_to_user`
- `role_summary`
- `personality_summary`
- `shared_experience_summary`
- `emotional_weight`
- `timeline_summary`
- `first_known_period`
- `last_mentioned_at`

### 7.4 正文结构建议

```md
## 关系
- 用户的初恋

## 身份
- 在用户人生中具有高情感权重的重要人物

## 性格
- 温柔
- 害羞
- 内向

## 和用户的共同经历
- 2021 年冬天相恋
- 2022 年春天疏远
- 2022 年夏天决裂

## 对用户的意义
- 用户认为这段关系至今仍是重要回忆与前进动力来源
```

### 7.5 注入优先级

重要人物页应作为**高优先级条件注入页**。

策略上：

- 平时不必把所有人物页都注入
- 但当用户提到相关名字、关系词、共同经历词时，应优先召回
- 对极高权重人物，可在日常摘要里保留轻量痕迹

## 8. 页面结构与 Topic Index 的联动

Identity 实体页和 Topic Index 不应彼此替代，而应协同工作。

### 8.1 Page 是正文，Topic 是索引

- Page：存放正式、结构化、可编辑的长期认知正文
- Topic Index：负责关键词、日期、来源、热度与快速跳转

### 8.2 推荐联动方式

#### 用户主身份页

- 常驻一个主索引项，例如用户名字、昵称、称呼

#### 偏好页

- 对应若干偏好主题词

#### 性格页

- 通常不需要过多主题化
- 但可在重要关键词上留轻索引

#### 人物页

- 每个人物都应有对应 Topic Index 项
- 包含：
  - 人物名
  - 别名
  - 相关日期
  - 聊天引用
  - 观察日志引用
  - 记忆页引用

### 8.3 钟奕菲类场景示例

如果用户提到“钟奕菲”：

- Topic Index 先命中“钟奕菲”
- 找到相关日期、聊天记录、观察日志、人物页
- 再由模型读取人物页摘要
- 必要时再补查具体聊天和观察日志

这能避免每次都从全库遍历。

## 9. Identity 页面之间的关系结构

Identity 各页面之间应允许建立关系链接。

### 9.1 推荐关系

- `identity_profile` -> `identity_person`
  表示该人物属于用户重要关系圈

- `identity_profile` -> `identity_preference`
  表示这条偏好属于用户整体身份

- `identity_profile` -> `identity_trait`
  表示这条侧写属于用户整体画像

- `identity_person` -> `identity_trait`
  如果某人物页中沉淀出“用户在此关系中的状态特征”，可做弱关联

### 9.2 关系使用原则

- 页面关系应服务于理解，不应过度复杂
- 先保证“用户主身份页 -> 人物页”这条关系清晰
- 复杂图谱关系可放后续阶段

## 10. 写入策略建议

### 10.1 不同实体的写入门槛不同

#### `identity_profile`

写入门槛最高，但一旦确认后优先级最高。  
适用于：

- 用户明确说出自己的名字
- 用户明确说明与 Cornie 的关系
- 用户明确给出自我身份设定

#### `identity_preference`

适用于：

- 明显偏好表达
- 多次重复表达
- 对未来互动有持续影响

#### `identity_trait`

必须更谨慎，建议：

- 需要反复证据
- 或用户自己明确表达
- 或人工确认后再沉淀

#### `identity_person`

适用于：

- 用户反复提及某个人
- 情绪浓度高
- 对用户人生叙事有明显影响

### 10.2 高风险字段建议确认

以下内容建议进入确认流或至少进入治理候选：

- 用户名字更新
- 用户与 Cornie 的关系定义
- 重要人物关系定义
- 人物性格结论
- 用户性格结论

## 11. 读取与注入策略建议

### 11.1 默认稳定注入

每次对话建议默认稳定注入：

- 用户主身份页摘要
- 用户与 Cornie 的关系摘要
- 用户名字与称呼信息

### 11.2 条件注入

按话题命中再注入：

- 人物页
- 偏好页
- 性格侧写页

### 11.3 不建议的做法

不建议：

- 每次把所有 Identity 页面都塞进 prompt
- 每次都把所有人物页全文注入
- 把长期记忆当大文档整块注入

正确做法应是：

- 主身份稳定注入
- 相关实体按需召回
- 细节通过工具补查

## 12. 当前 prompt 构建边界说明

这一节用于明确：当前对话主链在构建 prompt 时，到底会把哪些信息带给模型。

### 12.0 一句话结论

会。

当前对话主链不是“只把摘要塞给模型”，而是：

1. `system prompt` 中带结构化上下文摘要
2. `messages` 中继续带入当天最近的真实聊天上下文

也就是说，模型看到的不是纯摘要模式，而是“摘要 + 真实近轮聊天”的混合上下文。

### 12.1 会带入的上下文

当前对话 prompt 默认包含以下几块：

1. 当天最近对话摘要
2. 当前全部类目摘要
3. 未完成待办摘要
4. 近期日程摘要
5. 当天观察日志摘要
6. 长期记忆 Wiki 摘要
7. 主题索引摘要
8. 命中的历史聊天日期摘要
9. 命中的观察补查摘要
10. 当前可调用工具摘要

其中最关键的是两层：

- 一层是 system prompt 里的结构化上下文摘要
- 一层是当日聊天消息本身，会作为真实对话 history 一并传给模型

也就是说，**聊天上下文本身是会进入 prompt 的**，不只是摘要。

### 12.2 聊天上下文到底带多少

当前实现里：

- 当天消息会先写入聊天记录
- 然后读取当天该日期下的消息列表
- 再组装进 `messages`
- 为避免无限膨胀，会裁剪为：
  - 1 条 system prompt
  - 外加最近最多 40 条历史消息

因此目前不是“只靠摘要聊天”，而是：

- 最近真实聊天消息进入 prompt
- 同时再带一个“最近对话摘要”辅助模型快速把握语境

需要特别强调的是：

- 这里的“40 条历史消息”是当前真实消息层的硬裁剪边界
- 它优先保证短期连续对话体验
- 跨天稳定记忆则不依赖这 40 条消息，而依赖 Identity / Memory Wiki 注入

补充说明：

- `recentConversationSummary` 本身还会额外读取**最近 8 条消息**做摘要层表达
- `wikiContext` 在构建召回 query 时，会取**最近 3 条消息**拼成检索查询
- 因此当前主链不是“只有 history”也不是“只有摘要”，而是：
  - 近 40 条真实对话消息
  - 最近 8 条消息形成的摘要
  - 最近 3 条消息形成的记忆检索 query

这三层一起服务于“短期连续对话 + 中期语境归纳 + 长期记忆召回”。

### 12.3 观察日志到底读几条

当前实现里的观察日志读取边界是固定的：

- 聊天主 prompt：
  - 读取**当天最多 5 条**观察摘要
- Wiki recall 补充：
  - 读取**当天最多 3 条**观察补充
- Cornie 日记生成：
  - 读取**当天最多 20 条**观察事实

因此观察日志不会在每一轮聊天时被全量塞进 prompt。

还需要补一句产品语义：

- 观察日志**每天归档保存，不会每天清空**
- 但聊天主链**不会把当天全部观察日志原文塞进 prompt**
- 历史观察日志默认也**不会自动整包注入**
- 只有当天少量摘要默认进入主链，其余靠 recall / tool 按需补查

### 12.4 这意味着什么

这套机制的核心取舍是：

- 聊天主链优先轻量，避免 prompt 过长
- 长期记忆承担跨天稳定信息
- 观察日志承担当天事实层记录
- 更细节的历史材料通过 recall / tool 再补查

因此 Identity 页的职责就更清晰了：

- 不负责替代当天聊天上下文
- 不负责替代观察日志流水
- 只负责沉淀“跨天仍然重要”的稳定身份信息

### 12.5 当前主链装载顺序建议理解

可以把当前 prompt 装载顺序理解为：

1. 人设与 JSON 协议
2. 结构化摘要上下文
3. 当天最近真实聊天消息
4. 如有需要，再通过工具补查历史聊天、观察日志、长期记忆细节

所以当前系统不是“把所有聊天历史都拼进去”，也不是“完全不带聊天上下文”，而是：

- 默认带当天最近对话
- 默认带少量摘要层
- 更深历史靠 recall / tool 触发

### 12.6 当前 prompt 装载矩阵

为避免后续开发误把“可查询”理解成“默认注入”，这里明确分层：

| 信息层 | 默认进入主 prompt | 默认进入真实 messages | 按需 recall / tool | 说明 |
| --- | --- | --- | --- | --- |
| 当天最近聊天原文 | 否 | 是 | 否 | 最近最多 40 条 |
| 最近对话摘要 | 是 | 否 | 否 | 最近 8 条摘要化 |
| 主身份页摘要 | 是 | 否 | 否 | 跨天稳定主身份 |
| 相关偏好 / 人物 / trait 摘要 | 视命中情况 | 否 | 是 | 相关时进入 |
| 当天观察日志摘要 | 是 | 否 | 否 | 默认最多 5 条 |
| 当天观察日志补查 | 否 | 否 | 是 | 默认最多 3 条 |
| 历史聊天归档 | 否 | 否 | 是 | 命中主题再查 |
| 历史观察日志 | 否 | 否 | 是 | 命中主题再查 |
| Topic Index 摘要 | 是 | 否 | 否 | 轻量索引层 |
| 完整 Wiki 页面正文 | 否 | 否 | 是 | 不应整页默认塞入 |

这张表是当前模型侧、工具层、记忆层共同遵守的装载边界。

## 13. Identity 与观察日志的分工边界

为了避免记忆层互相污染，建议明确区分：

### 13.1 观察日志记录什么

观察日志记录：

- 当天发生了什么
- 用户说了什么事实
- 某次情绪、事件、消费、安排、表达
- 可作为日记与长期记忆的事实来源

它本质上是**事实流水层**。

### 13.2 Identity 页面记录什么

Identity 页面记录：

- 用户是谁
- 用户与 Cornie 的关系
- 用户长期稳定偏好
- 用户长期特征侧写
- 用户重要人物关系网络

它本质上是**跨天稳定认知层**。

### 13.3 什么不该直接写进 Identity

以下内容不应该因为出现一次就直接进入 Identity：

- 一次性消费
- 偶发情绪
- 当天临时安排
- 低价值寒暄
- 还未稳定的人物判断

这些应先留在观察日志或聊天记录里。

### 13.4 什么适合从观察日志升级进 Identity

以下内容适合从观察日志 / 聊天中逐步升级：

- 用户明确说出自己的名字
- 用户明确说明自己与 Cornie 的关系
- 用户反复提及的重要人物
- 用户多次重复的稳定偏好
- 对未来交互长期有影响的身份设定

### 13.5 一个判断原则

可以用一句话区分三层：

- 聊天记录回答“今天我们具体说了什么”
- 观察日志回答“今天发生了哪些值得留档的事实”
- Identity 回答“跨天之后，Cornie 仍然应该稳定记住你是谁、你和谁有关、什么对你重要”

只要某条内容离不开“具体发生在哪天、哪一轮、哪句话”，它通常先属于聊天记录或观察日志；  
只有当它已经能上升为稳定认知时，才适合进入 Identity。

---

## 14. 开发优先级建议

### P1

- `identity_profile` 主身份页模型
- 默认跨天稳定注入
- 用户名字 / 与 Cornie 的关系闭环

### P2

- `identity_person` 人物页模型
- 关键人物沉淀规则
- Topic Index 对人物页的联动

### P3

- `identity_preference` 偏好页
- `identity_trait` 性格侧写页

### P4

- 页面关系图谱增强
- 更细的治理与合并策略

---

## 15. 当前结论

Identity 不是一页大杂烩，而应该拆成：

- 一个用户主身份页
- 若干偏好页
- 若干性格侧写页
- 若干重要人物页

其中：

- 用户主身份页负责“用户是谁”
- 人物页负责“用户和谁有关、经历过什么”
- Topic Index 负责“快速定位这些记忆在哪些日期、哪些聊天里出现过”

只要这一层建起来，Cornie 才能真正从“会聊天”走向“会长期认识一个人”。
