# Cornie-0701-记忆层存储与长期记忆前端入口设计说明

## 1. 文档目的

这份文档用于正式澄清当前 Cornie 记忆层里两个容易混淆的问题：

1. 聊天记录数据库是否已经切到 `better-sqlite3`
2. 长期记忆 Wiki 当前是否已经有前端入口，普通用户到底能不能用

本文档不是重新发明一套新架构，而是基于当前代码现状，给出统一口径、现状判断与后续落地方向。

---

## 2. 结论先说

### 2.1 关于聊天记录数据库

当前项目的聊天记录模块，已经进入 `better-sqlite3` 主路线，但还不能简单表述为“整个项目数据库都已经全面切完”。

更准确的说法应该是：

- `聊天记录仓储层` 已完成 `better-sqlite3` 路线的设计与首轮实现
- `聊天记录模块` 已具备基于 `better-sqlite3` 的运行时能力
- `项目底层通用数据库初始化` 仍保留历史 `sql.js` 体系
- 因此当前状态是“聊天记录模块已进入 better-sqlite3 主路线”，而不是“全项目数据库已彻底统一迁移”

### 2.2 关于长期记忆 Wiki 前端入口

当前长期记忆 Wiki 并不是没有前端入口，而是处于“双轨状态”：

- 一侧已经存在 `高级入口 / 工作台入口`
- 一侧正在补齐 `普通用户可理解、可安全使用` 的正式入口

更准确的判断应该是：

- `高级前端入口已存在`
- `普通用户长期记忆入口已在建设中`
- `普通用户对长期记忆的增删改查能力已经有部分落地`
- `但完整的产品化收口还没有彻底完成`

## 3. 当前代码现状

### 3.1 聊天记录存储现状

当前聊天记录相关代码主要分为：

- 数据库初始化：`electron/db.js`
- 聊天记录仓储：`electron/backend/chatlog/repository.js`
- 聊天记录服务：`electron/backend/chatlog/service.js`
- 聊天记录接口：`electron/backend/chatlog/routes.js`

现状特征如下：

1. `electron/db.js` 仍承担通用数据库初始化职责，并保留 `sql.js` 历史路径。
2. `electron/backend/chatlog/repository.js` 已同时提供：
   - `sql.js` 仓储实现
   - `better-sqlite3` 仓储实现
3. `createChatlogRepository()` 已支持通过配置选择具体驱动。
4. `package.json` 已正式引入 `better-sqlite3`。

这说明聊天记录模块已经走上“仓储抽象先行”的迁移路径，而不是直接粗暴替换整套数据库层。

### 3.2 长期记忆 Wiki 前端现状

当前长期记忆相关前端主要分为：

- 高级入口：`src/renderer/components/AdvancedSettings.vue`
- Wiki 工作台：`src/renderer/components/MemoryWikiWorkspace.vue`
- 记忆列表：`src/renderer/components/MemoryPageList.vue`
- 记忆详情：`src/renderer/components/MemoryPageDetail.vue`
- 观察与记忆首页：`src/renderer/components/ObserveMemoryHome.vue`
- 主应用导航：`src/renderer/App.vue`

现状特征如下：

1. `MemoryWikiWorkspace.vue` 已经存在，而且能力较强。
2. 它覆盖了很多高级能力，例如：
   - 页面列表
   - 页面创建与编辑
   - 来源查看
   - 主题关联
   - 治理请求
   - 版本 / 回滚 / 审计等高级操作
3. 普通用户侧也并非空白，已经有以下落地：
   - 观察与记忆首页可进入长期记忆区域
   - 记忆列表可查看
   - 记忆详情支持普通用户的新建、编辑、删除闭环
   - Identity 视角正在逐步产品化
4. 但产品分层尚未完全收口：
   - 仍有部分高级语义和普通用户阅读体验混杂
   - 普通用户视角的“关于你 / 重要的人 / 偏好 / 特征”还在持续整理

因此，当被问到“长期记忆 Wiki 有没有前端入口”时，标准回答应该是：

- 有，而且不止一个入口
- 但面向普通用户的正式记忆入口还没有完全收口

## 4. 当前架构判断

当前记忆层相关结构，可以概括为：

`前端 -> API -> 记忆服务层 -> 存储层`

其中记忆服务层下方又分三条主线：

1. 聊天记录
2. 观察日志
3. 长期记忆 Wiki / Identity

### 4.1 聊天记录

- 负责保存原始对话
- 当前已进入 `better-sqlite3` 主路线
- 对外已暴露按日读取、历史列表、检索、导出等能力

### 4.2 观察日志

- 负责保存按需记录的事实层信息
- 不等同于长期记忆
- 不应全量塞进每轮 prompt

### 4.3 长期记忆 Wiki

- 负责保存跨天仍应记住的稳定信息
- 当前主线逐步收口到 Identity 页面体系
- 用户最终应看到的是“关于你、你在意的人、你的偏好、你的特征、你想保留的重要长期事实”
- Topic Index、审计、巡检、回滚等抽象治理能力，不应直接暴露给普通用户

---

## 5. 为什么聊天记录要走 better-sqlite3

`sql.js` 不是完全不能用，而是更适合中小体量、整库装载的场景。

对于聊天记录这种会长期增长的文本流，主要风险有三类：

1. 启动时整库读入内存，规模越大越重
2. 写入后整库导出回盘，成本会持续上升
3. 历史检索、分页、导出需求增加后，运行时压力会更明显

`better-sqlite3` 的价值在于：

1. 原生本地读写，不必整库装入内存
2. 对单日分页、按月读取、关键词检索更友好
3. 聊天记录持续增长时，运行时更稳

所以这里的迁移原则不是“全项目数据库重写”，而是：

- 先把增长最快、查询最密集的聊天记录模块迁到更稳的仓储实现
- 对上层 API 保持兼容
- 再决定是否扩展到其他模块

---

## 6. 为什么不能直接把高级工作台给普通用户

`MemoryWikiWorkspace.vue` 的问题不是“太弱”，而是“太强”。

它现在暴露的能力包括：

- 页面类型
- 别名
- related pages
- 主题关联
- 治理请求
- 巡检
- 版本
- 回滚
- 审计

这些能力对开发和治理有价值，但对普通用户会带来三个问题：

1. 概念负担太重
2. 容易误操作
3. 用户难以理解自己到底是在“看记忆”还是“修系统”

因此普通用户前端应该包装成“记忆内容界面”，而不是直接暴露“治理控制台”。

---

## 7. 普通用户长期记忆前端能力边界

普通用户在“观察与记忆”域里，优先应拥有以下能力。

### 7.1 可查看

- 查看观察日志
- 查看长期记忆页面
- 查看“关于你”
- 查看重要的人
- 查看偏好与习惯
- 查看页面来源摘要

### 7.2 可编辑

- 修改自己的名字、称呼、与 Cornie 的关系描述
- 修改人物页面中的关系、备注、共同经历
- 修改偏好页、习惯页、身份描述页
- 新建长期记忆页面
- 删除不想保留的长期记忆页面

### 7.3 不直接暴露

- Topic Index
- 页面合并细节
- 版本 diff
- 回滚
- 审计日志
- 巡检结果
- 治理请求内部状态

这些能力可以继续存在，但应停留在高级入口，不进入普通用户主界面。

## 8. 正式改造目标

### 8.1 存储层目标

聊天记录模块的正式目标是：

1. 运行时主查询链路稳定走 `better-sqlite3`
2. 保持现有前端 API 契约不变
3. 保持历史聊天、分页、搜索、导出能力一致
4. 不影响观察日志、Wiki、Identity 上层联动

### 8.2 前端入口目标

长期记忆 Wiki 的正式目标是：

1. 保留高级入口作为治理台
2. 独立建设普通用户长期记忆入口
3. 普通入口只呈现“记忆内容”，不呈现“治理术语”
4. 普通用户可对长期记忆做增删改查闭环

## 9. 推荐实施方案

### 9.1 聊天记录存储

#### P1

- 保持现有 chatlog service / routes 契约不变
- 继续以仓储注入方式驱动 `better-sqlite3`
- 将历史读取、分页、搜索相关验证脚本作为迁移基线

#### P2

- 明确 `sql.js` 在聊天记录模块中仅保留兼容路径
- 将主运行时配置切到 `better-sqlite3`
- 补性能与稳定性回归

#### P3

- 视后续情况再决定是否把其他高增长文本模块也做仓储层抽象
- 本期不强求整库完全迁移

### 9.2 长期记忆前端

#### P1

- 在“观察与记忆”中补正式长期记忆入口
- 面向普通用户提供：
  - 记忆列表
  - 记忆详情
  - 新建
  - 编辑
  - 删除

#### P2

- 将 Identity 视为普通用户长期记忆主入口
- 默认提供：
  - 关于你
  - 你在意的人
  - 你的偏好
  - 你的习惯与特征

#### P3

- 来源追溯可做轻量展示
- 版本、审计、回滚、治理池继续停留在高级入口

## 10. 风险与注意事项

### 10.1 存储层风险

如果直接说“数据库已经全改成 better-sqlite3 了”，会带来错误预期。

更准确的说法应当是：

- `聊天记录模块已进入 better-sqlite3 运行时路线`
- `全项目底层数据库尚未完成统一迁移`

### 10.2 前端风险

如果继续把 `MemoryWikiWorkspace.vue` 当成普通用户入口持续扩展，会出现：

- 页面越来越重
- 术语越来越多
- 产品边界继续混乱

所以普通入口和高级治理入口，必须彻底分层。

## 12. 最终结论

当前项目的真实状态可以正式归纳为：

1. 聊天记录并不是还停留在原始阶段，而是已经完成了 `better-sqlite3` 路线的首轮落地与仓储抽象。
2. 但这不等于整个项目已经彻底完成数据库统一迁移。
3. 长期记忆 Wiki 不是没有前端入口，而是同时存在高级入口与普通入口建设中的双轨状态。
4. 真正缺的，不是“有没有界面”，而是面向普通用户的长期记忆正式产品入口是否完全收口。

因此后续应坚持两条线并行：

1. 聊天记录存储层继续稳步推进 `better-sqlite3` 主运行时化
2. 长期记忆前端继续从“高级治理台”分化出“普通用户记忆入口”

这才是当前代码现状下，最准确也最稳妥的落地方向。
