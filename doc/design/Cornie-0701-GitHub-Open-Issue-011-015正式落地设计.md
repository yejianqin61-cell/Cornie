## 3. 总体判断

这 4 个 issue 有一个共同点：

- 不是后端主能力完全缺失
- 不是业务链路完全不存在
- 而是前端没有把已有能力正确组织成普通用户可理解、可顺手使用的成品体验

换句话说，当前问题已经从“能不能做”进入“做出来像不像一个能用的产品”阶段。

因此本轮设计目标不是继续堆技术能力，而是把以下四类体验补齐：

1. 主流程中的就地闭环
2. 数据表达的可读性
3. 页面布局的信息密度控制
4. 模型产出内容的成品化展示

## 4. 单项问题分析与落地方案

## 4.1 Issue #11 记账页新建类目闭环

### 4.1.1 用户真实诉求

用户不是想进入一个复杂的类目治理后台，而是在记账时发现：

- 现在没有合适类目
- 我想立刻补一个
- 补完后继续把这笔账记完

所以这里的核心不是“有没有类目管理功能”，而是“记账页内是否存在不中断的补类目闭环”。

### 4.1.2 当前问题本质

当前前端即使已经存在类目相关能力，也没有在普通用户记账主流程里形成自然入口，导致用户感知为“工具缺失”。

问题主要体现在：

1. 入口不可见或不明显
2. 创建动作可能把用户带离当前记账场景
3. 新建成功后未自动回填当前表单
4. 普通用户会把“缺一个就地入口”理解成“整个功能没做”

### 4.1.3 设计目标

记账页需要支持：

1. 在当前页面内直接新建类目
2. 不丢失已填写的金额、备注、日期等草稿
3. 新建成功后自动选中新类目
4. 全程不暴露技术术语和高级治理概念

### 4.1.4 推荐交互

推荐采用“类目选择器旁边的轻入口 + 轻弹层”：

1. 在类目下拉框旁边增加 `新建类目`
2. 点击后弹出小型表单
3. 表单只保留最小必要字段：
   - 类目名称
   - 收入/支出类型
4. 提交成功后自动：
   - 关闭弹层
   - 刷新类目列表
   - 选中新类目
   - 保留当前记账其他字段

### 4.1.5 错误与空态要求

1. 类目重名给出平实提示
2. 创建失败不能清空当前记账草稿
3. 不直接把后端原始错误暴露给用户

### 4.1.6 验收口径

1. 用户不离开记账页即可新增类目
2. 新建成功后当前表单自动继续可用
3. 用户不会误以为“类目功能缺失”

## 4.2 Issue #13 收支页趋势图语义增强

### 4.2.1 用户真实诉求

用户在吐槽“第一象限、xy轴”的时候，本质上是在说：

- 我看不懂这张图在表达什么
- 这张图不像一个能读数的趋势图

这不是纯审美问题，而是信息表达失败。

### 4.2.2 当前问题本质

当前趋势图即使已经有曲线或统计可视化，也缺少清晰的坐标语义：

1. 横轴没有稳定表达时间
2. 纵轴没有稳定表达金额
3. 收入与支出的区分不够明确
4. 用户无法快速判断趋势高低和时间分布

### 4.2.3 设计目标

把收支趋势图从“装饰性图形”提升为“可读的金额趋势图”，至少做到：

1. 一眼能看出横轴是时间
2. 一眼能看出纵轴是金额
3. 数据点与折线关系清楚
4. 收入与支出区分稳定

### 4.2.4 推荐实现方向

1. 增加明确的 X 轴日期刻度
2. 增加明确的 Y 轴金额刻度
3. 曲线保持正常第一象限语义
4. 为收入和支出提供稳定颜色与图例
5. 空数据时显示空态说明，不绘制误导性曲线

### 4.2.5 体验要求

图表不应做成“数据中台”风格，而应保持：

1. 普通用户看得懂
2. 第一眼能判断最近花得多不多
3. 与页面其他温和视觉语言协调

### 4.2.6 验收口径

1. 横轴时间、纵轴金额清楚可辨
2. 收入/支出至少有一种稳定的视觉区分
3. 在日期筛选前后，图表语义一致

## 4.3 Issue #14 日程页顶部工具区压缩

### 4.3.1 用户真实诉求

用户不是在抱怨功能太多，而是在抱怨：

- 顶部堆叠太重
- 重要信息没有被放在最顺手的位置
- 页面一进去就感觉乱

### 4.3.2 当前问题本质

当前日程页顶部可能把“日期状态”和“新增安排入口”做成了上下分离的大块卡片，造成：

1. 首屏垂直空间被吃掉
2. 真正重要的日程列表被往下推
3. 页面显得像控制面板，而不是日常安排页

### 4.3.3 设计目标

日程页顶部应当尽快回答四个问题：

1. 我现在在看哪一天
2. 我怎么回到今天
3. 我怎么清除筛选
4. 我怎么新增安排

而且这些动作应该在同一视觉层级内被组织好。

### 4.3.4 推荐交互结构

建议改成“一条压缩工具栏 + 按需展开表单”：

1. 左侧显示当前查看日期
2. 中部或右侧放 `回到今天`、`清除筛选`
3. 右侧主按钮放 `新增安排`
4. 新增表单默认折叠，仅在点击按钮后展开到工具栏下方

### 4.3.5 视觉要求

1. 顶部说明语缩短
2. 按钮比说明文字更突出
3. 避免连续上下堆两张大卡片
4. 让日程列表尽量上移

### 4.3.6 验收口径

1. 顶部工具区在一屏内更紧凑
2. 新增安排入口仍清楚可见
3. 首屏可见的日程内容明显增多

## 4.4 Issue #15 Cornie 日记 Markdown 渲染

### 4.4.1 用户真实诉求

用户想看到的是“写好的日记”，不是带 `##`、`**` 的原始模型标记。

这说明当前问题不是内容没有生成，而是内容没有被正确呈现。

### 4.4.2 当前问题本质

大模型输出已经进入 Markdown 形态，但前端仍按纯文本直出，导致：

1. 标题不成标题
2. 强调不成强调
3. 长文阅读体验差
4. 成品感大幅下降

### 4.4.3 设计目标

在安全前提下，把 Cornie 日记按 Markdown 的安全子集进行渲染，让用户读到的是自然排版后的日记内容。

### 4.4.4 推荐支持范围

本期建议支持：

1. 标题
2. 段落
3. 粗体
4. 斜体
5. 引用
6. 无序列表
7. 合理换行

### 4.4.5 风险控制

本期不应开放：

1. 原始 HTML 直通
2. 脚本注入
3. 高风险富文本能力

### 4.4.6 容错要求

1. Markdown 不完整时也能尽量渲染
2. 即使模型输出被截断，也不能整块崩坏
3. 异常内容至少要优雅降级到纯文本

### 4.4.7 验收口径

1. `##`、`**` 等标记不再直接裸露
2. 日记正文具备稳定阅读版式
3. 异常内容不会把整个页面渲染坏

## 5. 开发优先级建议

推荐顺序如下：

1. `#11` 记账页新建类目闭环
2. `#15` Cornie 日记 Markdown 渲染
3. `#14` 日程页顶部工具区压缩
4. `#13` 收支趋势图语义增强

原因如下：

1. `#11` 直接影响主流程是否能顺手完成
2. `#15` 直接影响内容成品感，收益高且边界清晰
3. `#14` 属于页面结构整理，能明显改善可用性
4. `#13` 虽然重要，但更偏可视化表达升级，适合排在后面

---

## 6. 推荐拆分的开发 task

建议直接拆成 4 个主 task：

1. 记账页类目创建入口与回流闭环
2. Cornie 日记 Markdown 安全渲染
3. 日程页顶部工具栏压缩与新增卡片合并
4. 收支趋势图坐标语义与图例增强

如果需要更细拆，可每项再拆成三段：

1. 交互结构改造
2. 视觉样式落地
3. 回归测试与验收

---

## 7. 最终结论

当前这批 GitHub open issue 的核心，不在于继续扩充底层能力，而在于把已有能力整理成普通用户可直接感知到的产品体验。

本轮前端治理应坚持两条原则：

1. 普通用户只面对自己的日常动作，不面对系统治理复杂度
2. 页面中的图、文、表单都要服务“看得懂、用得顺、不会打断”

按这个方向推进，后续拆 task 和逐项收口都会更稳。
