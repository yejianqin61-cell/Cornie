## 1. 文档目的

本文件用于把 Cornie 当前整套记忆系统的设计哲学、工程架构、运行思路、Prompt 构建方式，以及模型返回分支统一收口。

它回答五个问题：

1. Cornie 为什么要把“记忆”拆成观察日志、Cornie 日记、长期记忆 Wiki 三层
2. 整套记忆系统在工程上到底是怎么分层的
3. 不同情景下 Prompt 是怎么拼出来的
4. DeepSeek 在不同轮次允许返回哪些结构
5. 一条对话最终如何影响账本、待办、观察日志、长期记忆和日记

---

## 2. 设计哲学

Cornie 的记忆系统不是“把所有聊天存起来”，而是把记忆分成不同职责的层。

### 2.1 三层记忆观

| 层 | 定位 | 作用 | 风格 |
| --- | --- | --- | --- |
| 观察日志 | 事实层 | 记录当天发生了什么 | 客观、简洁、如实 |
| Cornie 日记 | 关怀层 | 生成铃湾视角的文学化回顾 | 温柔、文学化、有人味 |
| 长期记忆 Wiki | 稳定层 | 保存长期偏好、重要人物、重大事件、长期目标 | 结构化、可治理、可追溯 |

### 2.2 核心原则

1. 不把“聊天记录”直接等于“记忆”。
2. 观察日志优先记录事实，不承担文学表达。
3. Cornie 日记不是原始记录，而是对当天事实的关怀性整理。
4. 长期记忆不是全量聊天归档，而是值得长期保留的信息。
5. 长期记忆必须可被人类查看、编辑、回滚、合并、治理。
6. Prompt 不塞全量材料，而采用“摘要进 Prompt，细节靠工具补查”。
7. 模型每轮都可以接触长期记忆，但必须克制使用，避免恐怖谷。
8. 模型能做的操作，人类也应有对等接口。

### 2.3 为什么必须是 Wiki，而不是一份长文档

因为长期记忆会持续增长，若全塞成一份长文档，会出现：

1. Prompt 越来越长
2. 检索越来越不准
3. 编辑、合并、回滚都很困难
4. 用户几乎无法人工治理

因此 Cornie 选择：

1. 以 `Wiki 页面` 作为长期记忆一等公民
2. 以 `Topic Index` 作为主题入口
3. 以 `Version / Governance / Audit` 作为治理支撑

## 3. 系统总体架构

Cornie 当前的记忆系统可以概括为：

`前端 / 模型 -> 对话编排层 -> Prompt 构建层 -> 工具策略层 -> 记忆服务层 -> 记忆治理层 -> 记忆存储层`

### 3.1 逻辑分层

| 层 | 主要职责 | 关键文件 |
| --- | --- | --- |
| 交互层 | 接收用户对话、前端查看和治理 | `src/renderer/*` |
| 对话编排层 | 组织每轮模型调用、工具回合、确认流 | `electron/backend/agent/orchestrator.js` |
| Prompt 构建层 | 拼人格、协议、上下文摘要、后续提示 | `electron/backend/agent/promptBuilder.js` |
| 协议与解析层 | 约束模型只返回合法 JSON | `electron/backend/agent/jsonProtocol.js` |
| 策略层 | 决定 allow / confirm / ask_back / deny | `electron/backend/policy/rules.js` |
| 工具网关层 | 执行工具调用 | `electron/backend/tools/gateway.js` |
| 观察日志层 | 记录当日事实、做轻度去重 | `electron/backend/observation/service.js` |
| 长期记忆核心层 | 读写 Memory Wiki / Topic Index | `electron/backend/memory-wiki/*` |
| 记忆消费层 | 为模型构造 memory / topic / chat / observation 摘要 | `electron/backend/agent/wikiContext.js` |
| 日记生成层 | 用观察日志、人类日记、相关记忆生成 Cornie 日记 | `electron/backend/diary/generator.js` |

### 3.2 记忆系统核心对象

| 对象 | 说明 |
| --- | --- |
| Observation | 当天事实记录 |
| Diary Entry | 用户日记与 Cornie 日记 |
| Memory Wiki Page | 长期记忆页面 |
| Topic Index Item | 主题索引项，如“龙虾”“钟奕菲” |
| Governance Request | 待审核的治理动作，如合并、归档、调整重要性 |
| Version | Wiki 页面历史版本 |
| Chatlog Link | 主题与聊天日期的关联 |
| Observation Link | 主题与观察日志的关联 |

## 4. 运行时主链路

### 4.1 普通对话主链路

1. 用户发送消息
2. 对话编排层读取当日历史消息
3. 构建上下文摘要
4. 拼接主 Prompt
5. 调用 DeepSeek
6. 解析模型返回的 JSON
7. 若是 `reply`，直接回复
8. 若是 `tool_call`，进入策略层
9. 策略层返回 `allow / confirm / ask_back / deny`
10. 若允许执行，则调用工具并进入后续 Prompt
11. 最终保存 Cornie 回复
12. 结束后尝试写观察日志与长期记忆

### 4.2 观察日志与长期记忆写入链路

当前实现中，对话结束后：

1. `observation.recordConversationTurn(...)`
2. `memory.deriveFromConversation(...)`
3. 若符合条件则新增观察或长期记忆

注意：当前观察日志写入规则偏宽，容易写成“对话流水摘录”，这属于现阶段实现偏差，不是最终理想态。

### 4.3 Cornie 日记生成链路

1. 读取当天人类日记
2. 读取当天观察日志
3. 读取相关长期记忆摘要
4. 读取往年今日
5. 构建日记 Prompt
6. 调用 DeepSeek 生成文学化日记
7. 若首轮被 `length` 截断，则自动续写一轮
8. 写回 `diary_entries.cornie_text`

## 5. Prompt 构建总原则

### 5.1 一般原则

1. Prompt 永远先放人格与协议，再放上下文。
2. 能摘要就摘要，不直接塞原文全集。
3. 模型第一轮优先完成“理解与判断”，而不是盲目执行。
4. 完整细节通过只读工具补查。
5. 后续 Prompt 不重放所有上下文，只补“本轮工具结果”和“接下来该做什么”。

### 5.2 进入主 Prompt 的上下文

当前主 Prompt 由以下内容构成：

1. 日期
2. 最近对话摘要
3. 类目摘要
4. 未完成待办摘要
5. 近期日程摘要
6. 今日观察日志摘要
7. 长期记忆摘要
8. 主题索引摘要
9. 历史聊天命中摘要
10. 观察补查摘要
11. 可用工具摘要

### 5.3 默认不直接进入主 Prompt 的内容

1. 全量待办
2. 全量日程
3. 全量观察日志原文
4. 全量长期记忆全文
5. 全量聊天记录
6. 全量 Wiki 页面正文

这些内容应通过只读工具或检索摘要按需补查。

## 6. 全情景 Prompt 构建

本节按“情景”枚举 Prompt。

### 6.1 情景 A：对话首轮 Prompt

**用途**

用于每次用户发来新消息后的第一轮模型判断。

**组成**

1. Cornie 人格设定
2. 严格 JSON 协议
3. 类目映射规则
4. 当轮上下文摘要

**目标**

让模型首轮只做两种输出之一：

1. 普通回复 `reply`
2. 工具调用请求 `tool_call`

**关键特点**

1. 主人格中规定铃湾/小铃湾口吻
2. 规定不能输出解释、Markdown、额外文字
3. 规定类目映射的互斥规则
4. 规定信息不足时优先追问，而不是乱写

### 6.2 情景 B：只读补查后的 Follow-up Prompt

**触发条件**

首轮 `tool_call` 是只读查阅类工具，如：

1. 类目补查
2. 只读查询待办 / 日程 / 观察 / 记忆

**组成**

1. 告知模型“刚刚完成的是只读补查，不是最终写入”
2. 附上补查结果摘要
3. 要求模型重新判断：
   - 直接命中已有类目
   - 继续发起业务写入
   - 或 `reply` 追问

**允许输出**

1. `reply`
2. `tool_call`

**不允许输出**

1. 再次无休止补查同一域
2. 已经足够判断却仍反复查

### 6.3 情景 C：工具执行后的 Follow-up Prompt

**触发条件**

某轮 `tool_call` 已真正执行。

**组成**

1. 告知模型“刚刚已经执行过工具”
2. 附上工具结果
3. 要求它只生成给用户的最终说明

**允许输出**

只允许：

1. `reply`

**设计原因**

工具已经执行完，这一轮模型不应再发起新的业务动作，而应负责把结果说清楚。

### 6.4 情景 D：确认通过后的 Follow-up Prompt

**触发条件**

高风险动作先进入确认流，用户批准后，需要继续执行并给出后续说明。

**组成**

1. 重新构建当日上下文
2. 附上确认后执行的工具结果
3. 要求模型给出确认后的自然回复

**允许输出**

当前实现以 `reply` 为主。

**适用动作**

1. 类目新增确认
2. 类目候选歧义确认
3. 长期记忆 Wiki 高风险治理动作确认

### 6.5 情景 E：JSON 修复 Prompt

**触发条件**

模型首轮返回了不合法 JSON。

**组成**

1. 明确指出上一条不符合协议
2. 重申只允许 `reply / tool_call`
3. 重申结构格式
4. 附上原始错误输出

**目标**

给模型一次修复机会。

### 6.6 情景 F：Cornie 日记生成 Prompt

**用途**

生成当天的 Cornie 日记。

**组成**

1. Cornie 日记人格设定
2. 当天日期
3. 主人今天写下的人类日记
4. 当天观察日志全文摘要
5. 相关长期记忆摘要
6. 往年今日参考
7. “请直接写出 Cornie 日记正文”

**特点**

1. 不是 JSON 协议，而是直接生成正文
2. 不要求工具调用
3. 不允许编造未发生的核心事实

### 6.7 情景 G：日记续写 Prompt

**触发条件**

Cornie 日记首轮生成被 `finish_reason = length` 截断。

**组成**

1. 告知模型上一段输出被截断
2. 要求从最后一句自然续写
3. 不要重复前文
4. 附上已生成的前文

**目标**

把被截断的半篇日记补完。

## 7. 当前主 Prompt 的上下文来源

### 7.1 最近对话摘要

来自当日聊天记录，默认截最近若干条。

### 7.2 类目摘要

来自收支 / 待办 / 日程当前类目快照。

### 7.3 待办与日程摘要

默认只放：

1. 未完成待办前几条
2. 已安排日程前几条

### 7.4 观察日志摘要

当前实现默认只放当天前几条观察日志标题摘要，不放全文。

### 7.5 长期记忆摘要

来自 `wikiContext`：

1. 按重要性和确认状态选出的 Memory Wiki 页面摘要
2. 不是全量 Wiki 正文

### 7.6 主题索引摘要

来自 Topic Index：

1. 结合 query 命中
2. 结合主题热度、日期次数、关联页面数

### 7.7 历史聊天命中摘要

不是把历史聊天原文塞进 Prompt，而是只给“哪些日期命中过当前 query”。

### 7.8 观察补查摘要

来自当日少量观察记录，用于帮助模型避免重复写观察。

## 8. 模型允许返回的所有情况

本节分“协议层返回”和“策略层结果”两种。

### 8.1 协议层：模型原始返回

#### 8.1.1 `reply`

结构：

```json
{
  "type": "reply",
  "assistant_reply": "..."
}
```

含义：

1. 不需要工具
2. 或信息不足，先自然回应

#### 8.1.2 `tool_call`

结构：

```json
{
  "type": "tool_call",
  "assistant_reply": "...",
  "tool_calls": [
    {
      "tool_name": "tool.name",
      "arguments": {}
    }
  ]
}
```

含义：

1. 模型判断需要执行一个或多个工具
2. `assistant_reply` 是给用户看的即时说明

#### 8.1.3 非法 JSON

含义：

1. 格式错误
2. 输出了多余解释
3. 顶层字段不合规

处理：

1. 进入 JSON 修复 Prompt
2. 给一次修复重试
3. 再失败则走系统兜底回复

### 8.2 策略层：对 `tool_call` 的裁决

#### 8.2.1 `allow`

含义：

1. 工具允许直接执行
2. 常见于中低风险、参数完整动作

#### 8.2.2 `confirm`

含义：

1. 动作高风险
2. 或类目存在歧义
3. 或涉及新增类目
4. 或涉及长期记忆 Wiki 治理

结果：

1. 生成待确认项
2. 不立刻执行
3. 等用户批准/拒绝

#### 8.2.3 `ask_back`

含义：

1. 信息不足
2. 候选太歧义
3. 同一域补查次数已用尽
4. 高风险动作缺少必要前提

结果：

1. 不执行工具
2. 返回追问

#### 8.2.4 `deny`

含义：

1. 动作不被允许
2. 风险或规则不满足

结果：

1. 不执行工具
2. 返回拒绝原因

## 9. 业务场景与模型分支矩阵

### 9.1 普通聊天

1. 能直接回应 -> `reply`
2. 不够信息但无需工具 -> `reply`

### 9.2 记账

1. 金额、方向、类目都清楚 -> `tool_call -> allow`
2. 金额清楚但类目歧义 -> `tool_call -> confirm`
3. 金额清楚但需要新类目 -> `tool_call -> confirm`
4. 连收入还是支出都不清楚 -> `reply` 追问
5. 已执行成功 -> 工具后续 Prompt -> `reply`

### 9.3 待办 / 日程

1. 标题、时间、类目足够 -> `tool_call -> allow`
2. 时间不清楚 -> `reply` 追问
3. 类目无合适候选 -> `tool_call -> confirm`
4. 只想查看而非写入 -> 可先只读补查 -> `tool_call`

### 9.4 观察日志

理想设计应是：

1. 新事实 -> 新增观察
2. 已有事实补充 -> 更新观察
3. 低价值重复 -> 不写

当前实现偏宽：

1. 对话较长或命中关键词就可能新增一条
2. 容易形成聊天摘录式观察

### 9.5 长期记忆

1. 稳定偏好 / 长期需求 / 重大事件 -> 允许申请写入
2. 短期情绪、一次性碎事 -> 不应轻易写入
3. 高风险治理动作 -> `confirm`
4. 信息不足或价值不稳定 -> `ask_back` 或直接不写

### 9.6 Cornie 日记

1. 输入充分 -> 直接生成正文
2. 首轮截断 -> 续写
3. 生成失败 -> 使用温和兜底文案

## 10. 记忆系统中的“人类接口 = 模型工具接口”

本系统遵循一条硬原则：

`模型可调用的能力，应尽量与人类可操作的能力对齐。`

原因：

1. 避免模型比人类更有权限
2. 避免人类无法干预模型写下的记忆
3. 便于前端治理、回滚、审核

因此长期记忆 Wiki 最终应支持两套等价入口：

1. 模型工具集
2. 人类前端 / 路由接口集

## 11. 当前系统的优点

1. 已经不是单一 memory 表，而是多层记忆架构
2. 已经有长期记忆页面、主题索引、版本、治理、审计骨架
3. 已实现“摘要进 Prompt，细节靠工具”的基本模式
4. 已具备 `reply / tool_call / confirm / ask_back / deny` 的完整分支
5. 已有 Cornie 日记从观察日志和记忆摘要生成的链路

---

## 12. 当前系统的主要偏差与缺口

### 12.1 观察日志仍偏流水账

当前实现中，观察日志自动写入规则过宽，且内容常直接保存为：

1. 主人原话
2. 铃湾原话

这与目标中的“事实层、低噪声、按需记录”不完全一致。

### 12.2 长期记忆存在双轨并存

仓库中同时存在：

1. 旧式 `memory_entries`
2. 新式 `memory_wiki`

长期目标应继续向 LLM Wiki 主轨收口。

### 12.3 Cornie 日记生成仍偏重单次 Prompt

当前日记生成已经加入截断续写，但在来源治理、弱数据态处理、写作风格稳定性上仍有提升空间。

### 12.4 Prompt 与治理规则还可继续收紧

例如：

1. 观察日志应先看今日摘要再决定新增 / 更新 / 不写
2. 长期记忆应更严格地区分“长期价值”与“瞬时波动”

---

## 13. 后续推荐演进方向

1. 把观察日志从“聊天摘录”升级为“事实提炼记录”
2. 继续收口长期记忆到 LLM Wiki 主轨
3. 增强 Topic Index 热度衰减与检索排序
4. 让 Prompt 中的观察 / 记忆摘要更结构化
5. 补全前端可视治理体验，使用户可主动查看、修订、合并、回滚记忆

---

## 14. 一句话总结

Cornie 的记忆系统，本质上不是“记住聊天”，而是：

`把对话转化为事实观察，把事实沉淀为长期记忆，把长期记忆克制地反哺下一轮对话，并最终生成带有人文关怀的 Cornie 日记。`

这套系统的核心，不是存得越多越好，而是：

`分层、克制、可治理、可回看、可被人类最终把关。`
