## 2. 先讲人话：什么是 RAG

RAG 可以先简单理解成一句话：

> **先找资料，再让模型说话。**

在 Cornie 里，“资料”不是网页，也不是论文，而是：

- 主人的长期偏好
- 主人的长期厌恶
- 长期需求和目标
- 重要人物、宠物、项目、事件
- 已经确认有价值的历史事实

所以在 Cornie 里，RAG 的意思不是“高深的 AI 黑科技”，而是：

1. 把长期记忆存起来
2. 每次对话时，不把全部记忆都喂给模型
3. 而是先找出“这次最相关的几条”
4. 再把这几条放进 prompt

这就是 Cornie 版本的 RAG。

## 3. 为什么 Cornie 需要 RAG

如果没有 RAG，长期记忆通常会走向两个坏结果：

### 3.1 方案一：全塞进 prompt

问题：

- prompt 会越来越长
- 成本越来越高
- 不相关记忆干扰当前判断
- 更容易出现“恐怖谷”

### 3.2 方案二：完全不带长期记忆

问题：

- Cornie 会像没有连续性的聊天机器人
- 记不住主人的偏好
- 没法形成陪伴感

所以最合理的方案就是：

> **长期记忆不全塞，也不完全不用，而是按需检索。**

## 4. Cornie 的长期记忆到底记什么

长期记忆不是“所有聊天内容”，而是“值得长期保留的信息”。

### 4.1 应进入长期记忆的内容

| 类别 | 示例 |
| --- | --- |
| 稳定偏好 | 喜欢黑咖啡、喜欢安静办公、喜欢蓝色 |
| 稳定厌恶 | 不喜欢香菜、不喜欢被频繁提醒 |
| 长期目标 | 正在准备考研、想坚持记账、想减脂 |
| 重要关系 | 有一只猫、和某位朋友关系重要、家人健康情况 |
| 重要项目 | 正在做 Cornie、正在找工作、正在准备答辩 |
| 重大事件 | 搬家、换工作、生病、宠物去世、重要考试 |

### 4.2 不应轻易进入长期记忆的内容

| 类别 | 示例 |
| --- | --- |
| 一次性情绪 | 今天有点烦、刚刚有点饿 |
| 低价值闲聊 | 哈哈哈、在吗、今天天气不错 |
| 暂时性选择 | 今天想吃甜一点、今晚想早点睡 |
| 模糊表达 | 可能吧、也许以后再说 |

## 5. Cornie 的记忆分层

我建议长期记忆做成三层：

### 5.1 活跃记忆

最常用、最相关、最稳定的记忆。

例子：

- 主人不喜欢太甜
- 主人正在做 Cornie
- 主人想坚持记账

特点：

- 默认优先参与检索
- 更可能进入 prompt

### 5.2 低频记忆

仍然有价值，但不是每轮都该用。

例子：

- 去年搬过家
- 前阵子在准备面试
- 某段时间在健身

特点：

- 默认不直接进 prompt
- 只有相关时才会被检索出来

### 5.3 归档记忆

历史型、阶段型、低活跃度的记忆。

例子：

- 2026 年 6 月在准备某次答辩
- 一段已经结束的短期目标

特点：

- 默认不进入 prompt
- 只在明确相关时用作补充

## 6. MVP 阶段不要把长期记忆做成“大文档”

这是最重要的设计判断之一：

> **长期记忆不要做成一份越写越长的 Markdown 文档。**

原因：

- 不利于检索
- 不利于覆盖和替换旧记忆
- 不利于降权和归档
- 不利于避免重复

更好的做法是：

> **长期记忆做成一条条结构化记录。**

每条记忆都是数据库里的一个对象，而不是大段拼接文本。

## 7. MVP 阶段的 RAG，不需要复杂向量库

你现在几乎 0 基础是完全没问题的，因为 Cornie 的 MVP 阶段可以先不上复杂 RAG。

### 7.1 MVP 方案

先做：

- 结构化记忆表
- 标签 / 类型 / 关键词检索
- 权重排序
- 最近使用时间排序

也就是说，MVP 阶段不需要先搞：

- 向量数据库
- embedding 服务
- reranker
- 复杂召回链路

### 7.2 MVP 检索逻辑

可以先这样做：

1. 从当前用户消息里抽关键词
2. 用关键词匹配 `memory_entries`
3. 再结合：
   - `kind`
   - `weight`
   - `last_used_at`
   - `is_active`
4. 取前 3-5 条最相关记忆
5. 生成摘要注入 prompt

这已经能做出一个非常实用的“轻量 RAG”。

## 8. 长期记忆数据模型建议

```sql
CREATE TABLE IF NOT EXISTS memory_entries (
  id TEXT PRIMARY KEY,
  kind TEXT NOT NULL,
  title TEXT NOT NULL,
  content TEXT NOT NULL,
  tags_json TEXT,
  source_text TEXT,
  weight REAL DEFAULT 1.0,
  is_active INTEGER NOT NULL DEFAULT 1,
  last_used_at INTEGER,
  archived_at INTEGER,
  superseded_by TEXT,
  summary_group TEXT,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
```

字段含义建议：

| 字段 | 说明 |
| --- | --- |
| `kind` | 记忆类型，如 `preference` / `dislike` / `goal` / `event` |
| `title` | 简短标题 |
| `content` | 结构化或半结构化内容 |
| `tags_json` | 关键词标签 |
| `source_text` | 触发这条记忆的原始话语 |
| `weight` | 重要性权重 |
| `is_active` | 是否活跃 |
| `last_used_at` | 最近一次被引用时间 |
| `archived_at` | 归档时间 |
| `superseded_by` | 被哪条新记忆覆盖 |
| `summary_group` | 用于压缩合并 |

## 9. 长期记忆的写入机制

长期记忆不是每轮都写，而是“按需申请写入”。

### 9.1 写入来源

来源只有一个：

- AI 与人类对话过程中，由模型提出 `memory.create` 请求

### 9.2 写入判断

模型不是看到一点信息就写，而是判断：

- 这是不是稳定信息
- 这是不是未来还会有帮助
- 这是不是值得长期保留

### 9.3 写入策略建议

| 场景 | 默认策略 |
| --- | --- |
| 明显稳定偏好 | 可申请写入 |
| 明显稳定厌恶 | 可申请写入 |
| 明确长期目标 | 可申请写入 |
| 重大人生事件 | 可申请写入 |
| 一次性心情 | 不写入 |
| 低信息量闲聊 | 不写入 |
| 可能造成误解的信息 | 先追问或不写入 |

### 9.4 是否需要确认

我建议长期记忆写入属于 **高风险操作**，默认走确认流或至少经过 Tool Policy Layer 的严格判定。

原因：

- 写错一次会影响未来很多轮对话
- 用户会很在意“你到底记住了什么”

## 10. 长期记忆的检索机制

### 10.1 检索输入

检索时可以用这些内容作为查询线索：

- 当前用户消息
- 当前话题标签
- 本轮提议调用的工具类型
- 相关观察日志摘要

### 10.2 检索输出

检索输出不是整库，而是：

- 相关的 3-5 条活跃记忆
- 每条附简要摘要

例如：

```json
[
  {
    "id": "mem_001",
    "kind": "preference",
    "summary": "主人不喜欢太甜的饮品"
  },
  {
    "id": "mem_014",
    "kind": "goal",
    "summary": "主人想坚持长期记账"
  }
]
```

### 10.3 检索后注入 prompt

注入方式建议是摘要，而不是原始全文：

```text
长期记忆摘要：
1. 主人不喜欢太甜的饮品。
2. 主人想坚持长期记账。
```

## 11. 长期记忆的归档机制

长期记忆如果不归档，最后一定会膨胀。

### 11.1 归档条件建议

| 条件 | 说明 |
| --- | --- |
| 长时间未被使用 | 如 90 天以上未命中 |
| 已被新记忆覆盖 | 如“以前喜欢 A，现在明确更喜欢 B” |
| 阶段性目标已结束 | 如某次面试准备、某次答辩准备已完成 |
| 已不再有效 | 用户明确否认或放弃 |

### 11.2 归档后的行为

归档后：

- 不默认进入 prompt
- 不参与普通摘要
- 仍可在特殊检索中命中

## 12. 长期记忆的压缩机制

压缩不是“删掉”，而是“合并和降权”。

### 12.1 合并

例如：

- 喜欢黑咖啡
- 不喜欢太甜
- 平时更偏爱苦一点的饮品

可以压缩成：

- 偏好不甜、偏苦口味，尤其偏爱黑咖啡

### 12.2 覆盖

如果用户偏好发生变化：

- 新记忆成为活跃记忆
- 旧记忆转归档

### 12.3 降权

长期未被提及、也未被使用的记忆：

- 降低 `weight`
- 仍然保留

## 13. Cornie 的长期记忆为什么适合 RAG

因为长期记忆本质上就是一个“小型私有知识库”。

RAG 正好解决两个问题：

1. 不让 prompt 无限增长
2. 让模型只看到当前最有用的那几条记忆

所以 Cornie 的长期记忆和 RAG 是天然匹配的。

## 14. Cornie 的 RAG 演进路线

### 14.1 MVP

- 结构化记忆表
- 标签和关键词检索
- 权重 + 时间排序
- 相关记忆摘要注入 prompt

### 14.2 V1

- 引入 embedding
- 做轻量语义检索
- 支持“意思接近但词不完全一样”的召回

### 14.3 V2

- 完整 RAG
- 召回 + 重排序 + 记忆摘要压缩
- 支持更自然的长期陪伴体验

## 15. 当前最推荐的 Cornie 落地方案

如果只看你当前项目阶段，我最推荐的是：

### 15.1 现在就做

- 结构化长期记忆表
- `memory.create / update / delete / list_active / search`
- 关键词 + 标签检索
- 活跃 / 低频 / 归档 三层机制
- 每轮只注入检索出的摘要记忆

### 15.2 现在不要急着做

- 向量数据库
- 复杂 embedding 基础设施
- 复杂 rerank 链路

## 16. 设计结论

1. Cornie 的长期记忆不应该做成一份无限增长的大文档。
2. 更合理的做法是把长期记忆做成结构化、可检索的记忆条目集合。
3. Cornie 的 RAG 在 MVP 阶段不需要复杂技术，可以先做“关键词/标签检索版轻量 RAG”。
4. 每轮对话不应携带全部长期记忆，而应只携带当前最相关的几条摘要。
5. 长期记忆必须支持活跃、低频、归档三层分级。
6. 长期记忆写入属于高风险动作，应由模型提出、策略层审核、必要时由人类确认。
