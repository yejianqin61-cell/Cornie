## 2. 文档目标

这份文档只讨论一件事：

`Cornie 的记忆层，到底是怎样分层、怎样流动、怎样存储、怎样被模型和人类共同使用的。`

它不讨论整个产品前端，不讨论所有业务域，只关注长期记忆及其相关支撑层。

这份文档的目标有四个：

1. 给出记忆层的总体分层结构。
2. 澄清“前端 -> API -> 记忆 -> 数据库”这一说法哪里对、哪里不够准确。
3. 明确现阶段记忆层已经具备的可复用骨架。
4. 为未来把记忆层抽成脚手架提供架构边界。

## 3. 核心结论

如果只用一句话描述 Cornie 的记忆层架构，可以写成：

`前端 / 模型 -> 记忆 API -> 记忆服务层 -> 记忆治理层 -> 记忆存储层 -> 文件系统 / 结构化存储`

也就是说：

1. “记忆”不是一个单块模块。
2. “数据库”也不是唯一存储终点。
3. 记忆层本质上已经是一个多层结构，而不是简单 CRUD。

更准确地说，Cornie 当前的记忆层是：

`一个以 Wiki 页面为主载体，以主题索引、来源引用、版本系统、治理机制、上下文装载为支撑的长期记忆架构。`

## 4. 为什么“前端 -> API -> 记忆 -> 数据库”不够准确

这个说法作为最粗粒度理解没有问题，但它把中间几个关键层压扁了。

真实情况至少多出三层：

1. `记忆服务层`
2. `记忆治理层`
3. `记忆存储层`

同时，最末端也不是单一数据库，而是混合存储：

1. Markdown 页面
2. JSON 索引
3. 版本快照文件
4. 审核池与治理状态文件
5. 部分结构化业务数据

因此，Cornie 记忆层更适合被理解为：

`一个领域层 + 一个治理层 + 一个混合存储层`

而不是：

`一个 memory 表`

## 5. 记忆层总体分层

## 5.1 总览

Cornie 记忆层建议正式定义为 6 层：

1. 入口层
2. API / Gateway 层
3. 记忆服务层
4. 记忆治理层
5. 记忆消费层
6. 记忆存储层

说明：

1. `入口层` 是谁来用记忆。
2. `API / Gateway 层` 是怎么进入记忆域。
3. `记忆服务层` 是记忆域的日常读写与查询核心。
4. `记忆治理层` 是长期可维护、可审计、可回滚的保障层。
5. `记忆消费层` 是模型如何装载和使用记忆。
6. `记忆存储层` 是记忆最终如何落地。

## 5.2 分层结构图

```text
入口层
├─ 人类前端
└─ 模型编排层
      ↓
API / Gateway 层
├─ 人类接口
└─ 模型工具接口
      ↓
记忆服务层
├─ Wiki 页面服务
├─ 主题索引服务
├─ 搜索与摘要服务
└─ 来源关联服务
      ↓
记忆治理层
├─ 确认流
├─ 版本与回滚
├─ 合并与归档
├─ 巡检与审计
└─ 治理候选池
      ↓
记忆消费层
├─ 摘要装载
├─ 上下文注入
├─ 只读补查
└─ 选择性使用
      ↓
记忆存储层
├─ Markdown 页面
├─ JSON 索引
├─ 版本快照
├─ 治理状态文件
└─ 结构化存储
```

## 6. 各层职责定义

## 6.1 入口层

入口层只有两类调用者：

1. `人类`
2. `模型`

### 人类入口

人类入口负责：

1. 查看记忆
2. 编辑记忆
3. 回看记忆
4. 在必要时确认高风险操作

### 模型入口

模型入口负责：

1. 读取记忆摘要
2. 按需补查详情
3. 提议写入或修改
4. 触发需要策略判断的动作

这一层的重要原则是：

`模型和人类都能进入记忆域，但进入后不直接碰底层存储。`

## 6.2 API / Gateway 层

这一层是记忆域的统一入口。

当前架构中，它主要承接两类接口：

1. 人类接口
2. 模型工具接口

### 主要职责

1. 统一参数入口
2. 基础校验
3. 权限或策略前置判断
4. 将调用分发到服务层或治理层

### 为什么不能省掉

如果没有这一层：

1. 前端会直接耦合记忆内部结构
2. 模型工具会直接耦合底层服务实现
3. 未来抽脚手架时会很难脱业务

## 6.3 记忆服务层

这是记忆域的日常核心层。

它不负责最终治理裁决，也不负责最终落盘细节，而负责：

1. 页面 CRUD
2. 页面摘要维护
3. 别名维护
4. 页面关联维护
5. 主题索引维护
6. 搜索与查询
7. 来源引用补链

### 当前代码对应

这一层已经在仓库中有较明确的实现痕迹，例如：

1. `electron/backend/memory-wiki/service.js`
2. `electron/backend/memory/service.js`
3. `electron/backend/memory/search.js`
4. `electron/backend/memory/summary.js`
5. `electron/backend/memory-wiki/topicIndex.js`

### 这一层的定位

可以把它理解为：

`记忆领域服务层`

它负责把“长期记忆是怎么工作的”变成可调用的稳定能力。

## 6.4 记忆治理层

长期记忆和普通业务数据最大的区别在于：

`它不是只要能存就够了，而是必须长期可维护、可追溯、可修正。`

所以治理层是 Cornie 记忆架构里非常关键的一层。

### 治理层负责的事情

1. 高风险修改确认
2. 页面版本管理
3. 页面回滚
4. 页面合并
5. 页面归档与恢复
6. 巡检
7. 审计
8. 治理候选沉淀

### 当前代码对应

这一层在仓库中也已经有明确骨架，例如：

1. `electron/backend/memory-wiki/versionStore.js`
2. `electron/backend/memory-wiki/governanceStore.js`
3. `electron/backend/memory-wiki/inspector.js`
4. `electron/backend/memory-wiki/audit.js`

### 这一层的意义

没有治理层，记忆系统就只是“能写进去”；
有了治理层，记忆系统才开始变成“可长期使用的基础设施”。

## 6.5 记忆消费层

这一层很容易被忽略，但对 Agent 系统非常关键。

因为“把记忆存起来”和“让模型真正用起来”是两回事。

消费层负责：

1. 相关摘要装载
2. 上下文控长
3. 按需补查
4. 选择性注入
5. 避免恐怖谷式过度记忆使用

### 当前代码对应

这一层当前已有明显实现痕迹，例如：

1. `electron/backend/agent/wikiContext.js`
2. `electron/backend/memory/summary.js`

### 这一层的作用

它把记忆系统从“存储系统”推进成“模型可消费系统”。

## 6.6 记忆存储层

记忆存储层是最终落地层。

当前 Cornie 记忆层不是单一数据库方案，而是：

`混合存储方案`

### 当前主要存储形态

1. `Markdown 页面`
   用于承载 Wiki 页面正文和可读内容。

2. `JSON 索引`
   用于承载页面索引、主题索引、关键词索引、治理队列等。

3. `版本快照文件`
   用于承载页面历史版本和回滚依据。

4. `治理状态文件`
   用于承载审核池、候选池、待处理状态等。

5. `结构化存储`
   用于部分业务记录和辅助数据。

### 为什么不做成单库

因为 Cornie 当前记忆系统追求的是：

1. 人类可读
2. 人类可改
3. 模型可读
4. 版本可追
5. 文件可迁移

单纯的黑盒数据库不利于实现这些目标。

## 7. 记忆层核心对象

## 7.1 Wiki 页面

这是记忆层的一等公民。

它至少承载：

1. 页面标识
2. 标题与 slug
3. 摘要
4. 别名
5. 正文
6. 状态
7. 重要性
8. 来源引用
9. 相关页面
10. 更新时间

## 7.2 主题索引

主题索引不是记忆正文，而是定位系统。

它用于建立：

1. 关键词
2. 别名
3. 日期关联
4. 聊天来源关联
5. 观察来源关联
6. 页面关联

## 7.3 来源引用

来源引用用于回答：

`这条长期记忆是从哪里来的。`

当前主要来源包括：

1. 聊天记录
2. 观察日志
3. 其他记忆页

## 7.4 页面版本

页面版本用于回答：

1. 这页以前长什么样
2. 什么时候改过
3. 改坏了能不能回去

## 7.5 治理候选

治理候选用于回答：

1. 哪些页面疑似重复
2. 哪些内容疑似该归档
3. 哪些状态需要进一步审阅

## 8. 记忆层数据流

## 8.1 写入流

一个典型写入流如下：

```text
人类 / 模型提出写入请求
-> API / Gateway 接收请求
-> 服务层构造页面或修改提案
-> 治理层判断是否高风险
-> 如需确认则进入确认或待处理
-> 如可执行则进入存储层写入
-> 版本层生成快照
-> 索引层更新主题与来源关联
```

## 8.2 读取流

一个典型读取流如下：

```text
人类 / 模型提出读取请求
-> API / Gateway 接收请求
-> 服务层读取页面、摘要或索引
-> 如需补充来源或关联则继续补查
-> 返回适合调用方的视图
```

## 8.3 模型消费流

一个典型模型消费流如下：

```text
编排层准备上下文
-> 读取相关记忆摘要
-> 注入主 prompt
-> 如摘要不足则调用只读补查
-> 模型选择性使用
-> 如需长期写入则生成写入提议
-> 交回治理层决定
```

## 10. 这套记忆层为什么可复用

Cornie 现在的记忆层之所以有脚手架价值，是因为它已经天然拆成了可复用模块。

### 可复用的部分

1. Wiki 页面模型
2. 主题索引模型
3. 来源引用机制
4. 版本与回滚机制
5. 治理候选池
6. 审计与巡检机制
7. 上下文摘要装载机制

### 与业务强绑定的部分

1. 观察日志作为来源域
2. 聊天记录作为来源域
3. Cornie 的口吻和陪伴型使用方式
4. 具体的人类前端交互方式

### 脚手架抽象后的可能形态

如果未来抽脚手架，可以把它拆成：

1. `memory-core`
   页面、索引、来源、版本、存储。

2. `memory-governance`
   确认、合并、归档、巡检、审计。

3. `memory-consumption`
   摘要装载、只读补查、上下文注入。

4. `memory-adapters`
   聊天适配器、观察适配器、业务来源适配器。

## 11. 抽脚手架时的边界建议

如果未来要把记忆层做成可复用脚手架，建议边界如下：

## 11.1 属于脚手架核心的部分

1. 页面模型
2. 索引模型
3. 来源引用模型
4. 版本模型
5. 存储协议
6. 治理协议
7. 摘要装载协议

## 11.2 属于业务适配层的部分

1. 来源类型定义
2. 页面类型定义
3. 人类前端交互样式
4. 确认流表达方式
5. 模型提示词与产品口吻

## 11.3 不建议硬编码进脚手架核心的部分

1. Cornie 专属命名
2. 具体 UI 入口
3. 观察日志和聊天记录的业务细节
4. DeepSeek 专属编排细节

## 12. 对当前架构判断的最终回答

如果你问：

`我们的架构是不是前端-api-记忆-数据库？`

最简回答是：

`可以先这么理解，但真正准确的说法应该是：前端 / 模型 -> 记忆 API -> 记忆服务 -> 记忆治理 -> 记忆存储 -> 文件系统 / 结构化存储。`

如果再抽象一步：

`Cornie 的记忆层已经不是一个“记忆模块”，而是一套具备读写、治理、消费、追溯和存储分层的长期记忆架构。`

## 13. 最终结论

Cornie 当前的记忆层已经具备明显的脚手架潜力。

它的本质不是：

1. 一张 memory 表
2. 一份长文档
3. 一个单点服务

而是：

1. 一个以 Wiki 页面为主载体的长期记忆核心
2. 一个以版本、索引、来源、治理为支撑的可维护系统
3. 一个可同时服务人类与模型的双入口架构

一句话总结：

`Cornie 的记忆层已经自然长成了一套“可读、可写、可治理、可消费”的长期记忆架构，这正是它能够被抽成脚手架的根本原因。`
