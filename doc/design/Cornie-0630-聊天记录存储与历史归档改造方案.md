# Cornie-0630-聊天记录存储与历史归档改造方案

## 1. 背景

当前 Cornie 的聊天记录已经统一存储在本地数据库中，按 `date` 维度组织，并通过 `/api/chatlogs` 与 `/api/chatlogs/:date` 提供查询能力。  
本轮排查确认，“无法查看过往聊天记录”并非数据未存储，而是聊天主界面没有完整接入历史记录浏览入口，导致能力存在但未真正开放。

本方案的目标有两个：

1. 明确当前聊天记录存储现状与风险边界。
2. 给出后续可持续扩展的聊天记录归档与存储改造路径。

---

## 2. 当前实现现状

### 2.1 当前数据结构

聊天记录目前保存在 `conversations` 表中，核心字段包括：

- `id`
- `date`
- `role`
- `content`
- `created_at`

并已建立索引：

- `idx_conversations_date_created_at on conversations(date, created_at)`

这意味着当前已经具备：

- 按日查看聊天记录
- 按月列出有聊天的日期
- 按时间顺序回放某一天的聊天内容

### 2.2 当前技术实现特点

当前数据库层基于 `sql.js`：

- 启动时将整个数据库文件加载进内存
- 每次写入后重新 `export` 整库并写回磁盘

因此当前方案的优点是：

- 本地单文件，部署简单
- 无需外部数据库服务
- 对中小体量的文本数据足够稳定

但它的限制也很明确：

- 数据库越大，启动加载越重
- 每次写入都会触发整库序列化
- 聊天、记账、待办、日程、观察、记忆 wiki 共用一库时，长期会放大写放大问题

---

## 3. 是否适合把全部聊天都存进 SQLite

结论：适合，但要区分“SQLite 方案”和“当前 sql.js 实现”。

### 3.1 SQLite 本身适合

如果聊天记录主要是纯文本：

- 每日几十到几百条消息
- 累积数万到数十万条消息
- 需要本地查询、分页、按日归档、按关键词检索

那么 SQLite 是非常合适的本地存储方案。

它不会因为“聊天记录按天长期积累”就自然炸掉。

### 3.2 当前实现不适合无限膨胀

真正的风险不在 SQLite，而在当前 `sql.js` 的整库内存加载与整库落盘模式。

这意味着：

- 短期和中期完全可用
- 长期不应无限堆积而不治理
- 若未来聊天、观察日志、wiki 页面快速增长，性能瓶颈会先出现在启动和写入延迟上

---

## 4. 本轮已修复问题

本轮已完成以下修复：

1. 聊天主界面新增“翻看以前聊天”入口。
2. 将聊天模块接成三段式视图：
   - 当前聊天
   - 聊天记录列表
   - 单日聊天详情
3. 聊天历史页支持按月份查看日期列表，并可进入某一天的完整聊天详情页。

这意味着当前用户已经可以查看历史聊天，而不是只能看到当天对话。

---

## 5. 推荐的后续改造路径

### 5.1 第一阶段：保持 SQLite，不立即拆库

本阶段建议继续沿用本地 SQLite 作为聊天记录主存储，不引入新型存储系统。

原因：

- 当前主要问题不是数据库类型错误，而是产品入口和浏览体验不足
- 聊天记录仍以纯文本为主，体量可控
- 现阶段优先级更高的是功能闭环与体验完善

本阶段补强项：

- 聊天记录列表支持“全部月份 / 最近30天 / 指定月份”
- 聊天记录支持关键词检索
- 单日聊天记录支持长列表懒加载
- 聊天记录页增加“跳转到当天主聊天”能力

### 5.2 第二阶段：将数据库驱动从 `sql.js` 升级为 `better-sqlite3`

这是后续最值得做的一步。

升级目标：

- 保留 SQLite 作为本地单文件数据库
- 改为原生本地驱动读写
- 避免整库加载到内存
- 避免每次写入都整库导出

升级后的收益：

- 启动更稳
- 写入更快
- 长期聊天记录增长后仍可承受
- 后续做关键词搜索、分页、统计时更从容

### 5.3 第三阶段：增加聊天归档治理能力

聊天记录不建议删，但可以做“展示归档”与“技术归档”。

建议分两层：

#### 展示归档

面向用户体验：

- 首页默认只展示今天
- 历史页展示最近记录和月份入口
- 很久以前的聊天通过月份或搜索进入

#### 技术归档

面向系统性能：

- 仍存同一数据库
- 通过索引和分页减少一次性读取量
- 对极长单日消息按页拉取
- 观察日志、长期记忆、wiki 派生数据不和聊天展示强耦合

---

## 6. 推荐的数据边界原则

### 6.1 聊天原文和派生记忆分层

聊天记录应保留为原始事实流。  
观察日志、长期记忆、wiki 页面应视为从聊天中提炼出来的派生层。

不要让 prompt 每轮都带上整天甚至所有历史聊天全文。

推荐方式：

- 聊天原文：存 SQLite，供回看与索引
- 观察日志：按需记录事实片段
- 长期记忆 wiki：保存稳定偏好、关系、事件脉络
- 模型侧按需通过工具检索，而不是全量塞 prompt

### 6.2 不要把多媒体直接塞进聊天表

如果未来支持图片、音频、文件：

- 不要把大 blob 直接存进 `conversations`
- 应只保存元数据、路径、引用 id

否则数据库体积会迅速变重。

### 6.3 单日消息视图必须分页化

虽然当前可先全量展示，但中后期应支持：

- 单日消息分页
- 首屏只拉最近一段
- 向上滚动继续加载更早消息

否则超长日期会拖慢渲染。

---

## 7. 建议的下一步实施顺序

### P1

- 补聊天历史页的月份切换提示与空状态提示
- 增加“全部月份”或“最近历史”视角
- 增加聊天记录搜索入口

### P2

- 将 `sql.js` 替换为 `better-sqlite3`
- 保持现有 API 协议不变，仅替换底层存储实现

### P3

- 为聊天记录增加分页查询接口
- 增加按关键词检索日期和消息片段能力
- 增加聊天记录导出能力

---

## 8. 最终结论

聊天记录全部存 SQLite，这个方向本身没有问题。  
当前真正需要警惕的不是“会不会炸库”，而是：

1. 现阶段历史浏览入口是否完整。
2. 后续是否继续沿用 `sql.js` 的整库内存模式。
3. 是否把原始聊天、观察日志、长期记忆、wiki 页面分层治理清楚。

因此当前建议是：

- 短期继续全量存 SQLite
- 中期切换到 `better-sqlite3`
- 长期通过分页、检索、归档视图做可持续治理

这样既能保住完整历史，又不会让系统越跑越沉。
