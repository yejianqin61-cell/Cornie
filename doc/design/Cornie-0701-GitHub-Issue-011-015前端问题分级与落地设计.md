## 4. 当前代码现状判断

结合当前仓库实现，本组 issue 实际落点如下：

### 4.1 记账页

当前账本与类目已经不是完全不可用，但“记一笔的主流程”和“补类目”之间仍不够顺滑。  
用户的真实诉求不是“要一个类目管理后台”，而是：

- 正在记账时发现没有合适类目
- 能马上补一个
- 补完后不丢当前输入
- 继续把这笔账记完

所以 `#11` 本质上不是“缺一个页面”，而是“缺一个就地闭环”。

### 4.2 收支页

`#12` 说明用户需要“日历日期筛选”和“图表/流水联动”保持一致。  
`#13` 说明当前趋势图虽然有图形，但不具备足够明确的坐标语义，导致用户读不出“时间-金额”的关系。

也就是说，收支页的问题已经不再是“有没有图”，而是“图和筛选是否承担了真实信息表达职责”。

### 4.3 日程页

`#14` 不是后端能力问题，而是布局密度问题。  
当前页面上方工具区承担了：

- 当前筛选日期说明
- 返回今天
- 清除筛选
- 新增安排入口
- 展开式新增表单

这些内容如果全部拆成上下独立卡片，会让真正重要的“日程列表”被往下挤。

### 4.4 日记页

`#15` 是典型的“模型输出已变 richer，但前端仍按纯文本渲染”的错位问题。  
当前用户看到的是模型原始 Markdown 标记，而不是可阅读的 Cornie 日记成品。

这类问题修复收益非常高，因为：

- 成本相对可控
- 直接影响用户对“陪伴感”的主观体验
- 修好后能立即改善成品感

## 5. 问题分类

本组问题可以分成四类：

### 5.1 功能闭环缺口

- `#11` 记账页新建类目入口与回流闭环

### 5.2 交互联动与信息一致性

- `#12` 日历选日后图表与流水同步过滤

### 5.3 数据可视化表达不足

- `#13` 趋势图坐标语义不明确

### 5.4 页面布局与阅读体验

- `#14` 日程页顶部密度过高
- `#15` Cornie 日记未进行 Markdown 渲染

## 6. 优先级排序

### 6.1 P0

应优先处理：

1. `#11` 记账页补类目闭环
2. `#15` Cornie 日记 Markdown 渲染

原因：

- 这两项都直接影响普通用户是否能顺畅完成主要任务
- 一个影响“记账能否继续做完”
- 一个影响“日记内容是否能正常阅读”

### 6.2 P1

本轮前端收口阶段应继续处理：

1. `#14` 日程页顶部工具区压缩
2. `#13` 收支趋势图语义增强

原因：

- 它们不会导致功能完全失效
- 但会持续损耗页面可读性与产品完成度

### 6.3 基线约束

`#12` 已关闭，但后续改动必须保持以下行为不回退：

1. 日历点选某一天后，饼图只看当天
2. 流水列表只看当天
3. 日期取消后，图表和流水恢复总览态

## 7. 分问题设计方案

## 7.1 Issue #11 记账页类目创建入口与回流闭环

### 7.1.1 问题本质

用户不是来管理“系统分类树”的，而是来“快速记下一笔钱”。  
因此新增类目必须服务于当前动作，不能把用户拽进另一个复杂页面。

### 7.1.2 设计目标

账本页需要提供一个普通用户可理解的、原地完成的类目补录能力，满足：

1. 看得见入口
2. 不打断当前记账
3. 创建完成后自动选中
4. 不暴露“治理”“工具”“协议”等术语

### 7.1.3 推荐交互

推荐采用“表单内次级入口 + 轻弹层”的方式：

1. 在类目选择区域旁边提供 `新建类目`
2. 点击后打开轻量弹层
3. 弹层只保留最小字段：
   - 类目名称
   - 类目类型
4. 创建成功后自动：
   - 关闭弹层
   - 刷新类目列表
   - 选中新类目
   - 保留原表单其他已填写内容

### 7.1.4 错误提示要求

1. 同名类目给出友好提示
2. 不直接抛英文原始错误
3. 若创建失败，当前记账草稿不得丢失

### 7.1.5 验收口径

满足以下几点可视为完成：

1. 用户在账本页内可直接补新类目
2. 新类目创建后当前记账流程不中断
3. 无需跳转高级页面

---

## 7.2 Issue #12 收支页按日联动基线

### 7.2.1 问题本质

用户点击日历中的某一天，本质是在表达：

- “我现在想看这一天”

一旦页面只有部分区域响应这个筛选，用户就会认为页面逻辑是错的。

### 7.2.2 设计约束

虽然该 issue 已关闭，但后续所有收支页改造必须继续保持：

1. 日期筛选是当前页面的全局筛选条件
2. 饼图、流水、统计说明共享同一筛选源
3. 清除筛选后一起恢复

### 7.2.3 后续开发时的回归点

1. 修 `#13` 图表样式时，不能破坏 `#12` 的按日联动
2. 若未来新增趋势图 hover、分页或图例切换，也不能出现“图和列表看的是不同时间范围”

---

## 7.3 Issue #13 收支趋势图坐标语义增强

### 7.3.1 问题本质

当前用户吐槽的核心不是“图不好看”，而是“图不说人话”。  
趋势图如果没有明显坐标语义，就无法承担：

1. 横轴表达时间
2. 纵轴表达金额
3. 折线表达趋势变化

### 7.3.2 设计目标

把现有趋势图从“装饰性曲线”升级为“可读的趋势图表”，至少做到：

1. 有明确的 X 轴和 Y 轴
2. 曲线处于正常第一象限表达
3. 数值刻度与日期刻度可理解
4. 收入/支出含义清楚

### 7.3.3 推荐实现方向

1. X 轴显示日期或时间段
2. Y 轴显示金额刻度
3. 视图中保留零基线或最小合理基线
4. 图例明确区分收入与支出
5. 空数据时不画误导性折线，而是显示空态说明

### 7.3.4 普通用户表达要求

不要把图表做成分析后台味道太重的样子。  
它应该像“看一眼就知道最近花钱高低起伏”，而不是像数据中台。

### 7.3.5 验收口径

1. 用户一眼能看出横轴是时间、纵轴是金额
2. 收入/支出至少有一种稳定区分方式
3. 在按日筛选、清除筛选后图表语义保持一致

---

## 7.4 Issue #14 日程页顶部工具栏压缩与卡片合并

### 7.4.1 问题本质

不是功能过多，而是布局组织方式不对。  
顶部工具区应该是“轻工具栏”，而不是“说明卡片堆叠区”。

### 7.4.2 设计目标

让用户进入日程页后，第一眼尽快看到：

1. 正在查看哪一天
2. 如何回到今天
3. 如何新增安排
4. 下面有哪些安排

### 7.4.3 推荐交互结构

建议把顶部两块合并为一条工具栏式区域：

1. 左侧：当前日期状态
2. 中部或右侧：`回到今天`、`清除筛选`
3. 右侧主按钮：`新增安排`

新增表单默认折叠，只在点击后展开到工具栏下方。

### 7.4.4 视觉要求

1. 顶部区域高度明显压缩
2. 动作按钮比说明文字更突出
3. 不再出现两张上下连排的大卡片

### 7.4.5 验收口径

1. 顶部工具区与新增入口可在一屏内自然共存
2. 日程列表上移，首屏可见内容更多
3. 页面不再给人“信息堆叠”的感觉

## 7.5 Issue #15 Cornie 日记 Markdown 安全渲染

### 7.5.1 问题本质

Cornie 日记已经是偏文学化的内容成品。  
如果前端仍按原始文本显示，用户看到的是“模型标记语言”，不是“日记”。

### 7.5.2 设计目标

在保证安全与稳定的前提下，把日记内容渲染为真正可阅读的文本版式。

### 7.5.3 推荐支持范围

本期建议支持安全子集：

1. 标题
2. 段落
3. 粗体
4. 斜体
5. 引用
6. 无序列表
7. 合理换行

### 7.5.4 不建议开放的内容

1. 原始 HTML 直通
2. 脚本相关内容
3. 高风险富文本注入

### 7.5.5 容错要求

1. Markdown 不完整时也能尽量正常显示
2. 不能因为单段格式异常导致整页空白
3. 截断文本、半成品文本也要能降级展示

### 7.5.6 视觉要求

1. 标题层级要清楚
2. 行高要舒展
3. 不要做成技术博客风
4. 整体气质要更像“被写下来的陪伴记录”

### 7.5.7 验收口径

1. `##`、`**` 等标记不再裸露给用户
2. 日记长文可稳定渲染
3. 空态和异常态有温和提示

## 10. 最终结论

这组 GitHub issue 的共同点是：

- 已经不是“后端没有能力”
- 也不是“页面完全不可用”
- 而是产品进入到“要把真实用户体验补完整”的阶段

其中最关键的原则有两条：

1. 不让普通用户被迫进入复杂治理界面
2. 让页面中的图、文、表单都真正服务于用户的日常动作

因此，本轮落地方向应当明确为：

- 以普通用户主流程为中心补闭环
- 以可读、可用、可持续操作为标准做前端收口
