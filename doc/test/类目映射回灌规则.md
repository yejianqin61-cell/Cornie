# 类目映射回灌规则

## 1. 文档目的

本规则用于约束“发现样本之后应该怎么处理”，避免样本只被记录，不进入实际修复闭环。

## 2. 回灌入口分类

### 2.1 `prompt`

适用场景：

- 模型理解方向明显偏了
- 提示词没有强调“优先复用现有类目”
- 应追问还是应确认的边界不清晰

典型标签：

- `should_map_but_ask`
- `wrong_domain_bias`

### 2.2 `rule`

适用场景：

- 本地候选打分偏弱或偏强
- 通用类目词（如“提醒”“其他”）命中权重不合理
- 拒绝新增后的推荐类目策略不稳定

典型标签：

- `should_map_but_new`
- `low_signal_generic_match`
- `duplicate_category_proposal`

### 2.3 `test`

适用场景：

- 问题已经明确复现
- 需要防止未来回归
- 当前问题能稳定在 stub 或本地脚本中重放

规则：

- `P0` 样本必须补 `verify-category-flow` 或同等级自动化保护
- `P1` 样本至少补到文档验收清单或专项回归文档

### 2.4 `tool`

适用场景：

- 只读补查工具返回信息不够
- 工具结果缺字段，导致上层无法更稳判断
- 日志结构不足，无法沉淀样本

### 2.5 `confirm`

适用场景：

- 新增类目确认与已有类目推荐之间的切换不自然
- 拒绝新增后的收口策略不清晰
- 映射确认与新增确认文案/行为不一致

## 3. 样本处理流程

1. 记录样本到台账
2. 先判断问题主归因：`prompt / rule / tool / confirm`
3. 判断是否需要补自动化回归
4. 修复后回填台账状态
5. 若问题仍未解决，保留样本并追加新的观察记录

## 4. 优先级规则

- `P0`
  - 会导致错误写入、错误类目落库、错误恢复执行
  - 必须补自动化回归
- `P1`
  - 不一定写错库，但会明显影响用户体验和命中率
  - 应尽快补回归或专项验证
- `P2`
  - 偏资产组织、观测质量、文档化补充

## 5. 与开发任务的衔接

- 如果样本指向现有 task 范围，优先回灌到当前 task
- 如果样本揭示新的系统性问题，再拆新 task
- 不要为了“台账好看”把尚未真正解决的问题标记为已收口

## 6. 当前首批回灌建议

| 标签 | 优先回灌入口 | 建议动作 |
| --- | --- | --- |
| should_map_but_new | rule + test | 调整现有候选打分与新增确认阈值，并补回归 |
| should_map_but_ask | prompt + test | 强化补查后继续决策约束，避免过早 ask_back |
| duplicate_category_proposal | rule + prompt | 强化已有类目复用优先级，并保留 reused_existing 审计 |
| low_signal_generic_match | rule | 降低“提醒/其他/默认”等通用类目直接命中权重 |

## 7. 最小验收标准

以下条件同时满足，才算本轮样本已真正回灌：

- 台账有记录
- 有明确归因
- 有对应修复动作
- 有回归或验证证据
