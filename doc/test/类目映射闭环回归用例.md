# 类目映射闭环回归用例

## 1. 文档目的

用于回归 `7.2 类目快照注入与映射闭环` 的核心链路，覆盖：

- 类目快照注入
- 现有类目直接命中
- 只读补查后命中
- 新增类目确认
- 已有类目复用
- 拒绝新增后的收口
- ask_back 追问降级
- 三域补查轮控统一

本文档适合作为：

- 每次相关提交后的手工回归基线
- `verify-category-flow` 自动化脚本的用例来源

## 2. 回归范围

### 2.1 业务域

- `ledger`
- `todo`
- `schedule`

### 2.2 主链路节点

- prompt 中包含真实类目摘要
- Tool Policy 正确分流 `allow / confirm / ask_back`
- 确认流可持久化、批准、拒绝、恢复执行
- 重复类目不重复创建
- 审计日志可追踪关键决策

### 2.3 三域覆盖状态

当前三域最小自动化覆盖状态如下：

| 域 | 已覆盖主链路 | 已覆盖确认恢复 | 已覆盖拒绝收口 | 已覆盖补查轮控 |
| --- | --- | --- | --- | --- |
| `ledger` | 是 | 是 | 是 | 是 |
| `todo` | 是 | 是 | 是 | 是 |
| `schedule` | 是 | 是 | 是 | 是 |

## 3. 回归前准备

### 3.1 基础数据

建议准备一套稳定初始数据：

- 收支类目：
  - 收入：`工资`、`红包`
  - 支出：`餐饮`、`交通`、`购物`、`娱乐`
- 待办类目：
  - `待办`、`学习`、`生活`
- 日程类目：
  - `日程`、`会议`、`提醒`

### 3.2 环境要求

- 使用独立测试库或可重置本地数据库
- 确认后端已注册 `ledger` / `todo` / `schedule` / `*_category` 相关工具
- 能查看控制台中的 `[category-audit]` 日志

### 3.3 结果检查维度

每条用例至少检查：

- 策略层决策
- 工具调用结果
- 前端状态
- 落库结果
- 审计日志
- 最终回复

#### TC-032 待办与日程域只读补查轮控统一

| 字段 | 内容 |
| --- | --- |
| 编号 | `TC-032` |
| 域 | `todo / schedule / ledger` |
| 优先级 | `P0` |
| 类型 | 策略统一 / 补查轮控 |
| 验证目标 | 三个业务域共享一致的“单域一次只读补查”规则 |
| 期望结果 | 同一域第二次补查被阻止；其他域首次补查不受影响 |
| 期望日志 | 出现带 `domain` 的只读补查上下文；超限时走 `category_mapping_ask_back` |
| 期望脚本 | `verify-category-flow` 中存在待办和日程轮控专项 case |

## 4.3 冒烟用例集合

每次提交前建议至少执行以下 6 条：

1. `TC-001` 支出命中已有类目
2. `TC-003` 待办命中已有类目
3. `TC-004` 日程命中已有类目
4. `TC-005` 支出申请新增类目并确认通过
5. `TC-008` 用户拒绝新增类目
6. `TC-010` 类目名过于模糊，降级追问

## 5. 自动化优先级标注

| 用例 | 自动化优先级 | 说明 |
| --- | --- | --- |
| `TC-001` | P0 | 最基础命中链路，必须自动化 |
| `TC-003` | P0 | 待办主链路必须纳入冒烟保护 |
| `TC-004` | P0 | 日程主链路必须纳入冒烟保护 |
| `TC-005` | P0 | 新增确认后恢复执行是高风险链路 |
| `TC-008` | P0 | 拒绝后不可误落库 |
| `TC-009` | P0 | 重复防护容易回归 |
| `TC-010` | P0 | ask_back 兜底很关键 |
| `TC-012` | P1 | 补查协同可后补自动化 |
| `TC-032` | P0 | 三域补查轮控统一是后续扩展基础 |

## 6. 通过标准

- P0 用例全部通过
- 无重复脏类目产生
- 拒绝新增后无误写库
- 最终回复与真实执行结果一致
- 审计日志能支持定位链路停留位置
