## 2. 复评范围与依据

本次复评不沿用旧口径，而是基于当前仓库真实状态重新判断，主要依据包括：

1. `electron/backend/` 当前已存在的后端实现文件。
2. `src/renderer/` 当前已存在的前端页面与组件。
3. `package.json` 当前可执行脚本。
4. `doc/acceptance/7.1-7.3` 当前阶段验收文档。
5. 当前仓库根目录的实际工程状态。

本次复评重点回答四件事：

1. 现在到底做到了哪里。
2. 哪些模块已完成，哪些只是设计完成。
3. 当前最明显的缺陷和风险是什么。
4. 接下来最合理的行动顺序是什么。

本次复评补充采用以下刚性原则，后续开发、验收与发布判断都应以此为准：

1. `Ollama` 以及一切本地模型方案全部抛弃，产品正式口径永远只保留 `DeepSeek-only`。
2. 前端人类接口不以“最小闭环”为目标，而以“人类接口全覆盖”为目标；凡模型正式可调用能力，人类都应有对应前端入口或等价治理页面。
3. 发布治理不只覆盖首次启动。只要当前未配置有效 `DeepSeek API Key`，前端就应持续进入引导 / 拦截态，并以平实、易懂、偏铃湾口吻的文案提示用户，禁止把后端编译、日志、调试语义直接暴露给用户。
4. 前端测试脚手架必须正式搭建完成，并将前端页面、组件测试覆盖率目标明确收口到 `95% 以上`。
5. 上述四条属于后续阶段的硬验收线，而不是“尽量做到”的优化项；只要任一项未收口，本项目就不能被判断为前端产品化完成。

## 3. 本次复评结论摘要

当前项目的真实状态可以概括为：

`后端代理骨架已基本成型，7.1 / 7.2 / 7.3 后端范围已完成，但前端、人类接口全覆盖、桌面端主程序收口、DeepSeek-only 彻底收口、发布治理、前端测试体系仍明显未完成。`

更直白一点说：

- 后端比前端成熟很多。
- 设计文档比最终产品状态走得更前。
- 测试体系已经从“几条专项脚本”升级成了结构化分层测试。
- 本项目后续模型方案必须收敛为 `DeepSeek-only`，不再保留 Ollama 或其他本地模型正式方案。
- 前端后续目标不是补一个最小可演示壳子，而是要把人类可操作接口补到与模型工具集正式对齐，并做到“模型能做的正式能力，人类也能在前端完成”。
- 发布治理必须改成“只要没填有效 DeepSeek Key 就持续引导”的产品机制，而不是一次性提示。
- 前端测试目标不是“有 smoke case 就行”，而是搭起正式测试脚手架并把页面、组件覆盖率推到 `95%+`。
- 但项目仍不能简单定义为“可发布产品”，更适合定义为：

`后端主链路已成型、前端与发布层明显滞后的 Alpha 工程版本`

## 6. 未完成或明显滞后的模块

### 6.1 前端人类接口集远未与工具集全等

当前前端实际文件主要集中在：

- `App.vue`
- `ChatHistory.vue`
- `CornieComposer.vue`
- `ConfirmCard.vue`
- `AskBackBubble.vue`
- `ToolResultPanel.vue`

当前前端已能覆盖的主要是：

- 日记本
- 聊天记录按天翻阅
- 基础聊天确认卡片 / 追问 / 工具结果展示
- Cornie 形象拼装编辑器

但尚未看到正式落地的人类前端入口：

- 记账记录完整 CRUD 页面
- 记账类目管理页
- 待办完整生命周期页
- 日程完整生命周期页
- Memory Wiki 页面列表与详情页
- Memory Wiki 版本历史页
- Topic Index 管理页
- 记忆治理待审核工作台
- 巡检结果页

判断：

`模型工具集 = 人类接口集 = 前端可达能力集` 这个目标在后端方向推进很多，但在前端侧仍明显未达成。

补充原则：

- 后续前端目标不能只做“最小闭环”。
- 必须以“前端对人类接口全覆盖”为正式目标推进。
- 也就是：凡是模型可调用的正式工具，用户都应拥有对应的人类操作入口或等价页面能力。
- 该原则不只覆盖“查看”和“提交”，还必须覆盖新增、编辑、删除、审批、回滚、归档、恢复、重试、巡检处理、版本查看等完整生命周期动作。
- 对于模型正式具备、且会影响真实数据或记忆治理结果的能力，前端不能再以“暂时先不给人类入口”作为长期方案。
- 因此前端验收标准不能只看“主链路能不能走通”，还要看“是否仍有模型可做但人类前端做不了的正式动作”。
- 这里的“全覆盖”不是指只做一个总入口，而是要求前端对人类提供可完成业务闭环的正式操作面，至少覆盖列表、详情、创建、编辑、删除、归档、恢复、审批、回滚、巡检处理、失败重试、结果查看等动作。
- 对账本、类目、待办、日程、观察日志、Cornie 日记、长期记忆 Wiki、Topic Index、确认流、聊天记录翻阅等所有正式业务域，都应按上述原则补齐人类前端入口。

### 6.2 桌面端主程序存在高风险异常状态

当前 `electron/main.cjs` 的实际内容不是正常的 Electron 主进程启动逻辑，而是调试脚本：

- 读取 `electron`
- 写入 `electron-debug.txt`
- `process.exit(0)`

这意味着：

- 当前仓库主程序入口很可能不是可运行发布态。
- 即使后端和前端代码存在，桌面应用主启动链路也处于异常状态。

这是本次复评中最需要单独点名的高优先级问题之一。

### 6.3 “永远只支持 DeepSeek”的设计目标与代码现状尚未完全一致

虽然当前正式配置已走 DeepSeek：

- `electron/backend/model/config.js`
- `electron/backend/model/deepseek/client.js`

但仓库中仍存在：

- `electron/backend/ollama/client.js`

这代表：

- 主链路已经切到 DeepSeek。
- 但代码库仍保留旧本地模型遗留模块。

这不一定马上造成运行问题，但会造成：

- 设计口径与代码口径不完全一致
- 后续维护者误判支持边界
- 发布前配置和文档口径不够干净

正式收口原则：

- `ollama` 以及本地模型方案应全部抛弃，不再保留“备用”“兼容层”“未来可能切回”的产品口径。
- 后续永远只保留 `DeepSeek-only`。
- 不再保留“以后也许还能切回本地模型”的产品口径。
- 若有历史遗留代码，只允许作为待删除遗留项，不应再被视为正式能力。
- 前端、设置页、发布文案、帮助提示中，也不应继续出现“支持本地模型”“可切换本地模型”的产品表达。

### 6.4 发布治理仍基本未展开

虽然前端里已经出现了 DeepSeek API Key 缺失提示，但当前仍缺少系统化发布治理：

- 非首次启动场景下的持续配置引导
- 未配置 API Key 时的独立引导页
- 首次启动引导
- API Key 配置流程
- 配置持久化方案说明
- 隐私与联网提示
- 故障降级说明
- 面向普通用户的错误恢复引导

当前更像“工程师知道怎么配”，还不是“普通用户也能顺利配”。

补充原则：

- 发布治理不能只覆盖首次启动。
- 只要用户尚未填写 `DeepSeek API Key`，前端就应持续进入引导态，弹出独立引导页或拦截页，而不是只给一条工程化 banner 提示。
- 该引导页应被视为正式产品页面，而不是临时调试遮罩；其职责是帮助用户完成配置、理解为什么需要 Key、以及在失败时知道下一步怎么办。
- 这类引导属于前端用户体验层，不应混入后端编译、调试、服务日志式信息。
- 面向用户的提示文案应平实、易懂，并尽量使用铃湾 / 小铃湾自然、可爱的口吻，而不是后端错误术语直出。
- 前端展示给用户的文案、状态说明、错误引导，必须与后端编译信息、调试日志、接口堆栈彻底分层，禁止把工程内部术语直接暴露给普通用户。
- 上述机制不属于“首次安装向导”，而属于“配置缺失时始终生效的持续治理能力”。
- 这意味着发布治理要按“运行时状态拦截”设计：无论首次启动、二次启动、配置丢失、Key 失效还是用户手动清空配置，只要缺少有效 `DeepSeek API Key`，前端都应重新进入引导 / 拦截页。
- 引导页文案应优先告诉用户“现在缺什么、为什么需要、下一步点哪里”，而不是展示后端异常名词；即使底层真实报错复杂，前端也应先转译为普通用户能理解的话。

### 6.5 工程清洁度存在明显欠账

当前仓库根目录存在大量临时产物，例如：

- `tmp-task*.sqlite`
- `tmp-tools-test-*.sqlite`
- `tmp-service-test-*.sqlite`

这说明当前测试和验证虽然能跑，但测试产物清理机制不够收口，带来的问题包括：

- 仓库目录噪音大
- 容易干扰人工判断
- 发布打包和工程交接时观感较差

### 6.6 前端测试体系已启动，但距离正式验收仍明显未收口

目前 7.3 结构化测试的成熟部分仍主要集中在后端与编排链路。

前端测试脚手架已经开始搭建，且已有页面、组件、异步交互与契约回归用例，但当前仍不能判断为“前端测试体系已完成”，原因包括：

- 前端页面与组件覆盖率尚未稳定达到 `95%+`
- 关键页面状态矩阵仍未全部补齐
- Memory Wiki 治理工作台等复杂前端场景仍需持续补测
- 启动引导、配置拦截、错误恢复等产品化前端流程仍需继续扩展回归

因此当前测试进展，不应被误判为“全产品测试完成”，更不应被误判为“8.5 已经收口”。

补充目标：

- 前端测试不应只补几个 smoke case，而应正式搭建脚手架。
- 前端页面、组件测试覆盖率目标应达到 `95% 以上`。
- 后续所有核心前端页面与组件都应进入可持续回归体系。
- 覆盖目标不仅包括静态渲染，还应包括页面切换、组件交互、异步 API 调用、错误态、空态、加载态、前后端契约对齐与关键用户流程回归。
- 覆盖率目标是正式验收门槛之一，不应在执行期被弱化为“先有一点测试再说”。
- 若最终覆盖率未达到 `95%+`，则不能宣告 8.5 完成，也不能将前端测试工作描述为“已收口”。
- 该覆盖目标不是只看单一页面，而是要覆盖前端正式产品面：页面、组件、弹层、确认卡、异步状态机、配置引导页、错误恢复流、前后端契约模拟、主流程回归与关键空态分支。
- 若某些页面因“尚未做完”而缺少测试，这本身就意味着前端产品化尚未完成，不能通过缩窄统计口径来规避 `95%+` 目标。

## 7. 当前存在缺陷的模块清单

### 7.1 P0 缺陷

1. `electron/main.cjs` 当前不是正式主进程逻辑，而是调试退出脚本。
2. 前端未与 0627 / 0628 设计中的人类接口全集同步，产品面严重滞后于后端，且尚未达到“人类接口全覆盖”目标。
3. 发布与启动配置治理未收口，DeepSeek 接入仍偏工程态。
4. `DeepSeek-only` 决策尚未完成代码级彻底收口，仓库仍保留本地模型遗留模块。
5. 前端测试脚手架虽已启动建设，但页面与组件 `95%+` 覆盖目标仍未达成，不能视为已收口。
6. 未配置 `DeepSeek API Key` 时的持续引导页机制尚未形成正式产品能力。
7. 前端当前仍未达到“人类接口全覆盖”标准，存在模型侧正式能力已具备、但用户侧缺少对应操作面的产品断层。
8. 前端用户提示分层仍需持续收口，必须彻底杜绝把后端编译、日志、调试语义直接外露给普通用户。
9. 前端当前尚未证明对全部正式业务域建立了“人类可直接操作”的完整入口矩阵，仍存在以最小闭环代替正式产品面的风险。
10. 前端配置治理与提示文案仍需产品化重写，尚未形成统一的铃湾 / 小铃湾风格用户提示规范。

### 7.2 P1 缺陷

1. 旧 Ollama 客户端遗留，设计口径与代码口径未完全统一。
2. Memory Wiki 治理虽然有后端待审核池，但前端治理工作台尚未实现。
3. 工程目录中保留大量临时 sqlite 产物，测试清理机制不完善。
4. 前端没有同步建立完整高覆盖回归体系。

### 7.3 P2 缺陷

1. 文档体系很多，但产品完成状态与文档完成状态之间存在认知落差。
2. Cornie 形象拼装编辑器属于专项工具页，和当前核心产品闭环相比优先级并不高。

## 8. 下一步行动建议

### 8.1 第一优先级：恢复桌面端正式主程序链路

建议立即处理：

1. 恢复 `electron/main.cjs` 为正式主进程入口。
2. 核对 Electron 窗口创建、Express 后端启动、前端加载链路是否完整。
3. 建立最小桌面端启动验收脚本。

原因：

- 这是当前最接近“系统不能正常交付运行”的问题。
- 不先修这一层，后面继续堆前端页面意义有限。

### 8.2 第二优先级：补前端人类接口全覆盖

本项标题应调整为：

`补前端人类接口全覆盖，而不是只做最小闭环`

建议按业务价值顺序推进：

1. 记账记录页与类目管理页
2. 待办页与类目管理页
3. 日程页与类目管理页
4. Memory Wiki 列表页 / 详情页
5. 记忆治理待审核区
6. Memory Wiki 版本历史 / 回滚页
7. Topic Index 管理页
8. 巡检结果页与修复建议页
9. 全部高风险确认流的人类可见入口
10. 观察日志、Cornie 日记、长期记忆 Wiki 与 Topic Index 的人工治理入口全补齐
11. 配置中心、DeepSeek Key 引导页、失效 Key 恢复页、帮助说明页

补充要求：

- 前端范围不能只补“能用一次”的最小路径，而要对齐人类真实可操作全集。
- 也就是：模型能新增、编辑、删除、审批、回滚、归档、恢复、巡检处理的能力，人类前端都要有对应页面或操作入口。
- 若某项能力暂不适合直接开放为高频入口，也必须至少提供明确的治理页、详情页或高级操作区承接。
- 人类接口验收不应只看“能不能发起”，还要看“能不能查、能不能改、能不能撤回、能不能审、能不能追溯历史版本”。
- 前端页面规划必须与模型工具集保持全等：凡模型正式可操作对象，人类都应拥有等价可见、可控、可恢复的前端治理能力。

原因：

- 当前后端工具能力已经很多，但用户侧几乎没有对应操作面。
- 这正是当前“工程完成度高、产品完成度低”的根本原因。
- 目标必须是“人类接口全覆盖”，而不是“先凑合有几个页面”。
- 本阶段前端开发范围应明确视为产品能力补全，而不是演示层包装。

### 8.3 第三优先级：收口 DeepSeek-only 代码口径

建议处理：

1. 审计是否还有其他本地模型遗留引用。
2. 明确删除 `ollama` 遗留模块及所有本地模型方案代码。
3. 同步更新启动、配置、文档口径。
4. 禁止前端、后端、配置层再出现“本地模型可切换”的正式产品表达。
5. 同步清理帮助文档、引导文案、设置页和测试夹具中的本地模型旧口径。

原因：

- 这属于设计决策已经定下，但工程清理未做完。
- 越晚处理，后续越容易混乱。

### 8.4 第四优先级：补发布治理与用户引导

建议处理：

1. API Key 配置页面或设置入口
2. 未配置 API Key 时的独立引导页
3. 首次启动引导
4. 非首次启动但仍未配置时的持续拦截与引导
5. 网络与隐私提示
6. 配置错误时的用户可理解提示
7. 发布前默认配置策略
8. 铃湾口吻的用户提示文案规范
9. Key 缺失、Key 无效、网络失败、权限不足等场景的统一拦截页与恢复动作
10. 前端用户提示与后端真实错误的分层映射规则

补充要求：

- 引导页出现条件不是“首次启动”，而是“当前未配置有效 `DeepSeek API Key`”。
- 一旦缺少有效 Key，前端就应进入可理解、可恢复、可退出说明明确的引导态。
- 所有用户可见提示都应使用普通用户能理解的话来表达，不允许把后端编译信息、运行日志、异常堆栈直接呈现给用户。
- 前端引导文案默认应以铃湾 / 小铃湾口吻撰写，但前提是清晰、平实、低负担，而不是为了可爱牺牲可理解性。
- 前端配置页、引导页、错误页属于产品界面，不是后端控制台镜像；要明确区分“给用户看的解释”与“给开发排障看的日志”。
- 引导机制必须与运行时检测绑定，而不是只在首次安装时展示一次。

原因：

- 当前项目离“内部可用”已经不远，但离“可交给别人顺畅使用”还差这一层。
- 前端提示必须是用户语言，不应把后端错误、调试信息直接抛给用户。

### 8.5 第五优先级：搭建前端测试脚手架并补齐高覆盖率回归

建议目标：

- 前端页面、组件测试覆盖率达到 `95% 以上`

建议处理：

1. 搭建正式前端测试脚手架
2. 页面级测试
3. 组件级测试
4. 确认流 UI 回归
5. 聊天历史翻阅回归
6. 引导页与配置页回归
7. 启动流程 smoke test
8. 主要页面状态矩阵
9. 配置引导页 / 拦截页 / 恢复页矩阵
10. 页面文案不泄露后端术语的提示分层回归

补充要求：

- 前端测试脚手架需要在本阶段搭建完成，而不是只写零散测试文件。
- 覆盖对象至少包括页面、核心组件、状态切换、异步请求、错误恢复、确认流、引导页与前后端接口契约。
- `95%+` 是正式目标，不是理想目标。
- 覆盖统计口径应明确包含前端正式产品面，而不是只统计少数基础组件；若新增了正式页面，也必须同步纳入覆盖率体系。
- 对于配置引导、拦截、恢复、错误提示、权限确认等“非主功能页”，同样要进入正式回归，因为这些恰恰是发布后最常见的用户接触面。

原因：

- 当前 7.3 已把后端测试体系立住了，下一步必须把前端正式拉齐。
- 覆盖率目标应明确，不应停留在“以后再补”。
- 若前端测试脚手架与高覆盖回归没有落地，则不能判定 8.5 完成，也不能说前端进入可稳定迭代状态。

### 8.6 第六优先级：收紧测试产物与工程清洁度

建议处理：

1. 临时 sqlite 文件统一输出到临时目录
2. 测试结束自动清理
3. 补 `.gitignore`
4. 建立仓库清洁检查

原因：

- 不影响功能本身，但影响长期维护质量和团队协作体验。

## 9. 建议的下一阶段顺序

建议严格按这个顺序推进：

1. 修复 `electron/main.cjs`，恢复正式桌面端启动链路。
2. 审计并清理 DeepSeek-only 决策下的全部本地模型遗留代码。
3. 做前端人类接口全覆盖：
   - 记账
   - 待办
   - 日程
   - Memory Wiki
   - Topic Index
   - 治理待审核区
   - API Key 引导与配置治理页
   - 观察日志 / Cornie 日记 / 聊天记录翻阅与治理页
4. 实现未配置 API Key 时的持续引导页与设置引导，且文案与错误展示完全前端化、用户化。
5. 搭建前端测试脚手架，并把页面 / 组件覆盖率推到 `95%+`。
6. 补前端 / 启动链路回归体系。
7. 最后做工程清洁度收口。

## 10. 最终结论

当前项目最准确的判断不是“还差一点就能发布”，而是：

`后端主能力已基本成型，但产品层、桌面端启动层和发布层还没有收口。`

所以接下来不该继续优先扩新后端概念，而应该转入：

1. 修主程序入口
2. 清空 Ollama 与本地模型遗留，只保留 DeepSeek-only
3. 补前端人类操作面全覆盖，而不是停留在最小闭环
4. 补持续性的 API Key 引导页与发布治理，并确保用户提示语言平实易懂
5. 补前端高覆盖率回归，把前端测试脚手架和 `95%+` 覆盖率真正落地
6. 确保前端正式产品面与模型工具集保持全等，不再留下“模型能做但人类做不了”的长期断层
7. 确保所有用户可见配置与错误提示都完成前后端语义分层，以铃湾 / 小铃湾口吻做平实表达

只有这几步做完，Cornie 才会从“后端很强的工程原型”真正走向“可用的桌面产品原型”。
