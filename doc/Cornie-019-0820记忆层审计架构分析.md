## 2. 文档目的与审计口径

### 2.1 文档目的

本文档回答四个问题：

1. **当前记忆层"是谁在决定记什么"**：审计全部后端代码，统计所有由正则/关键词/规则匹配计入记忆的地方，给出精确位置清单。
2. **与设计哲学的差距**：对照"是否计入记忆由 LLM 决定、后端只执行与治理、人类把关"这一设计初衷，明确当前实现偏离点及已产生的真实损害。
3. **改造的目标架构（写入侧）**：给出"记忆提炼轮次（Memory Distillation Turn）"的目标架构草案，作为后续任务分发（task 化）的输入。
4. **改造的目标架构（读取侧）**：给出"消费侧渐进钻取架构"草案——固定小基座（画像 + 分层目录）+ 按需钻取 + 联想式层间话语 + 流式说话段（§7），与写入侧并列，共同兑现"读取/写入都由 LLM 决定"。

### 2.2 设计哲学声明（本文档的评估基准）

> **Cornie 记忆层的最高设计原则：是否载入记忆、记什么内容，只由 LLM 决定；后端负责执行与治理；人类负责最终把关。**
>
> **补充原则（V1.1 决策）**：正则匹配不是记忆决策的候选手段，**全面弃用**。当 LLM 不可用（未配置 API Key / 超时 / 协议解析失败）时，本轮**不写入任何记忆**，并在界面明确引导用户配置 DeepSeek Key——而不是委曲求全降级到正则写入。

依据：

- `doc/design/Cornie-0627-长期记忆LLM-Wiki正式设计.md §5.3`：模型提出写入或合并请求 → 策略层判定风险 → 必要时进入确认流 → 确认后才执行真正写入。
- `doc/design/Cornie-0628-记忆层总体架构设计.md §2.2`：明确"**模型工具集 = 人类接口集**"、"LLM 决定、后端执行、人类把关"。
- `doc/Cornie-018-记忆层改进计划.md` D-18 / I-18：记忆决策权必须从后端正则交还给 LLM。

**因此，本文档将"正则/关键词/硬编码规则决定记忆写入"视为设计违背（缺陷），而非可接受的实现细节。**

### 2.3 审计范围与方法

- **范围**：`electron/backend/` 下与记忆写入、记忆候选、记忆治理相关的全部模块；不含纯检索（聊天记录搜索、主题索引查询）与业务记账类目映射。
- **方法**：全量阅读 + grep 正则/关键词判定点；逐函数登记（文件、函数、行号、判定内容、风险）。
- **口径**：只登记"**会真实触发记忆写入或记忆候选入队**"的判定点；注入侧（prompt 装载）与治理侧（巡检/状态机）单独成节，明确标注不属"写入决策"，但同样存在规则化问题。

## 3. 记忆层总体架构

### 3.1 设计上的三层记忆观（目标态）

| 层 | 载体 | 定位 | 写入者（按设计） |
| --- | --- | --- | --- |
| 事实层 | 观察日志（observation_logs） | 低噪声、按需记录的事实 | LLM 提炼 |
| 关怀层 | Cornie 日记（diary_entries） | 情感视角的每日叙事 | LLM 生成 |
| 稳定层 | Memory Wiki（memory-wiki 页面） | 长期稳定的记忆、身份、人物 | LLM 提议 + 后端执行 + 人类确认 |

### 3.2 六层架构（设计态）

入口（对话/接口）→ API-Gateway（Express 路由）→ 服务层（observation / identity / memory-wiki）→ 治理层（governance / inspector / audit）→ 消费层（wikiContext 注入 / 工具）→ 存储层（SQLite + 文件式 Wiki）。

### 3.3 当前实现的数据流（实际态）

每轮对话结束后，`orchestrator.runTurn` 尾部**无条件**顺序执行 6 条记忆链路（当前工作区 `electron/backend/agent/orchestrator.js` L424-500）：

```text
对话轮次完成
  ├─ ① observation.recordConversationTurn        （正则判定 + 流水账写入）        L430
  ├─ ② enqueueObservationWikiUpgradeCandidates   （复用 4 个正则 extract → 治理入队）L442
  ├─ ③ upsertIdentityProfileFromConversation     （profile 正则链 → Wiki 页面）    L454
  ├─ ④ upsertIdentityPreferenceFromConversation  （preference 正则链 → Wiki 页面） L469
  ├─ ⑤ upsertIdentityTraitFromConversation       （trait 正则链 → Wiki 页面）      L480
  └─ ⑥ upsertIdentityPersonFromConversation      （person 正则链 → Wiki 页面）     L491
```

**关键事实**：这条链的每一个"是否记录、记录什么"判定都发生在后端硬编码正则/关键词中，LLM 在整条链里没有任何决策权——与 3.1/3.2 的设计完全相反。

## 5. 与设计哲学的偏差分析

### 5.1 核心偏差：记忆决策权完全在后端（D-18 实证）

- 当前"是否计入记忆、记什么内容"100% 由 §4 清单中的后端正则/关键词决定，LLM 被完全排除。
- **已产生真实脏数据**：`data/memory-wiki/pages/identity/profiles/啥名字啊.md`（slug 为"啥名字啊"、title 已人工改为"叶健钦"）；`review-queue.json` 中存在被人工 rejected 的"啥名字啊"、"谁啊"、"不是有点厚脸皮"等错误候选（均为 `我叫…` / `我是…` 正则误提取）。
- **每轮无条件触发**：§4.2 的 6 链在每轮对话尾部无差别运行，观察日志退化为流水账（内容 = 主人原话 + 铃湾原话），与"事实层、低噪声、按需记录"背道而驰。
- **绕过人类把关**：orchestrator 直接调用 upsert 落库（ownerConfirmed: false 但 status: active），完全绕过 policy 层的 memory_wiki 确认规则（`policy/rules.js` L502-585 只约束 LLM 工具调用路径，当前路径根本不经过它）。

## 6. 目标架构：记忆提炼轮次（Memory Distillation Turn）

> 对应 `Cornie-018` Phase 0 / I-18。本文档给出可作为任务分发输入的目标架构草案。

### 6.1 决策点迁移图

| 现状（§4 清单） | 目标（LLM 决策） |
| --- | --- |
| `shouldRecordObservation`（关键词+长度） | LLM 提炼轮次输出 `observations[].action = create/update/skip` |
| `deriveConversationObservation`（原话拼接） | LLM 输出 `content`（事实提炼，非原话） |
| 4 个 identity `extract*Candidate`（正则） | LLM 输出 `identity_updates[]`（entity + fields） |
| `enqueueObservationWikiUpgradeCandidates`（正则入队） | 提炼轮次结果驱动；正则候选彻底删除 |
| orchestrator 尾部 6 链（无条件） | 提炼轮次一次调用；LLM 不可用时**不写入**，引导配置 key |

### 6.2 提炼轮次设计（草案）

- **触发时机**：对话轮次完成后（orchestrator 尾部），替代现有 6 链。
- **输入**（轻量，控成本）：今日最近对话 N 条、今日已有观察日志摘要、相关记忆页摘要（主身份 + 活跃页）。
- **LLM 调用**：低温度（≤0.3）、短输出（maxTokens ≤ 700）、结构化 JSON 输出；沿用 `jsonProtocol` 的解析修复机制（1 次重试）。
- **输出 schema**（草稿）：

```json
{
  "observations": [
    { "action": "create|update|skip", "type": "event|misc|emotion|idea|note",
      "title": "", "content": "事实提炼，非原话", "observationId": "update 时必填" }
  ],
  "identity_updates": [
    { "entity": "profile|person|preference|trait", "action": "create|update|skip",
      "fields": { "…": "实体白名单字段" } }
  ],
  "memory_wiki_requests": [
    { "action": "create_page|update_page|merge_pages|rollback_page|archive_page|delete_page",
      "pageType": "", "title": "", "body": "", "importance": "",
      "pageId": "", "targetPageId": "", "sourcePageId": "", "versionId": "" }
  ],
  "reasoning": "不超过一句话"
}
```

- **后端执行边界**（收窄为执行与治理）：
  - 观察日志：按 LLM 提议 create/update/skip，保留指纹去重与来源补链（现有 `addNoteSmart` 能力）。
  - 身份页面：LLM 提议字段 → 现有 upsert 落库路径（冲突检测、治理入队、topic 补链保留）；候选不再来自正则。
  - Memory Wiki 请求：create/update 直接执行（ownerConfirmed: false）；merge/rollback/archive/delete 等破坏性动作入治理队列（人类审核），与 policy 确认流衔接。
  - **字段白名单校验**（防注入、防非法值），沿用 `jsonProtocol` 校验风格。
- **不可用策略（V1.1 决策，替代原 FALLBACK 设计）**：LLM 不可用（未配置 API Key）/超时/协议解析失败/输出 schema 非法时，**本轮不写入任何记忆**（不创建观察日志、不创建身份页面、不入治理队列），并在界面明确提示用户配置 DeepSeek Key（复用现有配网引导遮罩）。**正则提取函数不做兜底、直接删除**；此取舍成立的前提是：对话本身依赖 LLM，无 Key 时用户本就无法对话，记忆空窗与对话不可用是同一状态。
- **审计**：每次提炼轮次写入 `memory_distillation` 审计事件（提议数/采纳数/跳过数/不可用原因），用于评估 LLM 决策质量与不可用频率。
- **可观测**：遥测埋点（调用次数、时长、token 估算），沿用 `metrics.js` 模式。

### 6.3 与现有机制的衔接

| 机制 | 衔接方式 |
| --- | --- |
| 治理队列（governance） | 提炼轮次的破坏性动作/低置信身份变更入队，人类审核后由现有 apply 链路执行 |
| 确认流（confirm） | 后续接线 `memory_wiki.*` 工具（I-01）后，提炼结果的高风险动作可升级为确认卡 |
| ownerConfirmed | 提炼轮次创建的页面一律 false；仅人类确认后置 true（修复 N-05） |
| 旧 memory 表 / 旧 extract 函数 | 随本轮改造**直接退役**（正则全面弃用，不保留任何兜底路径；仅保留纯文本规范化工具，如 `stripTrailingParticles`、`normalizeString`） |

## 7. 消费侧渐进钻取架构（读取侧草案）

> 对应设计哲学的另一半：**读取什么记忆、读到多深，同样只由 LLM 决定**。本节为 V1.2 新增（基于 0820 设计讨论定稿），与 §6 写入侧并列，共同构成记忆层 LLM 化改造；落地前置条件是 D-01 记忆工具接线（I-01）。

### 7.1 问题与目标

- **问题**：当前消费侧（`agent/wikiContext.js` `buildWikiContext`）每轮对话注入最多 N 页全文 + 主题摘要 + 聊天命中，注入量随记忆库增长线性膨胀；上下文预算固定而记忆无限增长，最终只能靠截断失真。
- **目标**：把"每轮全量注入"改为"**固定小基座 + 按需钻取**"——每轮只带紧凑的画像与目录，LLM 按当前问题决定是否顺着目录逐层读下去、读到多深；多次请求串成一轮回答。
- **原则**：读取侧的"是否读取、读什么"判定权交给 LLM（与写入侧一致）；后端只提供目录、页面读取工具与预算约束，不做语义筛选（§4.11 的 N-06 注入侧规则化随之消解为"排序信号"而非"是否注入"的判定）。

### 7.2 会话上下文分层：固定基座 + 按需钻取

| 层 | 内容 | 规模预算 | 注入时机 |
| --- | --- | --- | --- |
| L0 常驻基座 | 用户画像卡 + 身份/重要人物/高热度主题目录 + 最近对话滚动摘要 + 业务现状摘要（todo/schedule/category） | ~1-2K token | 每轮必带 |
| L1 候选目录 | 按查询命中 / 热度 / 最近更新排序的 top-N 目录条目（摘要 + 重要性 + 最近提及） | 10-20 条，各 30-60 字 | 每轮带（紧凑） |
| L2 全量目录 / 页面 | 全量索引翻页、`memory_wiki.get_page` 全文 | 按需 | 仅 LLM 决定钻取时 |

- **目录条目三信号**（LLM 判断"值不值得钻"的依据）：**摘要 + 重要性 + 最近提及/更新时间**；缺信号则 LLM 无法决策。
- **用户画像卡**：紧凑的"关于主人"摘要卡（名字/称呼/与铃湾关系/当前阶段/关注/压力/沟通偏好 + 重要人物与偏好要点），由**提炼轮次（LLM）持续维护**（§6 写入侧），每轮随 L0 注入。

### 7.3 钻取机制

- **工具通道**：`memory_wiki.get_page` / `list_pages` / `search_topic_index` / `list_topic_index`（已定义未注册，D-01）+ 已注册的聊天片段检索（`system.search_message_snippets` 等）。**本架构落地的前置条件是 D-01 工具接线（I-01）。**
- **多轮协议**：复用现有 JSON 协议 `tool_call` 多轮机制（orchestrator 现支持最多 2 轮，钻取架构下放宽到 3-4 轮并配预算）。
- **预算硬约束**：
  - 每轮钻取次数上限（建议 3-4 次），防死循环（沿用 `toolRoundState.canExecuteReadOnlyLookupRound` 的域级限制思路）；
  - 单页读取内容截断（正文前 N 字符 + 结构化字段）；
  - 轮内结果缓存（`toolRoundState` 已有）避免同轮重复读同一页。
- **跨轮缓存（新增）**：按 `pageId` 的内存短 TTL 缓存（建议 60s~5min），避免相近轮次重复读同一页；**写侧必失效**——提炼轮次/人类编辑更新页面时清除对应缓存（版本号或失效钩子）。对应 Cornie-018 I-11 的读取侧优化。

### 7.4 联想式层间话语（核心交互设计）

**原则：层间话语不是流程播报（"让我找找""正在查询记忆"是胡扯），而是基于本轮已见目录/内容的联想话语——铃湾"想起了什么"，而不是"在检索什么"。**

- **内容来源**：每次钻取时，LLM 手里已有本轮刚看到的目录条目或页面片段；若这些内容触发联想，用一句话说出（例："嗯……她是你高中同桌，你总说她笑起来眼睛弯弯的。"）。
- **生成机制**：钻取请求的 prompt 写明——"每次决定读取一页记忆时，若已见内容触发联想，用一句话说出来；联想必须基于本轮已见内容，像是'哦对…''我记得…''提到这个…'；没有联想就不说；不得播报查找过程。"输出放 `assistant_reply` 字段，立即亮到气泡。
- **护栏（防虚构）**：联想内容必须能追溯到本轮输入中的某条目录/某段文字；拿不准就沉默。**禁止编造"我记得你…"的未见过内容**——幻觉会摧毁信任；审计记录联想文本供抽查。
- **双重价值**：
  1. **体验**：钻取轮与轮之间的等待被"回忆流"填充——活人感来自内容本身，而非状态播报；
  2. **内容**：联想话语可被用户接话确认/纠正——**确认/纠正是最高置信度的记忆信号，回流给提炼轮次**（确认→强化/固化，纠正→修正），联想成为"记忆对账入口"。
- **联想引导钻取**：铃湾说出联想后可顺势决定再钻一层（读关联页），钻取路径从"按问题导航"扩展为"按联想导航"——更像人回忆时被一个细节牵着走。

### 7.5 最终回复流式

- **现状**：`model/deepseek/client.js` `stream:false`，整段生成完才返回。
- **目标**：最终回答阶段改为 `stream:true` + SSE（或 fetch `ReadableStream`），逐字渲染到气泡；思考段（钻取多轮）只吐联想话语，**tool_call 信封不流式**（它是结构化指令，不是给人看的话）。
- **结构建议**：编排器拆为"思考段（信封协议，内部多轮钻取，输出联想话语）+ 说话段（纯文本流式生成最终回答）"；两段解耦，协议更干净（代价：多一次模型调用，可接受）。
- **前端**：`useChat` 增加 `streaming` 消息项，delta 追加、done 定稿并走现有 `saveMessage` 落库。

### 7.6 与写入侧（§6）的闭环

```text
对话轮次
  ├─ 读取侧（本 §7）：L0/L1 基座 + 钻取 → 联想话语 → 用户确认/纠正
  └─ 写入侧（§6）：提炼轮次（LLM 决策）→ 观察/身份/Wiki 变更 → 画像卡更新
       ↑ 用户对联想话语的确认/纠正回流为记忆信号（最高置信度）
```

- 画像卡由提炼轮次维护（写入侧），会话读取画像卡（读取侧）；两侧共用同一 memory-wiki 服务与存储。
- 读取侧与写入侧各自独立可上线：读取侧依赖 D-01（工具接线），写入侧依赖提炼轮次；可并行开发、独立验收。

### 7.7 与 Cornie-018 的关系

本节是 Cornie-018 I-01（工具接线）与 I-11（追溯缓存）的自然延伸，并新增"联想式层间话语"与"流式说话段"两项设计；建议作为 I-18 之后的第二阶段（消费侧改造）排期。

## 9. 风险与依赖

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| LLM 提炼质量不稳定 | 偶发漏记/乱记、输出结构不合法 | jsonProtocol 修复重试 + 字段白名单 + `memory_distillation` 审计持续评估 |
| 每轮额外 LLM 调用成本 | 提炼轮次增加延迟与 token | 低温度短输出、输入轻量化；后续可升级为按日批量提炼 |
| LLM 不可用时的记忆空窗 | 无 Key/超时期间记忆不写入 | 与对话不可用同状态（对话本身依赖 LLM）；界面明确引导配置 Key（复用配网引导遮罩）；审计记录不可用频率 |
| 正则退场范围蔓延 | 删除 extract 函数可能连带破坏治理 apply 链路 | 删除前 grep 全量复核引用 + 测试全绿后再删；按 T-2/T-3 顺序推进，每步独立验收 |
| 钻取延迟叠加 | 每次钻取 2-5s，多轮累计 10-20s | 轮次预算 3-4 + 跨轮缓存 + 联想话语填充感知 + 流式说话段；后续可按日预载热点页 |
| 联想幻觉 | LLM 编造未见过的记忆（"我记得你…"） | 护栏：联想必须溯源本轮输入（目录/页面片段）；拿不准就沉默；审计记录联想文本供抽查 |
| 目录膨胀 | L0/L1 目录条目越来越多 | 分层剪枝：身份页常驻、普通页按热度/最近更新取 TOP-N；条目仅保留三信号 |
| 缓存陈旧 | 写后未失效导致用过期记忆回答 | 写侧必清缓存（版本号或失效钩子）；验收覆盖"写后读新"用例 |
