## 2. 这份备忘的用途

这不是一份“重新做产品定义”的文档，而是一份面向前端 UI / UX 补完的明确备忘。

目标是把当前仓库里：

1. 还没做出来的前端工作台
2. 已经有入口但还很粗糙、很丑、信息层级混乱的页面
3. 需要靠 UI 和交互把价值真正显出来的透明提示 / 来源阅读 / 历史工作台

统一列出来，方便交给 Claude Code 继续做前端产品面。

## 3. 当前仓库真实前端状态

当前仓库里可见的前端核心组件主要是：

1. `src/renderer/App.vue`
2. `src/renderer/ChatHistory.vue`
3. `src/renderer/CornieComposer.vue`
4. `src/renderer/components/LedgerWorkspace.vue`
5. `src/renderer/components/TodoWorkspace.vue`
6. `src/renderer/components/ScheduleWorkspace.vue`
7. `src/renderer/components/MemoryWikiWorkspace.vue`
8. `src/renderer/components/ConfirmCard.vue`
9. `src/renderer/components/ToolResultPanel.vue`

当前最关键的事实是：

1. 没有看到正式的 `ObservationWorkspace.vue`
2. 聊天记录仍是独立轻页面，不像成熟工作台
3. 聊天透明提示与工具结果提示虽然有组件基础，但还没有形成成熟产品面
4. Memory Wiki 已经有工作台基础，但来源阅读、关联阅读、知识网络式浏览体验还未做完

## 4. 给 Claude Code 的总原则

### 4.1 不要只做美化

这次前端工作不能只停留在：

1. 改颜色
2. 改圆角
3. 改按钮样式

而是要把“缺页面、缺区块、缺阅读层级、缺交互落点”的地方一并补上。

### 4.2 不要把前端做成纯后台管理台

Cornie 不是企业后台，不要做成：

1. 满屏卡片堆叠
2. 全是灰白表格
3. 只有 CRUD，没有情绪和引导

它需要兼顾：

1. 个人知识工作台
2. 记忆与日志阅读器
3. 与铃湾协作的温和产品感

### 4.3 不要破坏现有 DeepSeek-only 引导口径

当前模型引导页的平实文案和铃湾口吻要保留，不要把它改回工程调试风。

### 4.4 模型工具集对应的人类入口要继续保持对齐

凡是模型能通过工具做的高价值操作，人类前端侧都应有对应入口，不应只给模型、不给人。

## 5. 当前前端剩余缺漏总表

## 5.1 P0 缺漏：观察日志工作台还没正式存在

这是当前前端最大缺口。

### 现状

后端有观察日志能力，也有与 Topic / Memory Wiki 的联动，但前端正式工作台缺席。

### 需要补的 UI / 页面

1. 主导航中的“观察日志”正式入口
2. 观察日志列表页
3. 按日查看区
4. 观察日志详情页
5. 观察日志新建 / 编辑表单
6. 删除确认流
7. 与 Cornie 日记、聊天记录、长期记忆的联动入口

### 需要补的体验

1. 让用户看懂“观察日志是事实记录，不是文学化日记”
2. 让用户能快速按日浏览和整理
3. 让用户能看到哪些观察已经被用作记忆素材
4. 让用户能从观察日志回跳到相关来源

### 不要做成什么

1. 不要做成一张单薄表格
2. 不要只给 CRUD 按钮，没有上下文说明
3. 不要和 Cornie 日记混成一个页面

## 5.2 P0 缺漏：聊天记录工作台还只是“能看”，不是正式工作台

### 现状

现在有 `ChatHistory.vue`，但整体仍偏轻页面。

### 需要补的 UI / 页面能力

1. 更明确的工作台头部
2. 日期摘要区
3. 回到今天 / 最近访问 / 最近对话日入口
4. 月份为空时的空态页
5. 当天无消息时的空态页
6. 长对话阅读辅助
7. 跨日跳转与回看提示
8. 来源回流提示区

### 需要补的交互表达

1. 当前读的是哪一天，要一眼可见
2. 为什么跳到了这里，要能看懂
3. 回流失败后改看替代落点，也要能理解
4. 长对话不能像原始聊天气泡随便摞一屏

### 当前可直接交给 UI 重构的点

1. 左右结构重做
2. 日期导航密度重做
3. 消息区排版重做
4. 摘要 / 状态 / 回流说明区重做
5. 长对话阅读锚点、跳读、状态提示重做

## 5.3 P0 缺漏：聊天侧记忆引用透明提示与工具结果面板没有成熟产品面

### 现状

现在有：

1. `ToolResultPanel.vue`
2. `ConfirmCard.vue`

但还没有形成真正成熟的“模型行为透明层”。

### 需要补的 UI / 区块

1. 只读补查结果区
2. 写入成功结果区
3. 写入失败结果区
4. 轻量记忆引用提示
5. 失败排障时的静默例外入口
6. 透明提示与最终回复的层级关系

### 需要补的体验

1. 用户能看懂铃湾做了什么
2. 用户能知道这轮有没有参考长期记忆
3. 用户不会被工程术语轰炸
4. 透明提示不抢最终回复主位
5. 失败时给可理解、可恢复的反馈

### 视觉和交互要求

1. 不要把所有结果都做成同一个灰框
2. 过程态、确认态、结果态要有清晰层级
3. 轻提示必须克制，避免恐怖谷
4. 失败态要温和，不要像控制台报错

## 5.4 P0 缺漏：Memory Wiki 来源阅读和关联阅读还没做完

### 现状

`MemoryWikiWorkspace.vue` 已经有较强基础，但还更像治理台和编辑台，不像成熟的知识阅读工作台。

### 需要补的 UI / 页面能力

1. 页面来源引用区
2. 关联页面阅读区
3. Topic 与页面关系可读区
4. 来源类型切换阅读区
5. 比较视角
6. 从来源回跳到原始记录的入口
7. 从正文返回来源阅读区的稳定入口

### 需要补的体验

1. 用户能知道一页记忆从哪里来
2. 用户能知道它和哪些页面相关
3. 用户能把页面、Topic、观察日志、聊天记录串起来读
4. 来源区不能只是技术附件，要成为可读内容的一部分

### 视觉和交互要求

1. 不要只强化治理按钮
2. 要提升阅读感、线索感、知识网络感
3. 比较视角、来源阅读、正文阅读三者要有明确主次

## 5.5 P1 缺漏：App 壳层与导航仍然偏工程壳

### 现状

`App.vue` 已有导航和引导，但整体很可能仍然是“开发可用，不够漂亮也不够高级”的壳层。

### 需要补的 UI / 结构

1. 全局导航视觉重构
2. 当前模块标题区重构
3. 引导遮罩和设置面板视觉优化
4. 主内容区留白、层级、宽度体系重构
5. 页面切换过渡与基础动效

### 需要补的体验

1. 不同模块要有清晰身份感
2. 铃湾口吻要保留，但不能幼稚
3. 整体从“开发样机”升级到“可长期使用的桌面应用”

## 5.6 P1 缺漏：Ledger / Todo / Schedule 虽然已落地，但仍需要统一 UI 语言

### 现状

这三块已经有正式组件和一些产品化提交，但大概率存在：

1. 页面语言不统一
2. 信息层级不统一
3. 表单密度不统一
4. 状态反馈风格不统一

### 需要做的 UI 收口

1. 统一头部结构
2. 统一筛选区、列表区、详情区分层
3. 统一类目管理入口样式
4. 统一空态、加载态、错误态表达
5. 统一确认卡、成功反馈、失败反馈风格

### 说明

这一块不一定是功能缺失，但 UI 质量和一致性很可能还不够。

## 5.7 P1 缺漏：可达性、键盘路径、异步状态可感知性还没有真正做成产品体验

虽然 task 已经拆得很细，但从现状看，这些大概率还是“设计已拆，代码未全落”。

### 重点包括

1. 键盘焦点回落
2. 展开收起后的焦点恢复
3. 多来源切换后的首焦点同步
4. 读屏可感知的状态播报
5. 异步降级、恢复、替代落点时的轻提示

### 给 Claude Code 的要求

UI 不能只顾视觉，必须顺手把这层产品体验一起兑现。

## 7. 给 Claude Code 的视觉方向建议

### 7.1 不要继续灰白后台风

当前最需要避免的是“通用管理后台审美”。

### 7.2 可以更像个人知识桌面工具

建议方向：

1. 更明确的版心和阅读宽度
2. 更好的字体层级
3. 更少但更准的强调色
4. 更轻柔的状态提示
5. 更强的卡片分区，但不要满屏卡片瀑布

### 7.3 铃湾口吻要体现在文案，不要体现在幼态装饰堆砌

重点是温柔、可靠、长期陪伴感，不是卖萌 UI。

## 8. 后端治理当前判断

结论先说：

`后端治理现在基本已经差不多了，可以从“继续补后端概念”切到“以前端产品面落地和联调收口为主”。`

但这个“差不多”是有边界的。

### 8.1 可以认为已经比较成熟的部分

1. 工具网关与策略层主骨架
2. Memory Wiki 后端主链路
3. Topic Index
4. 版本、回滚、审计、巡检
5. 聊天记录与观察日志的后端联动底座
6. DeepSeek-only 主方向
7. 发布治理底座

### 8.2 还不建议过度乐观的部分

1. “模型工具集 = 人类接口集”在前端侧还没完全兑现
2. 一些治理能力虽然已有后端，但前端人类入口还没补齐
3. 发布后的用户真实体验，还没经过前端产品面完整打磨

### 8.3 所以下一步最合理的重心

不是继续优先发明新的后端治理概念，而是：

1. 前端 UI / UX 补完
2. 前后端联调收口
3. 把已存在的后端能力真正显性化给用户

## 9. 最终结论

如果你现在要把工作交给 Claude Code 做 UI，方向是对的。

最值得交出去的不是“重新想需求”，而是：

1. 补观察日志工作台
2. 重做聊天记录工作台
3. 重做聊天透明提示层
4. 深化 Memory Wiki 来源阅读体验
5. 收口全局壳层和三大基础工作台的一致性

一句话总结：

`后端治理主骨架现在基本够用了，真正丑、真正薄、真正还没把价值显出来的地方，已经主要集中在前端。`
