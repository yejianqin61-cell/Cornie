## 2. 文档目的

本文档将 Cornie-020 §4 后端核心维度的 B1-B10 缺陷（经本次深度复核逐条核实）与新增 7 项发现，转化为可开发、可验收的改进设计。本期治理目标为**后端核心**（编排 / 确认流 / 工具链 / 模型层 / API 契约 / 可观测性），范围不含记忆层（memory-wiki/identity/提炼轮，已有专项评估）与数据库（另列批次）。

每个缺陷均已在 git HEAD=75022e7 下实读核实（含 file:line）；实现决策层不绑定具体文件路径，只描述模块职责与接口契约。

## 3. 问题陈述（Problem Statement）

### 3.1 用户视角的问题

1. **操作失败时后端返回 500 而非可理解的 400**：记账缺金额、设置超时非法、待办缺标题等业务校验错误被统一塌缩为"服务器错误"，前端无法区分"用户输入问题"与"系统故障"。
2. **断连后请求仍在空跑**：聊天流式输出时用户关闭窗口/切页，后端 SSE 流与 DeepSeek 调用仍跑完，白耗 token 与带宽。
3. **生成日记偶发报错**：对没有日记条目的日期点"重新生成"，后端抛 500，且前端无友好提示。
4. **故障无处可查**：模型超时/断网/协议失败的轮次在 telemetry 中零记录（成功轮次也不落盘），出问题时无从定位。
5. **同一种操作待遇不一致**：更新账目（update_entry）时协议层按类目域校验参数，策略层却不提供类目映射/确认，提示词也不教——模型行为与治理口径分裂。

### 3.2 开发者/运维视角的问题

6. **协议信封轮代码双份**：对话编排与确认恢复两条路径各有一套"组装 prompt → 调模型 → 解析 JSON → 修复重试"实现，协议改动必须双文件同步，且已出现漂移。
7. **写工具名单三处手写**：同一 7 工具名单在协议校验、编排判定、提示词三处维护，新增写工具容易漏改。
8. **死代码存量**：策略链上有不可达函数、确认服务有无调用方方法、上下文构建器有未用函数。
9. **可观测性名存实亡**：telemetry 结构齐全但无消费方，失败路径零记录；审计仅 console.log。
10. **一致性裂缝**：工具重名注册静默覆盖、HTTP 错误码不映射、路由风格分裂、启动注册竞态。

## 4. 解决方案（Solution）

对应用户/开发者视角的问题，目标态为：

1. **业务校验 400 化**：所有输入类错误返回 400 + 结构化 `{error}`（可带 code/details），只有真实系统故障才 500；日期/必填校验在路由或服务层统一。
2. **断连即停**：SSE 端点监听连接关闭并中止底层流与模型调用；心跳保活；`res.write` 容错。
3. **日记生成健壮**：空条目走兜底（不抛 TypeError），无条目时给友好语义。
4. **可观测性闭环**：telemetry 记录成功/超时/协议失败/网络错误分类，失败路径也埋点，并落盘（本地 JSONL）供查询；审计不再只 console。
5. **单一事实源**：协议信封轮、写工具名单/类目域规则、prompt 提示文本都从单一模块/元数据派生，消除双份与三层分裂。
6. **无死代码**：不可达/无调用方/未引用函数删除；规则表驱动合并。
7. **一致性**：工具重名注册报错、HTTP 错误码映射、路由风格统一、启动注册 await 化无竞态。

## 5. 用户故事（User Stories）

### 5.1 错误语义

1. 作为用户，我希望缺金额、缺标题、非法超时等输入错误收到明确的 400 提示，这样我知道改什么而不是以为系统坏了。
2. 作为开发者，我希望服务层的业务校验抛结构化错误（带 code），这样 HTTP 层能正确映射 4xx 并透出 details。
3. 作为开发者，我希望 `2026-99-99` 这类日期被拒绝，这样脏数据不会流入业务。

### 5.2 断连与流式

4. 作为用户，我关闭聊天窗口后，希望后端停止生成，这样不会白费 token 与带宽。
5. 作为开发者，我希望 SSE 端点监听 `req close` 并中止底层流，这样资源及时释放。
6. 作为开发者，我希望流式连接半截断开时能识别"未完成"，而不是把截断当完整回复。

### 5.3 日记生成

7. 作为用户，我对没有日记条目的日期点"重新生成"时，希望得到友好提示而不是错误。
8. 作为开发者，我希望空条目访问有兜底，这样不会抛 TypeError。

### 5.4 可观测性

9. 作为运维/开发者，我希望每一轮对话的成功/超时/协议失败/网络错误都有分类记录，这样出问题能定位到具体环节。
10. 作为运维/开发者，我希望 telemetry 落盘（JSONL）可被查询，这样不依赖在线日志。
11. 作为开发者，我希望审计记录落盘而不是只 console.log。

### 5.5 单一事实源

12. 作为开发者，我希望协议信封轮只有一份实现，这样协议改动单点生效。
13. 作为开发者，我希望写工具名单/类目域规则只有一个元数据源，这样新增写工具不会漏改。
14. 作为开发者，我希望 `ledger.update_entry` 在类目映射、策略确认、提示词三层行为一致。

### 5.6 死代码与一致性

15. 作为开发者，我希望策略链上没有不可达函数，这样阅读不误判。
16. 作为开发者，我希望工具重名注册直接报错，这样不会静默覆盖。
17. 作为开发者，我希望所有路由用同一错误处理风格，这样维护一致。
18. 作为开发者，我希望启动期工具注册 await 完成，这样首轮对话不会遇到 tool_not_found。
19. 作为开发者，我希望 chatlog 存储层砍掉单驱动抽象壳，这样响应更干净、代码更直白。

## 6. 实现决策（Implementation Decisions）

> 决策只描述模块职责与接口契约，不绑定具体文件路径；落地时以本决策为准。

### ID-1 共享"协议信封轮"模块（解决 B1）

- 新建**协议信封轮模块**：统一封装「组装 messages → 调模型（非流式）→ 解析候选 JSON → 修复重试（1 次）→ telemetry 记录」与 `trimMessages`/`sumPromptChars`；导出常量 `MAX_PROTOCOL_REPAIR_RETRIES`。
- 对话编排（初始/恢复/工具轮）与确认执行器**共同调用**该模块；两处的 tool followup 拼接（"assistant 信封 + user 追问"）也收敛为模块内单一 builder（含 lookupContexts 分支，修复 executor 版缺分支的漂移）。
- 行为等价：现有 orchestrator 与 confirm 测试保持通过。

### ID-2 工具元数据单一来源 + `ledger.update_entry` 补注册（解决 B2/N3）

- 类目域注册表补齐 `ledger.update_entry`：加入 actionToolNames，并配置其 validateToolCall 与类目列表/追问语义（与 add_expense 同族）。
- jsonProtocol 的类目域校验名单、orchestrator 的写工具成功判定名单、prompt 的类目域提示文本，全部改为**从单一元数据源派生**（不再手写三份）。
- 行为等价前提：update_entry 与 add_expense 在协议/策略/提示三层获得一致的类目处理。

### ID-3 业务校验 400 化 + 日期真实性校验（解决 B3/N5）

- 服务层业务校验改抛 `HttpError(400)`（或等价结构化错误），覆盖：ledger amount、todo/schedule title/startAt、settings timeoutMs、observation title、confirm createPending 必填。
- 日期/月份校验器加**真实性校验**（构造 Date 后回读年/月/日比对），拒绝 `2026-99-99` 类输入。
- HTTP 错误中间件支持 `error.code` 映射（4xx 语义表 + 保留 code/details），带 code 的业务错误不再塌缩为 500。

### ID-4 SSE 断连中止与心跳（解决 B7）

- 流式端点监听 `req.on('close')` → AbortController → 下传至流式客户端（chatStream 的 signal），中止 DeepSeek 调用与读取循环。
- `res.write` 包 try/catch（连接已关闭时静默）；周期性发送注释心跳行保活。
- 错误事件保留 `kind:error` 语义并携带分类后的 message。

### ID-5 telemetry 可观测化（解决 B6/N1）

- telemetry 增加失败分类：`outcome.status ∈ { ok, timeout, protocol_failed, network_error, aborted }` 与 `errorCode`；模型调用失败（chat 抛错）时在 catch 路径也调用记录函数（不再零记录）。
- 终态 telemetry **落盘**：写本地 JSONL（如 userData 下 telemetry 目录，按日期分片），提供只读查询入口（不要求前端 UI，接口就绪即可）。
- 审计事件同样落盘（与 telemetry 同目录或既有 audit 通道扩展）。

### ID-6 diary 空条目兜底（解决 N2）

- 生成入口对"无条目"日期做兜底（`getEntry(...) ?? {}` 或路由前置 404 语义），不再读空对象的 `.userText` 抛 TypeError；给前端友好错误文案。

### ID-7 死代码清理与规则表驱动（解决 B4/B5）

- 删除三处死代码：`applyMemoryRule`（连同链上挂载点）、`confirm/service.js` 的 `reject(id)`、`contextBuilder.js` 的 `summarizeTodos`/`summarizeSchedules`。
- 三个 `apply*Rule` 表驱动合并为单一"类目域规则"函数，域差异（validateToolCall 有无）从 domainRegistry 数据读取。

### ID-8 一致性收尾（解决 B10/N4/N5）

- 工具注册：重名即 throw（列出新旧来源），与 domainRegistry 行为一致。
- observation 路由改 asyncHandler + 路由层参数校验（date/type）。
- `server.js` 工具注册 **await 化**（createServer 改 async 或启动期显式 await），失败显式抛错退出启动，消除首轮竞态。
- 启动失败不再仅 console。

### ID-9 模型层统一（解决 B6/N7）

- 统一 fetch 封装（非流式/流式共用 headers/错误映射/超时逻辑）。
- chatStream 网络层加指数退避重试（仅对可重试错误；协议轮重试保持在外层）。
- SSE 解析记录是否收到 `[DONE]`：EOF 未见 `[DONE]` 返回 `finishReason:'incomplete'` 或抛错，由调用方决定回退（不把截断当完整回复）。

### 7.2 每缺陷对应测试要点

- **B1**：信封轮模块单元测试（trim/sum/修复重试/telemetry 记录）；orchestrator 与 executor 双路径集成测试保持通过（等价性证明）。
- **B2/N3**：`ledger.update_entry` 在协议校验/策略确认/prompt 三层一致的用例（类目缺失追问、建类目确认）。
- **B3**：缺 amount/非法日期/非法 timeout → 断言 400 + `{error}`（含 code）；`2026-99-99` 被拒。
- **B4/B5**：规则合并后既有策略用例不回归；死代码删除后全仓引用检查通过（可并入仓库清洁脚本）。
- **B6/N1**：模型失败（超时/断网/协议）→ telemetry `outcome.status` 正确分类且落盘 JSONL 存在记录。
- **B7**：模拟客户端断开 → 断言 abort 信号触发、流停止。
- **B9**：101+ 消息的当日记录按 id 可查（修复后）。
- **N2**：空条目日期调 regenerate → 友好错误而非 500。
- **N7**：SSE 无 `[DONE]` EOF → `finishReason:'incomplete'`。

### 7.3 好测试的标准

只测外部行为（HTTP 状态码、返回结构、telemetry 内容、流终止时机），不测内部实现细节。每个测试以"输入 → 可观察结果"书写；协议/策略层以行为等价为重构判据（合并/表驱动不改决策结果）。
